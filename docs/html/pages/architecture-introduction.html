Architecture Introduction

Bank of Z is a banking application that combines modern web technologies with IBM Z transaction-processing systems. This page is the entry point to the architecture documentation. It describes the main building blocks of the solution and how they fit together. It also shows how a request travels from the browser to the back-end systems.

1. Overview

Bank of Z uses a hybrid architecture. It integrates the following technologies into one banking solution:

  • CICS
  • IMS Transaction Manager (IMS TM)
  • Db2 for z/OS
  • IMS databases
  • z/OS Connect
  • IBM MQ

Users submit requests through a browser-based user interface. z/OS Connect routes each request to the appropriate transaction-processing environment. Business functions run in either CICS or IMS TM. Both environments share common data and application services.

The architecture shows how these technologies can work together in an IBM Z environment:

  • Modern interfaces
  • APIs
  • Transaction-processing systems
  • Databases
  • Messaging technologies

1.1 Key Characteristics

Characteristic Description
Hybrid design Modern web technologies are combined with IBM Z transaction-processing systems.
Single user experience Users work with one banking application through a consistent web interface. This is true even though the underlying transaction-processing path differs.
Multiple transaction managers Business functions run in either CICS or IMS TM.
Shared data and services CICS and IMS TM both use common data and application services.
API-enabled access z/OS Connect exposes the back-end functions as APIs.
Messaging IBM MQ provides messaging capabilities within the solution.
DevSecOps IBM Z development and DevSecOps tooling supports the application lifecycle.

1.2 Solution Components

The application combines these components:

  • A browser-based user interface
  • z/OS Connect APIs
  • CICS transaction processing
  • IMS Transaction Manager (IMS TM)
  • Db2 databases
  • IMS databases
  • MQ messaging
  • IBM Z development and DevSecOps tooling

2. System Architecture

The architecture is organized in layers:

  1. A presentation layer (the web browser).
  2. An API layer (z/OS Connect).
  3. A transaction-processing layer (CICS and IMS TM).
  4. A data and messaging layer (Db2, IMS databases, and IBM MQ).

DevSecOps tooling supports all of these layers.

2.1 High-Level Component View

The diagram below summarizes the main components and how they relate. It is a conceptual view. The source material doesn’t specify which data store each transaction manager uses for each business function.

graph TD U[Browser-Based User Interface] --> ZC[z/OS Connect APIs] ZC --> CICS[CICS Transaction Processing] ZC --> IMS[IMS Transaction Manager] CICS --> SD[Shared Data and Application Services] IMS --> SD SD --> DB2[(Db2 for z/OS Databases)] SD --> IMSDB[(IMS Databases)] SD --> MQ[IBM MQ Messaging] DEVOPS[IBM Z Development and DevSecOps Tooling] -.-> ZC DEVOPS -.-> CICS DEVOPS -.-> IMS

The browser sends all requests to z/OS Connect. z/OS Connect forwards each request to CICS or IMS TM. Both transaction managers share data and application services. These services draw on Db2, IMS databases, and MQ messaging. The dotted lines show that DevSecOps tooling supports the development and delivery of the API and transaction-processing components.

Each layer has a distinct responsibility:

Layer Components Responsibility
Presentation Browser-based user interface Gives users a consistent web interface to the banking application.
API z/OS Connect Receives requests and routes them to the appropriate transaction-processing environment.
Transaction processing CICS, IMS TM Runs the business functions.
Data and messaging Db2, IMS databases, IBM MQ Provides shared data and messaging services.

The layered diagram shows that both transaction managers can reach all three data and messaging components. The source states that data and application services are shared. It doesn’t say how individual functions map to specific data stores.

3. Request Flow

3.1 End-to-End Sequence

A user request follows the same general path whichever transaction manager handles it:

sequenceDiagram participant User participant Browser as Browser UI participant ZC as z/OS Connect participant TM as CICS or IMS TM participant Data as Shared Data and Services User->>Browser: Perform banking action Browser->>ZC: Submit request ZC->>ZC: Select transaction-processing environment ZC->>TM: Route request to CICS or IMS TM TM->>Data: Run business function and access data Data-->>TM: Return results TM-->>ZC: Return response ZC-->>Browser: Return API response Browser-->>User: Display result

The steps are:

  1. The user performs an action in the browser interface.
  2. The browser submits the request to z/OS Connect.
  3. z/OS Connect routes the request to the appropriate transaction-processing environment, CICS or IMS TM.
  4. The business function runs and uses the shared data and application services.
  5. The result returns along the same path to the browser.

3.2 Transaction Routing Decision

The routing decision is transparent to the user. The following flowchart illustrates it:

flowchart TD R[Incoming request from browser] --> ZC{z/OS Connect routes request} ZC -->|CICS-hosted function| C[CICS transaction] ZC -->|IMS-hosted function| I[IMS TM transaction] C --> S[Shared data and application services] I --> S S --> RESP[Response returned to browser]

Users interact with a single banking application and see a consistent web interface. The transaction-processing path behind that interface can differ.

6. Summary

Bank of Z shows how several IBM Z transaction-processing technologies can be integrated into one application. The solution has these features:

  • It has a consistent browser-based interface.
  • It uses z/OS Connect to expose APIs and route requests.
  • It runs business functions in CICS or IMS TM.
  • It shares data and application services across both transaction managers, backed by Db2, IMS databases, and IBM MQ.
  • It supports modern APIs, shared data services, and DevSecOps workflows.
