Repository Structure

The Bank of Z repository is a self-contained z/OS application project that bundles everything needed to develop, build, and deploy a full banking application on IBM Z. It encompasses COBOL/BMS/IMS/PL/I application source code, a browser-based frontend, a z/OS Connect API layer, and a comprehensive automation suite for provisioning middleware, compiling sources with DBB, and deploying artifacts with Wazi Deploy. The repository is organized so that developers can move from a fresh clone to a fully running application with minimal manual steps.

1. Overview

The Bank of Z repository contains the application source, setup automation, build assets, deployment configuration, and supporting documentation required to build and deploy the application. At the top level the project is divided into a small number of well-defined areas:

Directory / File Description
src/ Application source code — COBOL, BMS, IMS, z/OS Connect APIs, and the web frontend
.setup/ All automation for provisioning, building, and deploying Bank of Z
.vscode/ VS Code task definitions for triggering setup and pipeline scripts
scripts/ Utility scripts for downloading and installing IDE extensions
docs/ Product documentation
zcodescan/ ZCodeScan configuration for static analysis
dbb-app.yaml DBB application descriptor
zapp.yaml z/OS application manifest

The diagram below shows the high-level relationship between these top-level areas:

2. System Architecture

Bank of Z is a multi-tier z/OS application. A browser-based frontend communicates with the backend through a z/OS Connect API layer. The API layer in turn invokes CICS transactions and IMS programs written in COBOL and PL/I, which access business data stored in DB2. The repository’s setup automation provisions all of these middleware components — a CICS region, an IMS environment, a DB2 database, and a z/OS Connect server — before building and deploying the application code.

graph TD User[Browser / Web User] -->|HTTP| FE[Frontend WAR\nbank-frontend-vanilla] FE -->|REST API| ZC[z/OS Connect Server\nbankzServer] ZC -->|CICS Link| CICS[CICS Region\nCICSBOZ] ZC -->|IMS Call| IMS[IMS Region] CICS -->|EXEC SQL| DB2[DB2 Database\nBANKZ Tables] IMS -->|DL/I Call| DB2 subgraph z/OS USS FE ZC end subgraph z/OS Middleware CICS IMS DB2 end

The setup automation interacts with all of these tiers. During provisioning it creates DB2 tables, stands up a CICS region using zconfig, and starts a z/OS Connect server. At build time DBB compiles all source languages and packages the outputs into a versioned TAR archive. Wazi Deploy then unpacks that archive and distributes load modules, DBRMs, and WAR files to the correct z/OS datasets and USS directories.

3. Application Source (src/)

The src/ directory contains every line of code that makes up the running Bank of Z application. It is subdivided by transaction path and layer:

Directory Description
src/base/cics/ COBOL programs, BMS maps, and copybooks for the CICS transaction path
src/base/ims/ COBOL programs, PL/I programs, DBDs, PSBs, and copybooks for the IMS transaction path
src/base/batch/ Batch application components
src/api/ z/OS Connect API project — Gradle-based build producing the API deployment artifact
src/frontend/ Browser-based frontend — HTML, CSS, JavaScript, and a Node.js dev server

3.1 CICS Source (src/base/cics/)

The CICS path is the primary online transaction path. It contains a rich set of COBOL programs and BMS map definitions. During a full DBB build the following COBOL programs are compiled into CICS load modules:

Program Purpose
BNKMENU.cbl Main bank menu
BNK1CAC.cbl / BNK1CCA.cbl / BNK1CCS.cbl Customer account screens
BNK1CRA.cbl Credit/account management
BNK1DAC.cbl / BNK1DCS.cbl Debit/account screens
BNK1TFN.cbl Transfer function
BNK1UAC.cbl Update account
CREACC.cbl / CRECUST.cbl Create account / Create customer
DELACC.cbl / DELCUS.cbl Delete account / Delete customer
INQACC.cbl / INQACCCU.cbl / INQCUST.cbl Inquiry programs
UPDACC.cbl / UPDCUST.cbl Update account / Update customer
XFRFUN.cbl Transfer function
DBCRFUN.cbl Debit/credit function
BANKDATA.cbl Shared banking data routines
CRDTAGY1–5.cbl Credit agency integration (agents 1–5)
ABNDPROC.cbl / GETCOMPY.cbl / GETSCODE.cbl Utility and support programs

BMS map sources (.bms files such as BNK1MAI.bms, BNK1TFM.bms, BNK1CCM.bms, etc.) are compiled into MAPLOAD members and deployed alongside the load modules.

3.2 IMS Source (src/base/ims/)

The IMS path provides an alternative transaction processing path using DL/I. It contains:

  • COBOL programs (IBLOGIN1.cbl, IBLOGOUT.cbl, IBTRAN.cbl, IBACSUM.cbl, IBGCUDAT.cbl, IBSCUDAT.cbl, and a set of data-load programs such as LOADACCT.cbl, LOADCUST.cbl)
  • PL/I program (IBLOGIN.pli) — the login module for the IMS path
  • DBDs (Database Descriptors in src/base/ims/DBD/) — assembler source files describing IMS databases: ACCOUNT.asm, CUSTOMER.asm, HISTORY.asm, ACCTYPE.asm, CUSTACCS.asm, CUSTTYPE.asm, TSTAT.asm, TSTATTYP.asm, TTYPE.asm
  • PSBs (Program Specification Blocks in src/base/ims/PSB/) — assembler source files linking programs to databases: IB.asm, IBLOGIN.asm, IBLOGOUT.asm, IBTRAN.asm, IBACSUM.asm, IBGCUDAT.asm, IBSCUDAT.asm, IBLOAD.asm

3.3 z/OS Connect API (src/api/)

The src/api/ directory contains a Gradle-based z/OS Connect API project. Its openapi.yaml specification describes the RESTful banking API that the frontend consumes. The DBB build invokes the Gradle project to produce the api.war deployment artifact that is installed into the z/OS Connect server.

3.4 Frontend (src/frontend/)

The src/frontend/ directory contains the browser-based user interface — HTML, CSS, JavaScript, and a Node.js development server. The DBB build packages it into bank-frontend-vanilla.war, which is co-deployed with the API WAR into the z/OS Connect server.

4. Setup Automation (.setup/)

The .setup/ directory contains all scripts and configuration needed to go from a bare z/OS USS environment to a fully running Bank of Z instance.

graph TD Dev[Developer / CI] -->|Local machine| SL[setup-local.sh] Dev -->|Direct USS SSH| SC[setup-common.sh] SL -->|Zowe CLI remote exec| SR[setup-remote.sh] SR --> SC SC --> V[validate-prereqs stage] SC --> E[environment stage] SC --> I[install-bank-of-z stage] V --> V1[Check DBB version] V --> V2[Check ZOAU version] V --> V3[Check zconfig] V --> V4[Check Wazi Deploy] E --> E1[Clone DBB accelerators] E --> E2[Copy zBuilder framework] E --> E3[Create DB2 tables] E --> E4[Create CICS region via zconfig] E --> E5[Create z/OS Connect server] I --> I1[DBB full build] I --> I2[Wazi Deploy] I --> I3[Populate DB2 tables]

This diagram illustrates the two entry points (direct USS access and VSCode/Zowe CLI) both converging on setup-common.sh, which drives three sequential setup stages.

4.1 Orchestration Scripts

Script Runs on Description
setup-local.sh Local machine Creates the USS workspace, clones the repository on USS, and invokes setup-remote.sh via Zowe CLI. Used by the Zowe CLI workflow.
setup-remote.sh z/OS USS Chains the three setup stages in sequence. Used by both the Zowe CLI and GRUB workflows.
setup-common.sh z/OS USS Implements the three setup stages: validate-prereqs, environment, and install-bank-of-z.
pipeline-local.sh Local machine Uploads pipeline assets and invokes pipeline-remote.sh via Zowe CLI. Used by the Zowe CLI workflow for incremental builds.
pipeline-remote.sh z/OS USS Runs the DBB build and Wazi Deploy on USS. Used by both workflows for incremental builds.

The three stages of setup-common.sh can also be invoked individually from the USS command line:

BASH 
# Stage 1: Verify all prerequisites meet minimum version requirements
.setup/setup-common.sh validate-prereqs

# Stage 2: Provision middleware (DB2, CICS, z/OS Connect)
.setup/setup-common.sh environment

# Stage 3: Build and deploy the Bank of Z baseline
.setup/setup-common.sh install-bank-of-z

4.2 Configuration (config/)

The central configuration file for all setup scripts is .setup/config/config.yaml. It controls workspace paths, dataset naming, and tool locations:

YAML 
# Workspace location on z/OS USS
sandbox:
  path: /usr/local/sandboxes/bank-of-z

# Application identity
app:
  base_name: BANKZ    # Dataset prefix (max 8 chars)
  short_name: BOZ     # Short identifier (max 4 chars)
  zos_version: V0R1M0 # Version for dataset naming

# DBB configuration
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/java21/current_64

Edit this file before running any setup stage to match your z/OS environment.

4.3 Build Configuration (build/)

The .setup/build/ directory contains the DBB zBuilder framework configuration:

File Purpose
datasets.yaml Target dataset definitions for compiled outputs
dbb-build.yaml DBB build pipeline configuration
Language scripts Per-language build scripts (COBOL, BMS, Assembler, PL/I, z/OS Connect)
zosattributes USS file encoding and transfer attributes

4.4 Deployment Configuration (deploy/)

The .setup/deploy/ directory contains Wazi Deploy assets:

  • deployment-method.yml — defines all deployment activities (DBRM copy, DB2 bind, load module copy, CICS NEWCOPY, WAR file deployment, z/OS Connect refresh)
  • Development.yml — environment-specific variable overrides
  • zos_connect_app_config.xml.j2 — Jinja2 template that generates z/OS Connect application configuration XML at deploy time

4.5 JCL Assets (jcl/)

The .setup/jcl/ directory holds JCL submitted during setup, including Db2-grant.jcl for granting DB2 access to application users.

4.6 zconfig Definitions (zconfig/)

The .setup/zconfig/ directory contains zconfig resource definitions used to provision the CICS and IMS regions declaratively. zconfig creates all required CICS datasets (CSD, temporary storage, auxiliary trace, etc.) and starts the CICS region job automatically.

4.7 Task Scripts (tasks/)

Individual task scripts in .setup/tasks/ encapsulate discrete pipeline steps that can be invoked standalone or chained by the orchestration scripts:

Script Purpose
task-dbb-build.sh Invokes the DBB full or incremental build
task-wazi-deploy.sh Invokes Wazi Deploy generate and deploy phases
ZCodeScan task Runs static analysis via ZCodeScan

4.8 Setup Stage Scripts (setup/)

The .setup/setup/ directory contains per-component setup scripts called by the environment stage:

Script Purpose
validate-install.sh Checks DBB, ZOAU, zconfig, and Wazi Deploy version requirements
setup-db2-tables.sh Drops and recreates DB2 tables
setup-cics-region.sh Creates the CICS region using zconfig
setup-zosconnect-server.sh Creates and starts the z/OS Connect server
populate-db2-tables.sh Binds DB2 packages and inserts seed data
grant-perm-user.sh Grants DB2 and RACF keyring permissions to a non-IBMUSER ID

4.9 Shared Library (lib/)

The .setup/lib/ directory contains shared shell functions (logging utilities, common error handling, prerequisite checks, etc.) sourced by all orchestration and task scripts.

5. Build and Deploy Flow

The following sequence diagram shows what happens from source code change to running application during the install-bank-of-z stage (and during any subsequent incremental pipeline run):

sequenceDiagram participant Dev as Developer participant USS as z/OS USS participant DBB as DBB Build participant WD as Wazi Deploy participant CICS as CICS Region participant DB2 as DB2 Dev->>USS: Run setup-common.sh install-bank-of-z USS->>DBB: task-dbb-build.sh (full build) DBB->>DBB: Compile BMS maps → MAPLOAD DBB->>DBB: Compile COBOL → CICSLOAD / IMS load DBB->>DBB: Assemble DBDs and PSBs DBB->>DBB: Compile PL/I → IMS load DBB->>DBB: Build z/OS Connect API WAR DBB->>DBB: Package frontend WAR DBB-->>USS: BANKZ-.tar (build package) USS->>WD: task-wazi-deploy.sh WD->>WD: wazideploy-generate (create deployment plan) WD->>DB2: Copy DBRMs → BANKZ.V0R1M0.DBRM WD->>DB2: BIND PACKAGE for each DBRM WD->>DB2: BIND PLAN WD->>CICS: Copy load modules → BANKZ.V0R1M0.LOADLIB WD->>CICS: NEWCOPY each CICS program WD->>USS: Copy api.war → z/OS Connect apps/ WD->>USS: Copy bank-frontend-vanilla.war → z/OS Connect apps/ WD->>USS: Render zos_connect_app_config.xml.j2 WD-->>Dev: Deployment evidence YAML USS->>DB2: populate-db2-tables.sh (bind + seed data insert)

6. IDE Extension Scripts (scripts/)

The scripts/ directory provides Node.js utilities for managing IDE extension VSIX packages, supporting both VS Code and IBM Bob Premium Package for Z:

Script Description
download-vsix.js Downloads all required IDE extension VSIX packages
install-bobide-vsix.js Installs downloaded VSIX packages into IBM Bob Premium Package for Z
install-vscode-vsix.js Installs downloaded VSIX packages into VS Code

Refer to scripts/README.md for full usage instructions for each script.

7. Static Analysis (zcodescan/)

The zcodescan/ directory contains ZCodeScan configuration, including zcodescan-rules.yaml, which defines the static analysis rules applied to Bank of Z source code during the pipeline. ZCodeScan runs as a task in .setup/tasks/ and requires a separately created configuration file (with ISO8859-1 encoding) in the user’s home directory. A minimal ZCodeScan configuration file example:

YAML 
license_server:
  url: https://127.0.0.1:8195
  user: IBMUSER
  password: MY_PASSWORD
  verify: false

Note: The password field is encrypted automatically after the first scan.

8. Application Manifests

Two manifest files sit at the repository root and describe the application to IBM tooling:

File Description
dbb-app.yaml DBB application descriptor — tells DBB about the application name, source layout, and build configuration location so that task-dbb-build.sh can resolve everything relative to the repository root
zapp.yaml z/OS application manifest — used by z/OS-aware IDE tooling (such as IBM Z Open Editor) to describe the application structure, enabling features like dependency resolution and intelligent code navigation

9. Documentation (docs/)

The docs/ directory contains the product documentation published alongside the application source. It is organized into several sections:

  • Architecture — solution design and component descriptions
  • Installation and Setup — step-by-step provisioning and deployment guides
  • Reference — configuration reference, repository structure (this page), commands reference, and glossary

Documentation is maintained in Markdown and is rendered by a static site generator. Keeping documentation alongside the source ensures it stays in sync with application changes.
