Installation Verification

Bank of Z installation verification confirms that the application stack has been deployed correctly on IBM Z and that the supporting development, middleware, runtime, and API components are operational. This page describes the post-installation checks needed to validate the development workstation, target z/OS connectivity, required platform services, deployed application artifacts, and end-to-end application access.

1. Overview

Installation verification for Bank of Z is intended to establish confidence that the environment is ready for development and use. After deployment, verification should confirm:

  • The local development toolchain is installed and accessible
  • The workstation can communicate with the target z/OS environment
  • Required IBM Z middleware components are available
  • Bank of Z application resources have been deployed successfully
  • Runtime resources are active
  • Application services and APIs respond correctly

A successful verification indicates that Bank of Z is correctly installed and that its components are communicating as expected across the development and runtime environments.

2. System Architecture

Bank of Z verification spans both the local development environment and the target IBM Z platform. The process begins on the workstation, where the installed tooling and z/OS connectivity are validated. Verification then moves to the target environment, where core middleware and deployed application resources are checked, followed by functional validation of application access and API execution.

This architecture shows how verification depends on both platform readiness and application deployment. The workstation tools provide the entry point for validation, while the z/OS platform hosts the middleware and application resources that must be available for Bank of Z to function.

2.1 Verification Scope

The verification scope includes the following layers:

  • Development environment

    • Java
    • Git
    • Zowe CLI

  • Connectivity

    • z/OSMF communication from the workstation to z/OS

  • Target platform

    • z/OS 3.1 or later
    • CICS
    • IMS Transaction Manager
    • IMS DB
    • Db2 for z/OS
    • z/OS Connect Enterprise Edition
    • IBM MQ

  • Application deployment

    • Load modules
    • Db2 tables and plans
    • IMS resources
    • CICS resources
    • z/OS Connect API artifacts
    • Configuration resources

  • Application access

    • User interface access
    • User retrieval
    • Account detail lookup
    • Transaction execution
    • API invocation

2.2 Verification Flow

graph TD A[Start Verification] --> B[Verify Development Tools] B --> C[Verify z/OS Connectivity] C --> D[Verify Target Platform Components] D --> E[Verify Application Deployment] E --> F[Verify Application Access] F --> G[Confirm Operational Environment]

This flow emphasizes that verification should proceed in sequence. Problems found early, such as missing tools or failed connectivity, should be resolved before checking middleware or application behavior.

3. Development Environment Verification

The first stage of installation verification is to confirm that the required tools are installed and accessible from the workstation.

3.1 Verify Java

Java must be present and executable from the command line.

BASH 
java --version

Expected outcome:

  • The command completes successfully
  • A Java version is returned
  • The executable is available in the current shell environment

3.2 Verify Git

Git should be installed and available for source management tasks.

BASH 
git --version

Expected outcome:

  • The command completes successfully
  • A Git version is displayed

3.3 Verify Zowe CLI

Zowe CLI is required to interact with the z/OS environment from the workstation.

BASH 
zowe --version

Expected outcome:

  • The command completes successfully
  • The installed Zowe CLI version is displayed

3.4 Verify Connectivity to z/OS

Once the toolchain is confirmed, validate that the workstation can reach the target z/OS environment through z/OSMF.

BASH 
zowe zosmf check status

Expected outcome:

  • The command returns a successful status
  • The response confirms communication with the target z/OS environment

If this check fails, the remaining platform and application verification steps should be postponed until connectivity is restored.

4. Target Environment Verification

After confirming workstation readiness and connectivity, verify that the IBM Z platform provides the middleware services required by Bank of Z.

4.1 Required Platform Components

The following components should be available in the target environment:

  • z/OS 3.1 or later
  • CICS
  • IMS Transaction Manager (IMS TM)
  • IMS DB
  • Db2 for z/OS
  • z/OS Connect Enterprise Edition
  • IBM MQ

These subsystems collectively support transaction processing, database access, API exposure, and messaging for the application.

4.2 Platform Readiness Validation

The target environment should be reviewed to ensure that each required subsystem is available for use by Bank of Z. If any of these components are unavailable, installation verification is incomplete and the environment should not be treated as ready.

graph TD A[z/OS Platform] --> B[CICS] A --> C[IMS TM] A --> D[IMS DB] A --> E[Db2 for z/OS] A --> F[z/OS Connect EE] A --> G[IBM MQ] B --> H[Transaction Processing] C --> H D --> I[Data Access] E --> I F --> J[API Exposure] G --> K[Messaging Support]

This diagram illustrates the relationship between the core platform components and the roles they serve in Bank of Z.

5. Application Deployment Verification

With the platform confirmed, the next step is to verify that the Bank of Z application resources have been deployed successfully.

5.1 Application Resources to Verify

The following resources should be present and available:

  • Application load modules are available
  • Db2 tables and plans have been created
  • IMS application resources are installed
  • CICS resources are active
  • z/OS Connect API artifacts have been deployed
  • Required configuration resources are available

5.2 Deployment Validation Objectives

Deployment verification should establish that:

  • Executable application components are installed
  • Database definitions required by the application exist
  • Middleware-specific resources are active
  • API definitions are deployed and ready to be invoked
  • Configuration resources needed at runtime are present

5.3 Deployment Dependency View

graph TD A[Bank of Z Deployment] --> B[Load Modules] A --> C[Db2 Tables and Plans] A --> D[IMS Resources] A --> E[CICS Resources] A --> F[z/OS Connect API Artifacts] A --> G[Configuration Resources] B --> H[Application Runtime] C --> H D --> H E --> H F --> I[API Runtime] G --> H G --> I

This dependency view shows that application execution depends not on a single deployment artifact, but on a complete set of runtime, middleware, database, and configuration resources.

6. Application Access Verification

After validating the deployment, verify that the application can process requests successfully.

6.1 Functional Validation Activities

Typical post-installation validation includes:

  • Accessing the Bank of Z user interface
  • Retrieving user information
  • Viewing account details
  • Executing account transactions
  • Invoking deployed z/OS Connect APIs

These checks help confirm that the deployed components are communicating correctly and that Bank of Z is functional from an application perspective.

6.2 End-to-End Validation Sequence

This sequence shows how user actions depend on successful interactions between the application, middleware, data services, and APIs. A successful run validates both deployment correctness and runtime interoperability.

8. Verification Results

A successful installation verification should result in the following outcomes:

  • A configured development environment
  • Access to the target z/OS platform
  • Deployed application artifacts
  • Available middleware resources
  • Operational APIs and services
  • A functioning Bank of Z application environment

If all verification steps complete successfully, the Bank of Z deployment can be considered operational and ready for development activities.

9. Troubleshooting Verification Failures

If verification does not complete successfully, isolate the issue by stage:

9.1 Tooling Failures

Symptoms:

  • java --version fails
  • git --version fails
  • zowe --version fails

Recommended action:

  • Confirm the tool is installed
  • Confirm the executable is on the system path
  • Reopen the shell or reload the environment if needed

9.2 Connectivity Failures

Symptoms:

  • zowe zosmf check status does not return a successful response

Recommended action:

  • Confirm network access to the target z/OS environment
  • Confirm z/OSMF is reachable
  • Resolve authentication or connection issues before continuing

9.3 Platform Availability Failures

Symptoms:

  • One or more required subsystems are unavailable

Recommended action:

  • Contact the system administrator
  • Confirm that required middleware components are started and accessible

9.4 Deployment Failures

Symptoms:

  • Missing load modules
  • Missing database objects
  • Inactive CICS or IMS resources
  • Missing z/OS Connect API artifacts
  • Missing configuration resources

Recommended action:

  • Review deployment completion status
  • Re-run or correct failed deployment tasks
  • Confirm all required application resources were created

9.5 Functional Validation Failures

Symptoms:

  • UI cannot be accessed
  • User or account data cannot be retrieved
  • Transactions fail
  • API calls fail

Recommended action:

  • Verify that middleware and database components are available
  • Confirm that deployed resources are active
  • Recheck application configuration and runtime dependencies
