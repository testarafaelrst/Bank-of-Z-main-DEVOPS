Zowe CLI Workflow

1. Overview

The Zowe CLI workflow is a Git-based development approach that enables developers to build and deploy Bank of Z application changes directly from their local workstation to z/OS USS — without requiring direct SSH access to USS. It relies on two orchestrating shell scripts, setup-local.sh and pipeline-local.sh, which coordinate all build and deployment activities across the local machine and z/OS USS boundaries.

This workflow supports both full environment setup (used during initial provisioning or after infrastructure changes) and incremental builds (used for day-to-day feature development). Changes must be committed and pushed to the remote Git repository before a build is triggered, as the USS environment clones directly from GitHub.

Before using this workflow, ensure you have completed the Deploy Using Zowe CLI setup guide to configure your environment correctly.

2. System Architecture

The Zowe CLI workflow spans two environments: your local workstation and the z/OS USS system. Zowe CLI acts as the bridge, transferring assets and invoking remote scripts over secure channels without requiring the developer to maintain an interactive SSH session.

3. Full and Incremental Build and Deploy

Bank of Z supports two build modes to accommodate different stages of development:

Build Mode When to Use Script
Full Setup First-time environment provisioning or after infrastructure changes setup-local.sh
Incremental Day-to-day development; rebuilds only affected components pipeline-local.sh

For day-to-day development, the incremental build is the preferred approach. It triggers only the DBB build and Wazi Deploy steps, skipping the middleware re-provisioning that occurs during a full setup.

To trigger a full or incremental run directly from the command line:

BASH 
# Full environment setup (first time or after infrastructure changes)
bash .setup/setup-local.sh

# Incremental build and deploy only
bash .setup/pipeline-local.sh

You may also invoke these from USS directly:

BASH 
pipeline-remote.sh

4. Daily Development Cycle

The following sequence diagram illustrates the end-to-end daily workflow from making a code change to validating a live deployment:

4.1. Make Changes

Modify application source code in your local workspace. The following asset types are commonly changed during development:

  • COBOL programs and copybooks — core business logic
  • BMS maps — CICS screen definitions
  • z/OS Connect API assets — API layer definitions
  • Web application components — frontend code
  • Configuration files — environment and runtime configuration

4.2. Commit and Push

Because the USS build environment clones source code directly from GitHub, all changes must be pushed to the remote repository before triggering a build. Any unpushed local commits will not be included in the build.

BASH 
git add .
git commit -m "Your change description"
git push origin your-branch

4.3. Run the Setup or Pipeline Task

You can trigger the build from the command line or from within VS Code.

From the command line:

BASH 
# Full environment setup (first time or after infrastructure changes)
bash .setup/setup-local.sh

# Incremental build and deploy only
bash .setup/pipeline-local.sh

From VS Code:

Open the Command Palette and navigate to Tasks: Run Task, then select the appropriate task. The VS Code task is defined in .vscode/tasks.json as follows:

JSON 
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "Setup Bank of Z Environment",
      "type": "shell",
      "command": "bash .setup/setup-local.sh",
      "problemMatcher": [],
      "presentation": {
        "reveal": "always",
        "panel": "new"
      }
    }
  ]
}

4.4. What Runs Automatically

Once the local script is invoked, the following steps execute automatically across both environments:

graph TD A[setup-local.sh invoked on Local Machine] --> B[Create USS Workspace Directory] B --> C[Clone Branch from GitHub onto USS] C --> D[Invoke setup-remote.sh on USS] D --> E[validate-prereqs] D --> F[environment setup] D --> G[install-bank-of-z] A2[pipeline-local.sh invoked on Local Machine] --> B2[Upload Pipeline Assets via Zowe CLI] B2 --> C2[Invoke pipeline-remote.sh on USS] C2 --> D2[DBB Build] C2 --> E2[Wazi Deploy] D2 --> F2[Artifacts deployed to CICS] E2 --> F2 style A fill:#0066cc,color:#fff style A2 fill:#0066cc,color:#fff style F2 fill:#006400,color:#fff

For full setup, setup-local.sh creates the USS workspace, clones the branch from GitHub, and invokes setup-remote.sh on USS, which then runs prerequisite validation, environment setup, and the full Bank of Z installation.

For incremental builds, pipeline-local.sh uploads pipeline assets via Zowe CLI and invokes pipeline-remote.sh on USS, which executes only the DBB build and Wazi Deploy steps — middleware is not re-provisioned.

4.5. Validate Changes

Once the pipeline completes, open the Bank of Z frontend in your browser to verify that your changes are live:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

5. Performance

The table below compares the Zowe CLI workflow against the GRUB workflow across key operational dimensions:

Operation Zowe CLI GRUB
Initial setup ~5–8 minutes ~3–6 minutes
Incremental update ~5–8 minutes ~5–10 seconds
Requires push to remote Yes No

Note: For rapid iterative development where push-to-remote overhead is undesirable, consider the GRUB workflow. For CI/CD-aligned workflows where a remote repository is the source of truth, the Zowe CLI workflow is the preferred approach.

6. Working with Branches

The local scripts automatically detect your current Git branch and use it when cloning source code on USS. This means each feature branch you work on will be built from its own pushed state on the remote.

BASH 
# Switch to your feature branch before running
git checkout feature/my-change
git push origin feature/my-change
bash .setup/setup-local.sh

To avoid conflicts between developers sharing the same USS system, each developer should configure a separate workspace path in config.yaml. This ensures that concurrent builds do not overwrite each other’s USS working directories.
