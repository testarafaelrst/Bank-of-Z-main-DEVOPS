Tutorial: Incremental Build

This tutorial explains how to perform an incremental build for Bank of Z by changing a COBOL source file, moving that change through Git into the z/OS USS workspace, and running the remote pipeline so that only the affected component is detected, rebuilt, and verified.

1. Overview

An incremental build in Bank of Z shortens build time by avoiding a full application rebuild. Instead of recompiling and redeploying everything, the workflow identifies what changed and rebuilds only the impacted application component.

In this tutorial, you update a COBOL program, push the change to your Git branch, pull the update into the z/OS USS environment, and run the incremental build workflow with pipeline-remote.sh. You then verify that the changed program is detected and included in the build output.

1.1 Goals

By completing this tutorial, you will learn how to:

  • Modify a COBOL program in Bank of Z
  • Commit and push the change to a Git branch
  • Pull the latest changes into z/OS USS
  • Run an incremental build using pipeline-remote.sh
  • Verify that the changed COBOL source is detected
  • Confirm that the affected program is compiled
  • Optionally validate the updated behavior in CICS

1.2 Prerequisites

Before starting, ensure that you have:

  • Completed the Bank of Z deployment tutorial
  • Successfully built and deployed Bank of Z
  • A working Bank of Z development environment
  • Access to the Bank of Z Git repository
  • Access to the z/OS USS environment

1.3 Expected Outcome

After completing this tutorial, you will have made a COBOL change and verified that the Bank of Z incremental build workflow rebuilds the affected application component rather than requiring a complete full build.

2. System Architecture

The incremental build flow spans a local development environment, source control, the z/OS USS working copy, and the Bank of Z build pipeline. The key idea is that a source change originates in Git, is synchronized into USS, and is then analyzed by the build tooling so only changed components are rebuilt.

graph TD A[Developer Workstation] --> B[Git Branch] B --> C[z/OS USS Working Copy] C --> D[pipeline-remote.sh] D --> E[Incremental Build Process] E --> F[DBB Change Detection] F --> G[Compile Changed COBOL Program] G --> H[Updated Bank of Z Component] H --> I[Optional CICS Validation]

In this architecture:

  • The developer workstation is where the COBOL source update is made.
  • The Git branch stores the committed change.
  • The z/OS USS working copy receives the latest source through Git pull.
  • pipeline-remote.sh starts the remote build workflow.
  • DBB change detection identifies the modified source member.
  • Only the changed COBOL program is rebuilt.
  • The updated component can then be optionally validated in CICS.

2.1 Main Components

Component Purpose
COBOL source file Contains the application logic being changed
Git branch Tracks and transports the source change
z/OS USS workspace Hosts the source used by the remote build
pipeline-remote.sh Starts the build execution on the remote environment
DBB Detects changed files and drives incremental compilation
CICS Optional runtime environment for validating behavior

2.2 Incremental Build Relationships

graph TD A[Changed COBOL Source: BNKMENU.cbl] --> B[Git Commit] B --> C[Git Push] C --> D[USS Git Pull] D --> E[Remote Pipeline Execution] E --> F[DBB Detects Changed File] F --> G[BNKMENU Included in Build] G --> H[Updated Runtime Behavior]

This relationship diagram shows that the incremental build is fundamentally driven by source change propagation. The changed file is the trigger for the downstream compile and verification steps.

3. Tutorial Flow

This tutorial is divided into two main parts:

  1. Make and push a COBOL change
  2. Run and verify the incremental build

The example change updates the BNKMENU.cbl COBOL program by modifying the invalid-key message. That change is then committed, pushed, pulled into USS, and processed by the incremental build workflow.

4. Part 1: Make and Push the COBOL Change

The first phase focuses on creating a source-level change that the incremental build process can detect.

4.1 Update the COBOL Program

In the demonstration, the file being changed is:

  • BNKMENU.cbl

The tutorial specifically updates the invalid-key message in this program. The exact business change can vary, but the key requirement is that a real source modification is made so the incremental build process has a changed component to detect.

Example file reference:

TEXT 
BNKMENU.cbl

4.2 Confirm the Correct Git Branch

Before committing, verify that you are working on the intended branch. This is important because the same branch will later be pulled in the z/OS USS environment.

Example:

BASH 
git branch

4.3 Commit the Source Change

Once the COBOL change is saved, commit it to your current branch.

Example:

BASH 
git add .
git commit -m "Update BNKMENU invalid-key message"

4.4 Push the Change to the Remote Repository

Push the committed change so that the z/OS USS environment can retrieve it.

Example:

BASH 
git push

4.5 Change Flow from Development to Repository

sequenceDiagram participant Dev as Developer participant Local as Local Workspace participant Git as Remote Git Repository Dev->>Local: Update BNKMENU.cbl Dev->>Local: Review branch Local->>Git: Commit and push changes Git-->>Local: Change stored on branch

This sequence highlights that the incremental build starts with disciplined source control usage. If the change is not committed and pushed, the remote USS environment will not be able to consume it.

5. Part 2: Run and Verify the Incremental Build

After the source change is available in the repository, move to the z/OS environment and run the remote incremental build.

5.1 Connect to the z/OS Environment

Log in to the z/OS USS environment where the Bank of Z source tree and build scripts are available.

5.2 Confirm the Correct Git Branch in USS

Ensure the USS working copy is on the same branch where the COBOL change was pushed.

Example:

BASH 
git branch

5.3 Pull the Latest Source Changes

Pull the latest changes into the USS workspace.

Example:

BASH 
git pull

This step synchronizes the USS build environment with the latest application source from Git.

5.4 Run the Remote Incremental Build

Execute the Bank of Z remote pipeline script:

BASH 
./pipeline-remote.sh

This script launches the build workflow in the remote environment. In the tutorial, the build is expected to run incrementally so that only the changed component is selected for rebuild.

5.5 Verify DBB Change Detection

After the pipeline runs, review the output to confirm that DBB reports the changed COBOL source file.

The expected verification point is that the modified file, BNKMENU.cbl, is recognized as changed.

Example verification target:

TEXT 
BNKMENU.cbl

5.6 Confirm the Program Is Included in the Build

Next, verify that BNKMENU appears in the compiled or built program list. This confirms that the incremental build did not just detect the file, but also processed it as part of the build.

Example verification target:

TEXT 
BNKMENU

5.7 Optionally Validate the Updated Behavior in CICS

If your environment supports runtime testing, validate that the updated invalid-key message appears in CICS. This step is optional, but it provides end-to-end confirmation that the source change was built and made available to the runtime environment.

6. End-to-End Build Process

The full process combines source update, source control synchronization, remote build execution, and runtime verification.

sequenceDiagram participant Dev as Developer participant Git as Git Repository participant USS as z/OS USS participant Pipe as pipeline-remote.sh participant DBB as DBB participant CICS as CICS Dev->>Git: Push BNKMENU.cbl change USS->>Git: Pull latest branch changes USS->>Pipe: Run pipeline-remote.sh Pipe->>DBB: Start incremental build analysis DBB-->>Pipe: Detect changed COBOL source Pipe-->>USS: Build BNKMENU USS->>CICS: Optional behavior validation CICS-->>Dev: Updated message observed

This sequence shows the operational path of a single change through the Bank of Z delivery workflow. The most important optimization is the DBB-driven identification of changed source, which prevents unnecessary rebuild of unchanged components.

7. Verification Checklist

Use the following checklist to confirm the tutorial completed successfully:

  • BNKMENU.cbl was updated
  • The change was committed to the correct branch
  • The branch was pushed to the remote repository
  • The same branch was checked in z/OS USS
  • The latest changes were pulled in USS
  • pipeline-remote.sh was executed
  • DBB reported the changed COBOL file
  • BNKMENU was included in the build
  • The updated behavior was optionally verified in CICS

9. What This Tutorial Demonstrates

This tutorial demonstrates the Bank of Z incremental build workflow at the application level:

  • A COBOL source file is changed
  • The change is transferred through Git
  • The USS source tree is updated
  • The build pipeline is run remotely
  • DBB identifies the changed file
  • The affected program is rebuilt
  • The resulting behavior can be validated in CICS

This workflow reduces build time by focusing effort on changed components instead of rebuilding the entire application.

10. Conclusion

The Bank of Z incremental build process provides a practical way to shorten build cycles and validate source changes efficiently. By updating a COBOL program such as BNKMENU.cbl, pushing that change through Git, synchronizing it in z/OS USS, and executing pipeline-remote.sh, you can confirm that the build system detects and rebuilds only the affected component.

That makes incremental build an effective development workflow for faster feedback, targeted compilation, and simpler verification of application changes.
