Architecture Overview

Bank of Z is a full-stack banking demonstration application built on IBM Z. It combines a modern, browser-based front end with proven IBM Z transaction-processing systems, showcasing how classic mainframe technologies can be surfaced through contemporary APIs and web interfaces. The application leverages the reliability, security, and throughput of z/OS to handle core banking operations while remaining accessible through standard web protocols.

1. Overview

Bank of Z implements a hybrid architecture that bridges the modern web tier with the IBM Z back end. A browser-based client communicates with z/OS services through z/OS Connect, which acts as the API gateway, translating RESTful HTTP calls into native z/OS requests. Banking logic is executed inside either CICS Transaction Server or IMS Transaction Manager (IMS TM), both of which access shared banking data stored in Db2 for z/OS. External and asynchronous integrations are handled through IBM MQ, which decouples producers from consumers and bridges internal z/OS environments with outside systems.

This design demonstrates how multiple IBM Z middleware products — CICS, IMS, Db2, and MQ — can collaborate within a single unified application while each contributing its particular strengths: CICS for high-volume online transaction processing, IMS TM for reliable message-driven transaction routing, Db2 for relational data persistence and integrity, and MQ for resilient asynchronous messaging.

2. System Architecture

The diagram below illustrates the high-level component topology of Bank of Z, from the browser down to the shared data layer.

graph TD A[Browser / Web Client] -->|REST / HTTP| B[z/OS Connect API Gateway] B -->|CICS Transaction Path| C[CICS Transaction Server] B -->|IMS Transaction Path| D[IMS Transaction Manager] C -->|EXEC SQL| E[(Db2 for z/OS)] D -->|DL/I Calls| E C -->|MQPUT / MQGET| F[IBM MQ Queue Manager] D -->|MQI Calls| F F -->|External Integration| G[External Systems / Partner Banks] C -->|COBOL Business Logic| H[COBOL Application Programs] D -->|COBOL Business Logic| H H -->|Embedded SQL| E

The architecture separates concerns cleanly across tiers:

  • Presentation Tier — The web client sends standard REST calls; no mainframe-specific protocol knowledge is required on the client side.
  • API Gateway Tier — z/OS Connect exposes CICS and IMS services as REST APIs, handling protocol translation transparently.
  • Transaction Processing Tier — CICS and IMS TM provide transactional integrity, security, and high-throughput task dispatching. CICS is particularly suited to high-volume, short-lived online transactions, while IMS TM handles message-driven and hierarchical transaction flows.
  • Business Logic Tier — COBOL programs implement core banking rules, validations, and workflows. These programs run inside CICS or IMS regions and interact with Db2 via embedded SQL.
  • Data Tier — Db2 for z/OS provides the relational data store for all account, customer, and transaction records, enforcing ACID properties across the entire transaction lifecycle.
  • Messaging Tier — IBM MQ decouples components that do not need to communicate synchronously, routing messages between CICS, IMS, and external systems through a managed queue manager.

3. Technology Stack

3.1 CICS Transaction Server

CICS Transaction Server is the primary online transaction processing environment for Bank of Z. It provides runtime qualities of service — including transactional integrity, security, and high-performance task dispatching — without requiring these concerns to be coded into the application programs themselves.

CICS applications in Bank of Z are structured in layers:

Layer Responsibility
Adapter Receives inbound requests (e.g., from z/OS Connect or MQ)
Presentation Formats input/output data structures
Business Logic COBOL programs implementing banking rules
Data Access Embedded SQL calls to Db2

CICS interacts with both Db2 and IBM MQ. For Db2, CICS applications issue embedded SQL inside COBOL programs and rely on the CICS-Db2 attachment facility. For MQ, the CICS-WebSphere MQ adapter runs in the same address space as CICS and manages connections, supports MQI calls from CICS applications, and handles CICS triggering via the CKTI trigger monitor transaction.

A typical CICS COBOL program interacting with Db2 uses the following embedded SQL pattern:

COBOL 
EXEC SQL
    SELECT ACCT_BALANCE
    INTO  :WS-BALANCE
    FROM   ACCOUNT
    WHERE  ACCT_ID = :WS-ACCT-ID
END-EXEC.

IF SQLCODE = 0
    MOVE WS-BALANCE TO WS-OUTPUT-BALANCE
ELSE
    MOVE 'DB ERROR' TO WS-ERROR-MSG
END-IF.

3.2 IMS Transaction Manager

IMS TM provides an alternative transaction processing path within Bank of Z. It is used for message-driven transaction flows, where IMS places work onto its message queues and dispatches application programs in response. IMS TM supports synchronous calls to non-IMS services — including z/OS and distributed environments — through the ICAL (IMS Call) DL/I function code, which allows an IMS-hosted program to invoke external services synchronously.

IMS TM also integrates with IBM MQ via the IMS MQ adapter, which connects the queue manager to IMS and enables IMS application programs to issue MQI calls directly.

3.3 Db2 for z/OS

Db2 for z/OS is the relational data store for all banking data — accounts, customers, balances, and transaction history. Both CICS and IMS application programs access Db2 using embedded SQL. Db2 supports both CICS Transaction Server and IMS as local transaction managers, coordinating ACID updates across distributed resources using XA protocols where needed.

Db2 also supports distributed data access, allowing transactions that span multiple recoverable resources — such as Db2 tables, IBM MQ messages, and IMS databases — to be coordinated atomically.

3.4 IBM MQ

IBM MQ provides the messaging backbone of Bank of Z. The queue manager is the central component: it processes all MQI calls issued by applications, ensures messages reach the correct queues, and manages the channel initiator that connects the z/OS MQ instance to external systems.

graph LR A[CICS Application] -->|MQPUT| B[Request Queue] D[IMS Application] -->|MQPUT| B B --> C[IBM MQ Queue Manager] C -->|MQGET| E[Reply Queue] C -->|Channel Initiator| F[External System / Partner Bank] E -->|MQGET| G[CICS / IMS Response Handler]

The queue manager manages several resource types that are important for reliability:

  • Page sets — persistent storage for MQ object definitions and message data
  • Logs — used to recover messages and objects after a queue manager failure
  • Adapters — connection interfaces for CICS, IMS, and Batch application environments

For CICS applications, the CICS-WebSphere MQ adapter allows CICS programs to call the MQ API (MQPUT, MQGET, etc.) directly, enabling patterns such as request/reply and fire-and-forget messaging without requiring the CICS program to be MQ-aware at a protocol level.

4.2 Asynchronous / Event-Driven Flow via IBM MQ

For operations that require integration with external systems or that benefit from decoupled processing — such as inter-bank transfers or batch notifications — Bank of Z routes messages through the IBM MQ queue manager.

sequenceDiagram participant CICS as CICS Application participant MQ as IBM MQ Queue Manager participant IMS as IMS TM Application participant Ext as External System CICS->>MQ: MQPUT to Request Queue MQ-->>IMS: MQGET (triggered via CKTI / IMS adapter) IMS->>MQ: MQPUT to Reply Queue MQ-->>CICS: MQGET Reply MQ->>Ext: Channel Initiator → Remote Queue Manager Ext-->>MQ: Response Message

4.3 IMS Transaction Path

When a transaction is routed via the IMS path, IMS TM manages the full transaction lifecycle: it receives the inbound message, dispatches the appropriate COBOL program, and handles commit or rollback. If the program needs to interact with an external service, it can issue an ICAL call to synchronously invoke that service without leaving the IMS environment.

5. Cross-Cutting Concerns

5.1 Transactional Integrity

All write operations in Bank of Z are protected by ACID transactions. CICS and IMS both act as local transaction managers for Db2, coordinating commits and rollbacks across application programs and database updates. Where transactions span multiple recoverable resources — for example, both a Db2 table update and an MQ message put — the XA protocol is used to ensure atomic, coordinated updates.

5.2 Security

CICS Transaction Server enforces security at multiple levels: program execution keys (CICSKEY / USERKEY), storage protection (STGPROT), and thread-safety settings (THREADSAFE, QUASIRENT, REQUIRED). These settings control the Task Control Block (TCB) under which a program runs and determine how Db2 and MQ commands are dispatched, providing isolation between application components.

5.3 Scalability

CICS is designed to scale horizontally within a z/OS Parallel Sysplex. Multiple CICS regions can run across multiple LPARs, all sharing the same Db2 data and coupling facility resources. The Sysplex Distributor routes inbound workload across regions, enabling Bank of Z to sustain high transaction volumes without architectural changes to the application programs themselves.

graph TD SD[Sysplex Distributor] --> L1[LPAR 1 — CICS Regions] SD --> L2[LPAR 2 — CICS Regions] SD --> L3[LPAR 3 — CICS Regions] L1 --> CF[Coupling Facility] L2 --> CF L3 --> CF CF --> SD2[(Shared Db2 Data)]

5.4 Modern Integration with z/OS Connect

z/OS Connect is the integration layer that exposes CICS and IMS services as RESTful APIs. It eliminates the need for web-tier developers to understand CICS COMMAREA structures, IMS message formats, or any other z/OS-specific protocol. From the browser’s perspective, Bank of Z is simply a JSON API — the mainframe underpinning is entirely transparent.

6. Summary

Bank of Z demonstrates a production-realistic IBM Z application architecture:

Component Role
Browser / Web Client User interface; communicates via REST/HTTP
z/OS Connect API gateway; REST-to-z/OS protocol bridge
CICS Transaction Server High-volume online transaction processing
IMS Transaction Manager Message-driven and hierarchical transaction processing
COBOL Programs Core banking business logic
Db2 for z/OS Relational data persistence with full ACID support
IBM MQ Asynchronous messaging and external system integration

Together, these components form a layered, resilient, and scalable architecture that delivers modern web accessibility without sacrificing the reliability and throughput that IBM Z is built to provide.
