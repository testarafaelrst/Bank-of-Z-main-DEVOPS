Development Workflows Overview

This document provides a comprehensive overview of the development workflows supported by the Bank of Z application. These workflows enable developers to modify source assets, build and analyze changes, package artifacts, and deploy updates to the target z/OS environment using modern Git-based practices integrated with enterprise mainframe tooling.

1. Overview

Bank of Z bridges modern software delivery practices with enterprise z/OS technologies. Developers can work with standard development interfaces (such as VS Code, Git repositories, and command-line interfaces) while building and deploying components into z/OS subsystems, including IBM CICS, IBM IMS, IBM Db2, and z/OS Connect.

The build and deployment pipelines leverage IBM Dependency Based Build (DBB) to analyze code dependencies and compile modified programs, along with Wazi Deploy to orchestrate deployment and activation across z/OS runtime environments.

Bank of Z supports two primary workflows tailored to different stages of the development cycle:

  • Zowe CLI Workflow: A branch-based, Git-driven workflow utilizing Zowe CLI for cloning repositories to z/OS UNIX System Services (USS) and driving pipeline execution.
  • GRUB Workflow: A rapid-iteration workflow enabling direct file synchronization between the local workstation and z/OS USS without requiring intermediate Git commits.

2.2 Component Interaction Flow

  1. Local Workstation: Developers write and update application code (COBOL programs, BMS mapsets, copybooks, z/OS Connect API definitions, and web interfaces) in their local IDE.
  2. Transfer and Execution Channels:
    • In the Zowe CLI workflow, changes committed to Git are pulled down to z/OS USS via commands orchestrated over Zowe CLI.
    • In the GRUB workflow, changes are synchronized directly to USS directories over SSH.
  3. Pipeline and Build Automation: Shell scripts such as setup-local.sh invoke IBM Dependency Based Build (DBB) to perform dependency analysis and compile affected source assets.
  4. Target Activation: Wazi Deploy processes the built artifacts and deploys them to the target CICS, IMS, Db2, and z/OS Connect runtime subsystems.

3. Core Development Lifecycle

The Bank of Z development lifecycle follows a structured six-phase process to ensure code quality, dependency integrity, and validated deployments.

3.1 Step 1: Make Changes

Developers modify application source code, configuration definitions, or deployment artifacts. Typical changes include:

  • Core COBOL batch and online programs
  • BMS maps for CICS terminal interfaces
  • Shared copybooks and data structures
  • z/OS Connect API definitions and mappings
  • Modern web application components

3.2 Step 2: Commit Changes

When using version-controlled workflows, review changes and commit them to the dedicated feature branch with clear, traceable commit messages.

3.3 Step 3: Run the Pipeline

Initiate the build and deployment pipeline using the selected workflow mechanism. The pipeline performs:

  • Source change analysis
  • Dependency discovery via DBB
  • Compilation and linkage of affected components
  • Packaging of deployment artifacts and generation of deployment plans

3.4 Step 4: Review Results

Inspect the build outputs, execution logs, and generated summary reports. Identify and resolve any compiler diagnostics, unresolved copybook references, or packaging issues.

3.5 Step 5: Deploy Changes

Deploy validated artifacts to the target environment. The deployment process activates updated binaries and configurations across target runtimes:

  • Refreshing program definitions in CICS
  • Loading updated transactions in IMS
  • Executing DDL and BIND operations in Db2
  • Refreshing API endpoints in z/OS Connect

3.6 Step 6: Validate Changes

Perform functional testing and verify runtime application behavior. Confirm transactions execute correctly before promoting changes to shared integration or production environments.

4. Supported Workflows

Bank of Z supports two development workflow models depending on access privileges and the desired turnaround speed.

4.1 Zowe CLI Workflow

The Zowe CLI workflow is a task-based, branch-centric model. It utilizes Zowe CLI to manage remote operations on z/OS USS, clone specific repository branches, and trigger the environment setup and pipeline scripts.

Workflow Execution

Developers can trigger this workflow through configured VS Code tasks or directly via terminal commands invoking the setup script:

BASH 
# Example: Executing the setup script via command line
./setup-local.sh

Key characteristics:

  • Requires changes to be committed and pushed to a Git branch.
  • Operates effectively in environments where direct SSH access to z/OS USS is restricted.
  • Integrates directly into VS Code tasks for automated execution.

4.2 GRUB Workflow

The GRUB workflow is designed for rapid, local iteration during active coding sessions. It synchronizes modified local workspace files directly to the z/OS USS file system without requiring an intermediate Git commit.

Workflow Execution

  • Files are synchronized automatically over SSH upon save or trigger.
  • Setup and build activities are executed immediately on z/OS USS.
  • Provides immediate compiler feedback and rapid turnaround during iterative debugging.

5.2 Selection Guidelines

Use the Zowe CLI workflow when:

  • You follow a strict branch-based development and pull-request model.
  • Changes must be committed and traceable through Git prior to testing.
  • You leverage Zowe CLI integration within VS Code.
  • SSH access to z/OS USS is limited or unavailable due to network security policies.

Use the GRUB workflow when:

  • You need to test code modifications immediately without creating intermediate commits.
  • You require rapid feedback loops during complex debugging or iterative coding.
  • You have direct SSH access configured to the target z/OS USS environment.
  • You frequently make small, incremental changes that require rapid compilation and deployment validation.

6. Development Best Practices

Adhere to the following best practices when modifying, building, and testing applications in Bank of Z.

6.1 Work in Isolated Branches

Always create a dedicated feature or bugfix branch for your work. Isolating changes ensures uncommitted or intermediate code does not impact shared baselines and simplifies pull request reviews.

6.2 Keep Workspace Configuration Up to Date

Review local environment and workspace configuration settings prior to executing tasks. Ensure file paths, connection profiles, and environment variables match the target z/OS runtime. Update local configurations before initiating pipeline runs.

6.3 Make Small, Incremental Changes

Implement features and defect fixes in small, manageable units. Small changes reduce build times, simplify root-cause analysis when build or runtime errors occur, and streamline peer reviews.

6.4 Validate Changes Frequently

Trigger the setup and deployment pipeline after each incremental change. Running early validations ensures syntax, copybook references, and deployment mappings remain functional throughout the development cycle.

6.5 Keep Source Changes Organized

Maintain source files in their designated project directories (e.g., COBOL programs, copybooks, BMS map sources, API configurations) in accordance with project naming and structural conventions.

6.6 Review Setup Output and Logs

Always inspect output streams and logs generated during setup and deployment. Check for compilation warnings, link-edit return codes, and subsystem deployment notices before proceeding to validation testing.

6.7 Synchronize Regularly

Regularly synchronize local workspaces and branches with the primary project repository to incorporate upstream changes, prevent merge conflicts, and ensure dependencies remain compatible.

6.8 Document Significant Changes

Update project documentation whenever adding application capabilities, altering build dependencies, or updating environment configuration parameters.
