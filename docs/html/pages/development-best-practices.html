Development Best Practices

Recommended best practices for developing, testing, and maintaining Bank of Z code on IBM Z, covering branching strategies, code quality, and collaboration guidelines.

1. Overview

The Bank of Z project runs on IBM Z infrastructure and involves a mix of technologies including COBOL programs, copybooks, BMS maps, web applications, and z/OS Connect artifacts. To ensure code quality, maintainability, and team collaboration, every contributor should follow a consistent set of development practices.

These guidelines cover the full development lifecycle — from setting up your local workspace, through making and validating changes, to merging and documenting your work. Whether you are working on a new feature, an enhancement, or a defect fix, these practices help reduce risk, improve turnaround time, and keep the codebase in a healthy state.

2. System Architecture

The Bank of Z development environment is organized around a version-controlled source repository, a z/OS target environment, and two primary deployment workflows. The diagram below illustrates how these components relate to each other.

graph TD A[Developer Workstation] --> B[Local Workspace / Branch] B --> C{Workflow Selection} C -->|Version-Controlled Changes| D[Zowe CLI Workflow] C -->|Rapid Local Testing| E[GRUB Workflow] D --> F[Source Repository - Main Branch] E --> F F --> G[z/OS Target Environment] G --> H[COBOL Programs] G --> I[BMS Maps] G --> J[Copybooks] G --> K[Web Applications] G --> L[z/OS Connect Artifacts]

This architecture ensures that all changes flow through a controlled path — from the developer’s local environment, through a workflow, into the shared repository, and finally onto the IBM Z runtime. Selecting the right workflow at the branching stage is a key decision that affects testing speed and code quality.

3. Branching Strategy

3.1 Work in Isolated Branches

Create a dedicated branch for each feature, enhancement, or defect fix. Isolating changes makes it easier to review, test, and manage updates before they are merged into the main code line.

gitGraph commit id: "Initial Commit" branch feature/new-account-screen checkout feature/new-account-screen commit id: "Add BMS map" commit id: "Update COBOL logic" checkout main branch fix/transaction-defect checkout fix/transaction-defect commit id: "Fix balance calculation" checkout main merge feature/new-account-screen id: "Merge feature" merge fix/transaction-defect id: "Merge fix"

Each branch should represent a single unit of work. This keeps the main code line stable and makes code reviews focused and actionable.

3.2 Synchronize Regularly

Keep your local workspace synchronized with the latest project changes to reduce merge conflicts and ensure that development is based on the most current source.

Tip: Pull from the main branch frequently — especially before starting a new branch or submitting changes for review.

4. Workspace Configuration

4.1 Keep Your Workspace Configuration Up to Date

Review your setup configuration before starting development activities. Ensure that paths, environment settings, and required dependencies match your target environment.

If configuration values change, update your local environment before running setup or deployment tasks.

Key configuration items to verify before each development session:

Configuration Item Description
Target environment paths Ensure dataset and directory paths point to the correct z/OS environment
Environment variables Verify that all required variables are set for your current workspace
Dependency versions Confirm that required tools (e.g., Zowe CLI, compilers) match the expected versions
z/OS Connect settings Validate connection endpoints and credentials for API artifacts

5. Code Quality Practices

5.1 Make Small, Incremental Changes

Implement and validate changes in small increments rather than making large updates at once. Smaller changes are easier to test, troubleshoot, and review.

CODE 
* Example: Isolate a COBOL module change to a single paragraph
* rather than modifying multiple sections in one commit.

 CALCULATE-INTEREST.
     COMPUTE WS-INTEREST = WS-BALANCE * WS-RATE / 100
     END-COMPUTE.

Large, sweeping changes increase the risk of introducing defects and make root-cause analysis significantly harder.

5.2 Validate Changes Frequently

Run the appropriate setup and deployment workflow after making changes to verify that updates build and deploy successfully. Early validation helps identify issues before they affect additional development work.

The sequence below illustrates a recommended validation cycle:

sequenceDiagram participant Dev as Developer participant WS as Local Workspace participant WF as Workflow Engine participant ZOS as z/OS Target Dev->>WS: Make incremental code change Dev->>WF: Trigger setup/deployment workflow WF->>ZOS: Compile and deploy artifacts ZOS-->>WF: Build result (success/error) WF-->>Dev: Report output and logs Dev->>Dev: Review warnings and errors Dev->>WS: Apply fixes if needed Dev->>WF: Re-trigger workflow WF->>ZOS: Re-deploy ZOS-->>WF: Success WF-->>Dev: Confirmation

5.3 Keep Source Changes Organized

Store application updates in the appropriate source directories and follow established project conventions for all artifact types:

Artifact Type Source Directory Convention
COBOL Programs Main application source folder, following program naming standards
Copybooks Shared copybook directory, referenced by multiple programs
BMS Maps BMS source directory, one map per screen/panel
Web Applications Web source tree, following frontend project structure
z/OS Connect Artifacts API definition directory, organized by service

Following these conventions ensures that automated build and deployment workflows can locate and process all artifacts correctly.

6. Workflow Selection

6.1 Use the Workflow That Matches Your Development Needs

Select the workflow that best supports your current task. Using the wrong workflow can slow down development or introduce unnecessary overhead.

flowchart TD A[Start Development Task] --> B{Is this a committed,\nversion-controlled change?} B -->|Yes| C[Use Zowe CLI Workflow] B -->|No - Rapid local test| D[Use GRUB Workflow] C --> E[Push to Branch] D --> F[Test Locally] E --> G[Submit for Review] F --> H{Changes validated?} H -->|Yes| E H -->|No| I[Revise Code] I --> F G --> J[Merge to Main] J --> K[Deploy to z/OS Environment]

Zowe CLI Workflow

Use the Zowe CLI workflow when:

  • Working with branch-based development and version-controlled changes.
  • Changes need to be tracked, reviewed, and merged into the shared repository.
  • Collaborating with other contributors on the same project.

GRUB Workflow

Use the GRUB workflow when:

  • You want to rapidly test local changes without committing them first.
  • Performing exploratory development or quick diagnostics.
  • Validating a fix before formalizing it into a branch commit.

Note: Selecting the appropriate workflow can improve development efficiency and reduce turnaround time during testing.

7. Monitoring and Review

7.1 Review Setup Output

Monitor workflow output and setup logs during development activities. Review any warnings or errors before proceeding to the next task.

Recommended log review checklist:

  • [ ] No compilation errors in COBOL programs or copybooks
  • [ ] No binding errors for DB2 plans or packages
  • [ ] BMS map assemblies completed without warnings
  • [ ] z/OS Connect API deployments returned successful status
  • [ ] No JCL errors or abends in deployment jobs

Ignoring warnings early in development can lead to harder-to-diagnose failures later in the lifecycle.

8. Documentation and Collaboration

8.1 Document Significant Changes

Update relevant documentation when introducing new functionality, modifying configuration requirements, or changing development processes. Keeping documentation current helps other contributors understand and use your changes.

Changes that should always be accompanied by documentation updates:

  • New features or screens — Update user-facing and technical documentation to describe the new functionality.
  • Configuration changes — Record any new environment variables, dataset paths, or dependency updates.
  • Process changes — If a development or deployment process is modified, update the relevant workflow documentation.
  • API changes — Update z/OS Connect API definitions and any integration documentation affected by the change.

8.2 Collaboration Guidelines

The following practices support effective team collaboration on Bank of Z:

  1. Communicate early — Raise questions or flag blockers as soon as they are identified, rather than waiting until a change is complete.
  2. Write descriptive commit messages — Clearly describe what changed and why, so that the history of the codebase is understandable.
  3. Request reviews before merging — Have at least one other contributor review your changes before merging to the main branch.
  4. Respect branch ownership — Avoid modifying another contributor’s active branch without coordination.
  5. Keep branches short-lived — Merge or close branches promptly once their purpose is fulfilled to keep the repository clean.

9. Summary of Best Practices

The table below provides a quick reference for all recommended practices covered in this document.
