Build & Deployment Architecture

Bank of Z automates the full lifecycle of application delivery — from source compilation through runtime provisioning — using a modern, IBM Z-native toolchain. This page describes the build pipeline, artifact management strategy, and deployment topology for both CICS and IMS runtime environments. The pipeline is orchestrated by IBM Dependency Based Build (DBB), Wazi Deploy, zconfig, and the z/OS Connect CLI, ensuring repeatable and auditable deployments across all target environments on IBM Z.

1. Overview

The Bank of Z application is built from a polyglot source base that includes COBOL, PL/I, Assembler, BMS maps, Db2 definitions, Java source, and z/OS Connect API definitions. These sources are compiled and packaged into a unified deployment archive, which is then provisioned to one of two supported runtime targets: a CICS/Db2 environment or an IMS TM/DB/Db2 environment. Both paths are fronted by z/OS Connect APIs that expose the mainframe transactions as RESTful services.

The pipeline supports two operational modes:

  • Full build — Compiles all components from scratch and provisions a complete runtime environment. Used for initial installation or infrastructure-level changes.
  • Incremental build — Rebuilds only the components affected by source changes and deploys them to an existing environment. Used for day-to-day development and defect fixes.

3. Build Pipeline

3.1 IBM Dependency Based Build (DBB)

IBM DBB is the core build engine for Bank of Z. It performs dependency analysis on the source tree to determine which components must be compiled, then drives the compiler and link-edit steps for each affected module.

Inputs to the build:

Source Type Description
COBOL programs Core business logic (e.g., account management, transactions)
PL/I programs Supplementary application programs
Assembler programs Low-level utility and interface routines
BMS map definitions CICS screen layouts
Db2 source definitions DDL for tables, views, and bind parameters
Java source Java components for z/OS Connect integration
z/OS Connect API definitions API configuration and routing definitions

Outputs from the build:

Artifact Type Description
Load modules Compiled and link-edited COBOL, PL/I, Assembler, and BMS modules
Db2 tables & plans Provisioned Db2 objects and bound application plans
JAR files Packaged Java application archives
z/OS Connect artifacts Configured API definitions for CICS and IMS routes
Wazi Deploy archive Unified deployment package containing all of the above

4. Full and Incremental Builds

4.1 Full Build

A full build compiles all application components regardless of whether they have changed, packages the complete application, and prepares it for deployment. This workflow is used when:

  • Setting up a new Bank of Z environment for the first time.
  • Runtime infrastructure or environment configuration changes require a complete redeployment.

4.2 Incremental Build

An incremental build rebuilds and deploys only the components affected by source code changes. IBB DBB automatically identifies which source files have been modified and limits compilation to those files and their dependents. This workflow is intended for:

  • Day-to-day development activities such as feature enhancements.
  • Defect fixes that touch a limited number of source modules.

After the initial deployment, incremental builds are triggered via the pipeline-remote.sh script:

BASH 
# Trigger an incremental build and deploy against an existing environment
./pipeline-remote.sh

The script automatically:

  1. Identifies modified source files since the last build.
  2. Rebuilds impacted components.
  3. Packages the updated artifacts into a new deployment archive.
  4. Deploys the updated archive to the existing runtime environment.

Note: An incremental build requires an existing Bank of Z environment that has already been successfully deployed. Use a full build when setting up a new environment or when infrastructure changes require a complete redeployment.

4.3 Build Mode Comparison

Characteristic Full Build Incremental Build
Scope All components Changed components and dependents only
Typical duration Longer Shorter
Use case Initial setup, infrastructure changes Feature development, defect fixes
Requires existing environment No Yes
Triggers runtime reprovisioning Yes No

5. Artifact Management

All build outputs are consolidated into a single Wazi Deploy deployment archive. This archive is the unit of deployment — it contains every artifact that Wazi Deploy needs to install and configure the application on a target runtime.

graph LR LM[Load Modules] --> WD[Wazi Deploy Archive] DB[Db2 Tables & Plans] --> WD JAR[JAR Files] --> WD API[z/OS Connect Artifacts] --> WD WD -->|Deploy to CICS| CICS[CICS Runtime] WD -->|Deploy to IMS| IMS[IMS Runtime]

The archive approach provides several benefits:

  • Traceability — Each archive captures a precise snapshot of all artifacts from a single build, enabling rollback and audit.
  • Atomicity — Deployments are based on a complete, consistent set of artifacts rather than individual files.
  • Portability — The same archive can be promoted through multiple environments (e.g., development → test → production).

6. CICS Deployment

6.1 CICS Deployment Workflow

After the build completes, Wazi Deploy installs the generated artifacts into the CICS runtime provisioned by zconfig. The z/OS Connect APIs are then configured to route incoming REST requests to the CICS transaction-processing environment.

sequenceDiagram participant Archive as Wazi Deploy Archive participant WD as Wazi Deploy participant ZC as zconfig participant CICS as CICS Region participant DB2 as Db2 Subsystem participant ZOC as z/OS Connect Archive->>WD: Initiate CICS deployment WD->>ZC: Provision CICS runtime environment ZC-->>CICS: CICS region started & configured WD->>CICS: Install load modules (COBOL/PL/I/Assembler/BMS) WD->>DB2: Bind Db2 plans & provision tables WD->>ZOC: Deploy z/OS Connect API definitions ZOC->>CICS: Configure API-to-transaction routing ZOC-->>Archive: CICS deployment complete

6.2 CICS Runtime Components

Component Role
CICS Region Executes COBOL, PL/I, and Assembler transaction programs
BMS Maps Provides screen definitions for CICS terminal interactions
Db2 Subsystem Stores and retrieves application data via bound plans
z/OS Connect Exposes CICS transactions as RESTful APIs

7. IMS Deployment

7.1 IMS Deployment Workflow

IMS application artifacts are deployed to the IMS region provisioned by zconfig. The z/OS Connect APIs are configured to route requests to the IMS Transaction Manager ™ environment, with IMS DB handling persistent data storage alongside Db2.

sequenceDiagram participant Archive as Wazi Deploy Archive participant WD as Wazi Deploy participant ZC as zconfig participant IMS as IMS TM Region participant IMSDB as IMS DB participant DB2 as Db2 Subsystem participant ZOC as z/OS Connect Archive->>WD: Initiate IMS deployment WD->>ZC: Provision IMS runtime environment ZC-->>IMS: IMS TM region started & configured ZC-->>IMSDB: IMS DB initialized WD->>IMS: Install load modules WD->>IMSDB: Provision IMS DB definitions WD->>DB2: Bind Db2 plans & provision tables WD->>ZOC: Deploy z/OS Connect API definitions ZOC->>IMS: Configure API-to-transaction routing ZOC-->>Archive: IMS deployment complete

7.2 IMS Runtime Components

Component Role
IMS TM Region Executes IMS transaction programs
IMS DB Hierarchical database for IMS application data
Db2 Subsystem Relational data storage accessed alongside IMS DB
z/OS Connect Exposes IMS transactions as RESTful APIs

8. Tooling Summary

The following table summarizes the tools involved in the Bank of Z build and deployment pipeline and their respective roles:

Tool Role
IBM DBB Performs dependency analysis and compiles all application source (COBOL, PL/I, Assembler, BMS, Java)
Wazi Deploy Packages build artifacts into a deployment archive and installs them into CICS and IMS runtimes
zconfig Provisions and configures the CICS and IMS runtime environments on IBM Z
z/OS Connect CLI Configures and starts z/OS Connect APIs that expose CICS and IMS transactions as REST services
graph TD DBB[IBM DBB\nBuild Engine] -->|Compiled Artifacts| WD[Wazi Deploy\nPackage & Deploy] WD -->|Provision Request| ZC[zconfig\nRuntime Provisioning] WD -->|API Configuration| ZOC[z/OS Connect CLI\nAPI Management] ZC -->|CICS Runtime| CICS[CICS Region] ZC -->|IMS Runtime| IMS[IMS TM / IMS DB] ZOC -->|Route to CICS| CICS ZOC -->|Route to IMS| IMS

Each tool plays a distinct, non-overlapping role in the pipeline, ensuring clear ownership of the build, packaging, provisioning, and API exposure concerns.
