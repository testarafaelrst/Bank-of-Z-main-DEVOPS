Architecture Overview

Bank of Z is a hybrid banking application that unifies modern web technologies with IBM Z transaction-processing systems. It demonstrates how CICS, IMS Transaction Manager, Db2 for z/OS, IMS databases, z/OS Connect, and IBM MQ can be orchestrated into a single, cohesive banking solution — accessible through a standard browser-based interface.

1. Overview

Bank of Z delivers a full-featured banking experience by routing user requests from a modern web front end through z/OS Connect APIs into IBM Z transaction-processing environments. Depending on the transaction path, business logic is executed within either CICS or IMS Transaction Manager (IMS TM), each backed by their respective database systems (Db2 for z/OS and IMS databases). Shared messaging services via IBM MQ enable integration between components and with external systems.

This architecture proves that IBM Z is not a legacy silo — it is a modern, API-enabled platform capable of supporting DevSecOps workflows, cloud-native interfaces, and enterprise-grade transaction processing simultaneously.

The application combines:

  • A browser-based user interface for end-user interaction
  • z/OS Connect APIs for bridging web and mainframe protocols
  • CICS transaction processing for one set of banking operations
  • IMS Transaction Manager (IMS TM) for an alternate transaction path
  • Db2 for z/OS as the relational database backend
  • IMS databases as the hierarchical database backend
  • IBM MQ messaging for asynchronous integration and external communication
  • IBM Z development and DevSecOps tooling supporting modern CI/CD pipelines

2. System Architecture

The Bank of Z system is organized into distinct layers, each with a clear responsibility. The diagram below illustrates how these layers interact, from the user’s browser down to the core data stores.

The architecture is structured in three broad tiers:

Tier Components Responsibility
Presentation Browser-based UI User interaction and display
API & Transaction z/OS Connect, CICS, IMS TM Request routing, transaction execution
Data & Messaging Db2, IMS DB, IBM MQ Persistent storage, async messaging

Although two distinct transaction-processing paths exist (CICS and IMS TM), users interact with a single, consistent web interface — the routing is transparent at the application level.

3. Component Details

3.1 Browser-Based User Interface

The front end is a standard web application delivered to the user’s browser. It communicates with the IBM Z back end exclusively through z/OS Connect REST APIs, meaning no mainframe client software is required on the user’s machine. All banking operations — account inquiry, fund transfer, transaction history — are initiated from this layer.

3.2 z/OS Connect API Gateway

z/OS Connect acts as the integration bridge between the modern web interface and IBM Z transaction-processing systems. It exposes RESTful APIs over HTTP/S and maps incoming JSON payloads to the appropriate CICS or IMS TM transaction invocations.

sequenceDiagram participant U as User Browser participant Z as z/OS Connect participant C as CICS participant I as IMS TM participant D as Db2 for z/OS participant M as IBM MQ U->>Z: REST API Call (JSON/HTTPS) alt CICS Transaction Path Z->>C: Invoke CICS Transaction C->>D: Execute SQL Query D-->>C: Return Result Set C-->>Z: Transaction Response else IMS Transaction Path Z->>I: Invoke IMS Transaction I->>M: Publish MQ Message M-->>I: Acknowledgement I-->>Z: Transaction Response end Z-->>U: JSON Response

This sequence illustrates the two possible paths a banking request can take once it enters the IBM Z platform. The user experience remains identical regardless of which path is taken.

3.3 CICS Transaction Processing

CICS (Customer Information Control System) handles one branch of banking transactions. COBOL application programs run within CICS regions, processing business logic and interacting with Db2 for z/OS via embedded SQL statements.

A typical CICS-based banking program uses EXEC CICS commands for transaction control and EXEC SQL for data access:

COBOL 
* Retrieve account balance via CICS/Db2
EXEC SQL
    SELECT ACCOUNT_BALANCE
    INTO   :WS-BALANCE
    FROM   ACCOUNTS
    WHERE  ACCOUNT_ID = :WS-ACCOUNT-ID
END-EXEC

IF SQLCODE = 0
    EXEC CICS RETURN
    END-EXEC
ELSE
    EXEC CICS ABEND ABCODE('DBER')
    END-EXEC
END-IF

CICS provides high-throughput, low-latency transaction execution, making it ideal for synchronous, user-facing banking operations.

3.4 IMS Transaction Manager (IMS TM)

IMS Transaction Manager provides a second transaction-processing path within Bank of Z. IMS TM processes messages from its message queues and executes corresponding application programs. These programs interact with IMS databases using DL/I calls and may also publish messages to IBM MQ for downstream integration.

IMS TM complements CICS by demonstrating that multiple IBM Z transaction environments can coexist within a single application, each optimized for specific workload characteristics.

3.5 Db2 for z/OS

Db2 for z/OS serves as the relational database for the CICS transaction path. It stores core banking data — accounts, balances, customers, and transaction history — in a structured, SQL-accessible format. COBOL programs running in CICS use embedded SQL (via EXEC SQL blocks) to read and write this data.

3.6 IMS Databases

IMS databases store data accessed by the IMS TM transaction path. They use a hierarchical data model accessed via DL/I (Data Language/I) calls. This provides an alternative persistent storage layer that is entirely separate from Db2, demonstrating the breadth of IBM Z database technologies.

3.7 IBM MQ Messaging

IBM MQ provides asynchronous messaging capabilities within the Bank of Z architecture. Both CICS and IMS TM can interact with MQ, enabling:

  • Decoupled integration between application components
  • External system communication (e.g., payment networks, notification services)
  • Reliable message delivery with guaranteed once-and-only-once semantics

MQ acts as the backbone for any event-driven or asynchronous processing within the platform.

5. DevSecOps and Modern Development

Bank of Z is designed to support modern software development practices alongside its IBM Z runtime components. IBM Z development tooling integrates with standard DevSecOps workflows, enabling:

  • Source control using Git-compatible repositories
  • Automated build and test pipelines for COBOL, PL/I, and other z/OS languages
  • Security scanning integrated into the CI/CD pipeline
  • Deployment automation targeting CICS and IMS environments

This ensures that Bank of Z is not only a demonstration of IBM Z runtime capabilities, but also of how mainframe development can align with enterprise DevSecOps standards.

6. Architectural Principles

The Bank of Z architecture is guided by several key principles:

Principle Implementation
Unified User Experience A single web interface regardless of backend transaction path
API-First Integration All Z services exposed via z/OS Connect REST APIs
Technology Breadth Both CICS and IMS TM used to demonstrate complementary capabilities
Data Separation Db2 and IMS databases used independently per transaction path
Modern Operations DevSecOps tooling integrated into the development lifecycle
Reliability IBM MQ ensures resilient, guaranteed messaging
