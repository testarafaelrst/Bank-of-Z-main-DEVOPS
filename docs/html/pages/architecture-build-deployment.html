Build & Deployment Architecture

This document describes how Bank of Z source code is transformed into deployable artifacts and how those artifacts are provisioned across CICS and IMS runtime environments. The pipeline leverages IBM Dependency Based Build (DBB), Wazi Deploy, zconfig, and the z/OS Connect CLI to automate every stage — from source compilation through to live API endpoints on IBM Z.

1. Overview

The Bank of Z application spans multiple z/OS subsystems — CICS, IMS, and Db2 — alongside Java services and z/OS Connect APIs. To manage this complexity, the project adopts a modern, automation-first build and deployment model:

  • IBM DBB (Dependency Based Build) drives compilation, understanding source-level dependencies to build only what is necessary.
  • Wazi Deploy packages and deploys the build archive to the appropriate runtime environments.
  • zconfig provisions the CICS and IMS runtime infrastructure.
  • z/OS Connect CLI configures and activates the API layer that routes external requests into z/OS transaction processors.

Two build modes are supported — full and incremental — allowing teams to choose between a complete environment setup or a fast, change-driven redeploy during active development.

3. Build Pipeline

3.1 Source Assets

The repository contains source artifacts that span all layers of the application stack:

Source Type Description
COBOL, PL/I, Assembler Core transaction and batch application programs
BMS Map Definitions 3270 screen maps for CICS terminal interactions
Db2 Source Definitions DDL for tables and DBRM inputs for plan binding
Java Application Source Java services exposed or consumed by the application
z/OS Connect API Definitions API descriptors that map REST endpoints to z/OS services

3.2 IBM DBB Build Process

IBM DBB performs dependency-aware compilation across all source types. It inspects inter-module dependencies before invoking the compiler so that only the programs impacted by a change are rebuilt in an incremental run.

sequenceDiagram participant Dev as Developer participant DBB as IBM DBB participant ZOS as z/OS Compiler / Binder participant Pkg as Wazi Deploy Packager Dev->>DBB: Trigger build (full or incremental) DBB->>DBB: Scan source for changed files DBB->>DBB: Resolve dependency graph DBB->>ZOS: Compile COBOL / PL/I / ASM programs DBB->>ZOS: Assemble BMS maps DBB->>ZOS: Run Db2 pre-compiler & bind DBB->>ZOS: Build Java JARs DBB->>ZOS: Generate z/OS Connect artifacts ZOS-->>DBB: Load modules, DBRMs, JARs, API artifacts DBB->>Pkg: Hand off all generated artifacts Pkg-->>Dev: Deployment archive ready

The output of the build phase is a comprehensive Wazi Deploy deployment archive that bundles:

  • Load modules — compiled and link-edited COBOL, PL/I, Assembler, and BMS outputs
  • Db2 tables and plans — DDL and bound plans
  • Java archive (JAR) files — packaged Java services
  • z/OS Connect API artifacts — API configuration and descriptor files

4. Full and Incremental Builds

4.1 Full Build

A full build compiles all application components from scratch, packages the complete application, and prepares it for a fresh deployment. Use a full build when:

  • Setting up a new Bank of Z environment for the first time.
  • Infrastructure or environment configuration changes require a complete redeployment.
  • The runtime state needs to be fully reset and reprovisioned via zconfig.

4.2 Incremental Build

An incremental build rebuilds and redeploys only the components affected by source code changes, making it the preferred workflow for day-to-day development activities such as enhancements and defect fixes.

The pipeline-remote.sh script drives incremental builds:

BASH 
# Trigger an incremental build and deploy against an existing environment
./pipeline-remote.sh

The script automatically:

  1. Identifies modified source files since the last successful build.
  2. Resolves the dependency graph to determine all impacted components.
  3. Rebuilds only those components.
  4. Packages the updated artifacts into a new deployment archive.
  5. Deploys the archive to the existing runtime environment.

Note: An incremental build requires an existing Bank of Z environment that has already been deployed successfully. Use a full build and deployment when setting up a new environment or when infrastructure changes require a complete redeployment.

5. CICS Deployment

After the build archive is produced, Wazi Deploy installs the generated artifacts into the CICS runtime environment provisioned by zconfig. The z/OS Connect APIs are then configured to route inbound REST requests to the CICS transaction-processing environment.

graph TD A[Wazi Deploy Archive] --> B[zconfig: Provision CICS Region] B --> C[Deploy Load Modules to CICS] B --> D[Bind Db2 Plans for CICS Programs] C --> E[CICS Transaction Processing] D --> E E --> F[z/OS Connect API Layer] F --> G[External REST Consumers]

The CICS deployment flow proceeds as follows:

  1. zconfig provisions the CICS region with the correct runtime configuration (JCL, system definitions, resource groups).
  2. Wazi Deploy installs load modules into CICS program definitions and applies Db2 plan binds for CICS-resident programs.
  3. The z/OS Connect CLI registers and starts the APIs that front the CICS transactions, making them accessible to external clients over REST/HTTP.

6. IMS Deployment

IMS application artifacts follow a parallel but distinct deployment path. Wazi Deploy targets the IMS region provisioned by zconfig, and the z/OS Connect APIs are configured to route requests to the IMS Transaction Manager ™ environment.

graph TD A[Wazi Deploy Archive] --> B[zconfig: Provision IMS Region] B --> C[Deploy Load Modules to IMS] B --> D[Define IMS Program / Transaction Descriptors] B --> E[Bind Db2 Plans for IMS Programs] C --> F[IMS TM / DB Transaction Processing] D --> F E --> F F --> G[z/OS Connect API Layer] G --> H[External REST Consumers]

The IMS deployment flow proceeds as follows:

  1. zconfig provisions the IMS region, including IMS system definitions and database descriptors.
  2. Wazi Deploy deploys load modules and applies IMS program and transaction definitions.
  3. Db2 plans are bound for IMS-resident programs that access relational data.
  4. The z/OS Connect CLI registers and activates the APIs that expose IMS transactions as REST endpoints.

Tool Role

Each tool operates at a distinct stage of the pipeline: DBB handles all compilation, Wazi Deploy manages artifact distribution, zconfig owns infrastructure provisioning, and the z/OS Connect CLI activates the API gateway layer. Together they form a cohesive, end-to-end automated pipeline for deploying Bank of Z onto IBM Z.
