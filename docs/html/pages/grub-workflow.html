Grub Workflow

The GRUB workflow is a fast, patch-based development cycle that synchronizes local file changes directly to z/OS UNIX System Services (USS) without requiring a Git commit or push. Designed for iterative development in the Bank of Z application, GRUB transfers only the files that have changed, making it significantly faster than full setup workflows. Once files are synced, the environment setup runs automatically on USS, giving developers near-instant feedback on their changes.

1. Overview

The GRUB workflow enables developers to test application changes on z/OS in real time. Instead of committing code to a remote repository and triggering a full pipeline, GRUB creates patch files from local modifications and transfers only those deltas to USS. The remote setup script then runs natively on z/OS, validating prerequisites and installing the Bank of Z application — all without GitHub connectivity or Zowe CLI overhead.

Key highlights of the GRUB workflow:

  • No commits required — changes are picked up directly from the local workspace.
  • Incremental transfers — only modified files are sent to USS, keeping sync times minimal.
  • Automatic environment setup — setup-remote.sh runs immediately after files land on USS.
  • Native USS execution — scripts execute directly on z/OS without additional tooling layers.
  • Offline capable — no GitHub connectivity is needed after the initial clone.

Prerequisite: Before using this workflow, complete the Deploy Using GRUB setup guide to configure your local environment.

2. System Architecture

The GRUB workflow spans two environments: the developer’s local machine and z/OS USS. GRUB acts as the bridge between them, analyzing local changes, packaging them as patches, and transferring only the delta to the remote system.

The diagram above illustrates the end-to-end flow from a developer’s local workspace to the running Bank of Z application on z/OS. GRUB sits at the center of this architecture, decoupling the developer’s Git history from the deployment process. The setup-remote.sh script orchestrates all post-sync tasks natively on USS, ensuring the environment is fully configured and the application is ready as soon as the sync completes.

3. Daily Development Cycle

The typical GRUB-based day follows four repeating steps: edit, sync, wait for automatic setup, and verify. The cycle is intentionally lightweight — there is no branching, committing, or pushing involved.

sequenceDiagram participant Dev as Developer (Local) participant GRUB as GRUB Client participant USS as z/OS USS participant Script as setup-remote.sh participant App as Bank of Z Frontend Dev->>GRUB: Modify source files & trigger sync GRUB->>GRUB: Analyze local changes GRUB->>GRUB: Generate patch files GRUB->>USS: Transfer only changed files USS->>Script: Patches applied — script auto-runs Script->>Script: validate-prereqs Script->>Script: environment setup Script->>Script: install-bank-of-z Script-->>USS: Setup complete USS-->>App: Application deployed App-->>Dev: Verify at http://:9080/bank-frontend-vanilla

This sequence shows that the developer’s only active steps are modifying files and triggering the GRUB sync. Everything from patch application through application deployment is fully automated on the z/OS side.

3.1 Step 1 — Make Changes

Modify application source code in your local workspace. No Git commit is required. Common file types included in a typical change set:

  • COBOL programs and copybooks — core business logic
  • BMS maps — CICS screen definitions
  • z/OS Connect API assets — REST API descriptors and configuration
  • Configuration files — environment and deployment settings

3.2 Step 2 — Trigger a GRUB Sync

Trigger a GRUB sync from your local machine. GRUB will:

  1. Analyze the local workspace for modified files.
  2. Create patch files representing only the changes.
  3. Transfer the patch files to the Bank-of-Z directory on z/OS USS.

Refer to your GRUB installation documentation for the specific command or UI action used to initiate the sync.

3.3 Step 3 — Automatic Execution on USS

Once files are transferred, the following process runs entirely on z/OS USS without any further developer action:

CODE 
Local Machine                    z/OS USS
─────────────                    ────────
GRUB analyzes changes
Creates patch files
Transfers changed files ────────→ Patches applied to USS
                                  setup-remote.sh runs natively
                                  ├─ validate-prereqs
                                  ├─ environment
                                  └─ install-bank-of-z

GRUB detects that it is running from within the Bank-of-Z repository and uses the synced files directly — no re-cloning occurs. This is what makes subsequent syncs significantly faster than a full initial setup.

3.4 Step 4 — Validate Changes

Open the Bank of Z frontend in a browser to confirm your changes are live:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

Replace <your-zos-host> with the hostname or IP address of your z/OS system.

4. Stage Detection Mechanism

A critical feature of the GRUB workflow is how setup-remote.sh determines whether it is running inside a GRUB-synced repository or a freshly cloned environment. This distinction controls whether the script re-clones from GitHub or uses the files already present on USS.

When setup-remote.sh runs on USS after a GRUB sync, it checks Git metadata to identify its execution context:

BASH 
if git rev-parse --git-dir > /dev/null 2>&1; then
    local repo_name=$(basename "$(git rev-parse --show-toplevel)")
    if [[ "$repo_name" == "Bank-of-Z" ]]; then
        # GRUB workflow — use current repository location
        BANK_DIR="$(git rev-parse --show-toplevel)"
    fi
fi

How this works:

  • git rev-parse --git-dir checks whether the current directory is inside a Git repository.
  • git rev-parse --show-toplevel retrieves the absolute path to the repository root.
  • basename extracts the repository folder name and compares it to "Bank-of-Z".
  • If the name matches, BANK_DIR is set to the current repository location and no clone is performed.

This means your uncommitted local changes are used as-is — the exact state of your local workspace is what gets deployed and tested on z/OS.

graph TD A[setup-remote.sh starts] --> B{Inside a Git repo?} B -- No --> C[Clone from GitHub] B -- Yes --> D{Repo name == Bank-of-Z?} D -- No --> C D -- Yes --> E[Set BANK_DIR to current repo root] E --> F[Use synced files — skip clone] C --> F F --> G[Continue: validate, setup, install]

This detection logic ensures the GRUB workflow is non-destructive and always works with the most recent synced state, regardless of Git commit history.

5. Why Use GRUB

The GRUB workflow is purpose-built for speed and simplicity during active development. The table below summarizes the key benefits:

Feature Benefit
No commits required Test changes immediately without a Git commit or push
Patch-based sync Only changed files are transferred — fast incremental updates
Automatic setup Environment is ready as soon as the sync completes
Native execution Runs directly on USS — no Zowe CLI overhead
Works offline No GitHub connectivity needed after initial clone

5.1 GRUB vs. Zowe CLI Workflow

While both workflows deploy the Bank of Z application to z/OS, they serve different purposes:

Criterion GRUB Workflow Zowe CLI Workflow
Git commit required ❌ No ✅ Yes
Transfer method Patch-based (delta only) Branch-based (full clone)
Speed (iterative) ⚡ Faster 🐢 Slower
Git traceability Limited Full history
GitHub connectivity Not required after setup Required
Best for Rapid local iteration CI/CD and team collaboration
