GRUB Workflow

1. Overview

The GRUB workflow synchronizes local file changes directly to z/OS USS and automatically runs the setup or pipeline scripts. You don’t need to commit or push to a remote repository. GRUB transfers only the changed files, so it is the fastest option for iterative development of the Bank of Z application.

This page covers the day-to-day development cycle with GRUB:

  • Making local changes
  • Triggering a sync
  • What runs automatically on z/OS USS
  • How the setup script detects that it is running inside the Bank-of-Z repository
  • Why you might choose GRUB over other workflows

Before using this workflow, complete the Deploy Using GRUB installation guide to set up your environment.

2. System Architecture

The GRUB workflow has two sides: your local machine, and z/OS USS (Unix System Services). GRUB runs on the local side. It detects changes and builds patches. On the USS side, the patches are applied to the Bank-of-Z repository, and setup-remote.sh runs natively.

2.1 Components

Component Location Role
Local workspace Local machine Holds the application source you edit (COBOL, BMS, z/OS Connect assets, configuration)
GRUB Local machine Analyzes changes, creates patch files, and transfers only modified files
Bank-of-Z repository z/OS USS Target repository where patches are applied
setup-remote.sh z/OS USS Orchestrates setup and runs natively on USS
validate-prereqs z/OS USS Setup stage that validates prerequisites
environment z/OS USS Setup stage that prepares the environment
install-bank-of-z z/OS USS Setup stage that installs the application
Bank of Z frontend z/OS (port 9080) Where you validate your changes

The architecture has no remote Git hop. GRUB moves changes straight from the workstation to USS, which keeps the loop short.

3. Daily Development Cycle

The daily cycle has four steps: make changes, trigger a sync, let the automation run, and validate.

3.1 Make Changes

Modify application source code in your local workspace. No commit is required. Common changes include:

  • COBOL programs and copybooks
  • BMS maps
  • z/OS Connect API assets
  • Configuration files

3.2 Trigger a GRUB Sync

Trigger a GRUB sync from your local machine. GRUB analyzes your local changes, creates patch files, and transfers only the modified files to USS.

Refer to your GRUB documentation for the specific command or UI action for your installation.

3.3 What Runs Automatically

After the transfer, the patches are applied on USS and setup-remote.sh runs natively. It runs three stages: validate-prereqs, environment, and install-bank-of-z.

CODE 
Local Machine                    z/OS USS
─────────────                    ────────
GRUB analyzes changes
Creates patch files
Transfers changed files ────────→ Patches applied to USS
                                  setup-remote.sh runs natively
                                  ├─ validate-prereqs
                                  ├─ environment
                                  └─ install-bank-of-z

GRUB detects that it is running from within the Bank-of-Z repository and uses the synced files directly. No re-cloning occurs. This is why later syncs are much faster than a full setup.

3.4 Validate Changes

Open the Bank of Z frontend to verify that your changes are live:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

4. How Stage Detection Works

When setup-remote.sh runs on USS after a GRUB sync, it checks whether it is executing from within the Bank-of-Z repository. If it is, it uses that location directly:

BASH 
if git rev-parse --git-dir > /dev/null 2>&1; then
    local repo_name=$(basename "$(git rev-parse --show-toplevel)")
    if [[ "$repo_name" == "Bank-of-Z" ]]; then
        # GRUB workflow — use current repository location
        BANK_DIR="$(git rev-parse --show-toplevel)"
    fi
fi

Your uncommitted local changes are used as-is, and no clone from GitHub is attempted.

The diagram’s “No” branches show the fallback path. The source code doesn’t spell out that path, so the diagram only labels it as the standard setup path.

5. Why Use GRUB

Feature Benefit
No commits required Test changes immediately without a Git commit or push
Patch-based sync Only changed files are transferred, which gives fast incremental updates
Automatic setup The environment is ready as soon as the sync completes
Native execution Runs directly on USS, with no Zowe CLI overhead
Works offline No GitHub connectivity is needed after the initial clone
