Key Capabilities

Bank of Z is a full-featured reference application that demonstrates modern IBM Z development practices combined with real-world banking functionality. It serves as a showcase for how enterprise banking workloads can be built, integrated, and modernized on the IBM Z platform using industry-standard tooling and hybrid transaction architectures.

1. Overview

Bank of Z brings together core banking operations, enterprise middleware integration, and a modern development workflow — all running on IBM Z. The application is deliberately designed to illustrate both the depth of the IBM Z ecosystem and how teams can adopt contemporary software engineering practices (Git, CI/CD, VS Code) without abandoning the reliability and performance that IBM Z delivers.

Key highlights:

  • Banking domain coverage — accounts, customers, deposits, withdrawals, transfers, and transaction history
  • Hybrid transaction processing — requests are routed dynamically to either CICS or IMS Transaction Manager (IMS TM) implementations
  • Enterprise middleware stack — Db2 for z/OS, IMS DB, IBM MQ, and z/OS Connect work together as an integrated data and messaging tier
  • Modern DevOps toolchain — Dependency Based Build (DBB), zBuilder, Bob, Git, and VS Code bring z/OS development into alignment with mainstream software engineering

2. System Architecture

Bank of Z follows a layered architecture in which the user interface delegates work to a transaction routing layer, which in turn dispatches requests to either CICS or IMS TM. Both paths share access to the same data and messaging backends.

Both CICS and IMS TM have visibility into the shared middleware tier — Db2, IMS DB, and IBM MQ — ensuring that neither path is a second-class citizen in terms of data access.

3. Banking Operations

Bank of Z supports the full lifecycle of common retail banking activities. These operations serve as the functional test bed for the underlying IBM Z middleware and tooling integrations.

3.1 Account Management

Create, retrieve, update, and close bank accounts. Account data is persisted in Db2 for z/OS (relational) or IMS DB (hierarchical) depending on the active transaction path.

3.2 Customer Management

Manage customer profiles including personal details and account associations. Customer records are maintained consistently across both data tiers.

3.3 Deposits and Withdrawals

Process credit and debit transactions against customer accounts, with appropriate balance validation and record-keeping.

3.4 Funds Transfers

Move funds between accounts, demonstrating multi-step transactional integrity across the data tier.

3.5 Transaction History Processing

Retrieve and process historical transaction records, demonstrating how IMS DB hierarchical data structures and Db2 relational queries are used in combination to satisfy reporting and audit use cases.

4. Hybrid Transaction Processing

One of the most architecturally distinctive features of Bank of Z is its hybrid transaction processing model. Rather than committing exclusively to one subsystem, the application can route identical banking operations to either CICS or IMS TM.

4.1 CICS Path

The CICS implementation handles requests through standard CICS transaction definitions. CICS regions support connections to both Db2 for z/OS and IBM MQ, allowing COBOL programs to issue embedded SQL and MQI calls within the same unit of work.

COBOL 
* Example: CICS COBOL program issuing an SQL update for a deposit
EXEC SQL
    UPDATE ACCOUNT
    SET    BALANCE = BALANCE + :WS-AMOUNT
    WHERE  ACCOUNT-ID = :WS-ACCOUNT-ID
END-EXEC.

IF SQLCODE NOT = 0
    EXEC CICS ABEND ABCODE('SQLE') END-EXEC
END-IF.

4.2 IMS TM Path

The IMS TM implementation routes requests to IMS message processing programs (MPPs). These programs use DL/I calls to access IMS DB hierarchical data, and can issue commands to IMS TM using the CMD and GCMD DL/I call pair for automated operator-style control.

COBOL 
* Example: IMS DL/I GU call to retrieve a customer segment
CALL 'CBLTDLI' USING DLI-GU
                     PCB-MASK
                     IO-AREA
                     SSA-CUSTOMER.
IF PCB-STATUS-CODE = SPACES
    CONTINUE  *> Successful retrieval
ELSE
    PERFORM 9000-HANDLE-DLI-ERROR
END-IF.

4.3 Routing Logic

The user interface layer — exposed via z/OS Connect — determines which subsystem handles a given request. This allows the two implementations to be exercised and compared while presenting a single, consistent API surface to external consumers.

flowchart LR A[Incoming API Request] --> B{Routing Decision} B -- CICS --> C[CICS COBOL Program] B -- IMS TM --> D[IMS MPP COBOL Program] C --> E[(Db2 for z/OS)] C --> F[(IBM MQ)] D --> G[(IMS DB)] D --> E D --> F

5. Enterprise Integration

Bank of Z integrates across the core pillars of the IBM Z middleware stack. Each technology plays a specific role in the overall application architecture.

5.1 z/OS Connect

z/OS Connect exposes the banking application’s back-end logic as RESTful APIs, enabling modern web and mobile clients to interact with CICS and IMS TM programs without any knowledge of the underlying transaction processing subsystems.

5.2 CICS

CICS provides the primary online transaction processing (OLTP) engine for one of the two banking paths. CICS regions manage connections to Db2 for z/OS and IBM MQ, and host the COBOL application programs that implement the banking business logic.

5.3 IMS Transaction Manager (IMS TM)

IMS TM provides the alternative OLTP path. IMS message processing programs use DL/I APIs to read from and write to IMS DB, and can interoperate with Db2 and IBM MQ within the same logical transaction.

5.4 Db2 for z/OS

Db2 serves as the relational database backend for both the CICS and IMS TM paths. Embedded SQL in COBOL programs handles account and customer data access. Db2 stored procedures can also be called from IMS application programs using the ODBA (Open Database Access) interface, bridging the relational and hierarchical data tiers.

5.5 IMS DB

IMS DB provides hierarchical, high-performance data storage for the IMS TM path. DL/I calls (GU, GN, ISRT, DLET, REPL) are used by IMS application programs to navigate segment hierarchies for customer and account records.

5.6 IBM MQ

IBM MQ provides reliable, asynchronous messaging across both transaction paths. The IBM MQ queue manager on z/OS manages connections from CICS, IMS, and Batch environments through dedicated adapters, and participates in coordinated two-phase commit via z/OS Resource Recovery Services (RRS). This ensures that message delivery is consistent with database updates within the same unit of work.

6. Modern Development Workflows

Bank of Z is not only a functional banking application — it is also a reference implementation for how IBM Z development teams can adopt modern software engineering practices.

6.1 Dependency Based Build (DBB)

IBM Dependency Based Build (DBB) provides intelligent, incremental build support for z/OS source assets. DBB analyses inter-program dependencies and determines the minimal set of programs that need to be recompiled and link-edited after a source change, significantly reducing build times.

6.2 zBuilder and Bob Integration

zBuilder and Bob are build framework tools that integrate with DBB to provide a structured, scriptable build pipeline for z/OS projects. Together they enable repeatable, automated builds triggered from standard CI/CD orchestration platforms.

6.3 Automated Build and Deployment Pipelines

Bank of Z demonstrates end-to-end pipeline automation, from code commit through to deployment on z/OS. Build, test, package, and deploy stages are orchestrated without manual operator intervention.

6.4 Git-Based Source Management

All application source — COBOL programs, JCL, BMS maps, copybooks, and configuration — is managed in a Git repository. This brings standard branching, merging, code review, and history practices to z/OS development.

6.5 VS Code Development Workflows

Developers can write, browse, and debug Bank of Z source code using Visual Studio Code with IBM Z Open Editor and Zowe Explorer extensions, providing a familiar IDE experience connected directly to z/OS.

6.6 GRUB Development Workflows

Bank of Z also supports GRUB-based development workflows, providing an alternative toolchain path for teams that prefer or require it within their z/OS development environment.
