Configuration Reference

This page is the reference for the Bank of Z configuration settings. It covers the current .setup/config/config.yaml model, with its global section and variable expansion, and the legacy configuration guide kept as a backup.

1. Overview

Bank of Z uses a single YAML file, .setup/config/config.yaml, to define the environment-specific settings used during setup, build, and deployment. The setup scripts read this file, resolve variables, validate the result, and then use the values to create datasets, provision middleware, build the application, and deploy it.

1.1 Configuration File Capabilities

The configuration file supports:

  • Hierarchical configuration using YAML sections
  • Variable expansion using {{section.key}} (current model) or ${section.key} (legacy model) syntax
  • Environment variable references using ${ENV_VAR} syntax
  • Comments using the # character

1.2 Current Model and Legacy Backup

Aspect Current model Legacy backup (docs/backup/CONFIGURATION.md)
Primary structure A global section with flat, prefixed keys (for example sandbox_root, app_base_name) Separate sections (sandbox, app, dbb, zbuilder, …)
Cross-reference syntax {{ global.key }} ${section.key}
Application version app_version, app_release, app_modification app.zos_version (for example V0R1M0)
short_name limit Maximum 3 characters Maximum 4 characters
Scope Tools, z/OS system, GUI, frontend, CICS, IMS, DB2 Sandbox, application identity, repositories, DBB, zBuilder, optional tooling

Where the two models differ, treat the current model as authoritative and the legacy section as a historical reference. Both describe the same file location and the same validation intent.

2. System Architecture

2.1 Component Overview

The configuration file is the single source of truth for the setup scripts, the build and deploy tooling, and the middleware it provisions.

graph TD CFG[".setup/config/config.yaml"] --> RES[Variable Resolver] ENV[Environment Variables] --> RES RES --> VAL[Validation] VAL --> SETUP[Setup Scripts] SETUP --> REPO[Repository Cloning] SETUP --> ZB[zBuilder Deployment] SETUP --> MW[Middleware Provisioning] MW --> DB2[(Db2 Tables)] MW --> CICS[CICS Region via zconfig] MW --> ZOSC[z/OS Connect Server] SETUP --> BUILD[DBB Build] BUILD --> DEPLOY[Wazi Deploy] DEPLOY --> CICS DEPLOY --> ZOSC

The resolver merges values from the YAML file with environment variables. After validation, the setup scripts consume the resulting values. Later pipeline stages (DBB build and Wazi Deploy) use the same values.

2.2 Configuration Sections and Their Relationships

graph LR G[global] --> SB[Sandbox] G --> APP[Application] G --> TOOLS[Tools] G --> ZOS[z/OS System] G --> GUI[GUI / z/OS Connect] G --> FE[Frontend] G --> MWS[CICS / IMS / DB2] SB -->|sandbox_root| TOOLS APP -->|app_base_name| APP ZOS -->|zos_admin_user| GUI ZOS -->|zos_admin_user| FE ZOS -->|zos_current_user| MWS MWS -->|db2_ssid| MWS

Some values are derived from others:

  • app_hlq is derived from app_base_name.
  • Tool paths are derived from sandbox_root.
  • The task users for z/OS Connect and the frontend are derived from zos_admin_user.
  • db2_runlib is derived from db2_ssid.
  • db2_sqlid is derived from zos_current_user.

2.3 Configuration Processing Sequence

sequenceDiagram participant User participant Script as setup-common.sh participant Config as config.yaml participant Env as Environment participant Validator User->>Script: Run validate-prereqs / environment / install-bank-of-z Script->>Config: Read settings Script->>Env: Resolve ${ENV_VAR} references Script->>Script: Expand section references Script->>Validator: Check required keys, paths, limits Validator-->>Script: Pass / fail Script-->>User: Continue with stages or report error

3. Configuration File Syntax

3.1 Variable Expansion

Configuration values can reference other configuration entries. Variables are resolved during setup processing, and resolution is recursive: a variable can reference another variable.

YAML 
sandbox:
  path: /usr/local/sandboxes/bank-of-z

dbb:
  dbb_build: ${sandbox.path}/Bank-of-Z/.setup/build

In the current global model, cross-references use double braces:

Setting Value
app_hlq {{ global.app_base_name }}
zconfig_home {{ global.sandbox_root }}/tools/zconfig
db2_runlib {{ global.db2_ssid }}.RUNLIB.LOAD

3.2 Environment Variables

Environment variables can also be referenced. Use them for sensitive information such as credentials.

YAML 
cics:
  user: ${CICS_USER}
  password: ${CICS_PASSWORD}

The current model uses the same mechanism for the current z/OS user:

Variable Default value
zos_current_user ${ZOS_CURRENT_USER}

Note: The environment variable must be set before you run setup.

6. Legacy Configuration Backup

The backup guide (docs/backup/CONFIGURATION.md) documents the earlier section-per-tool layout. It is retained for reference and remains useful for the optional tool sections below.

6.1 Legacy Required Settings

6.1.1 Sandbox

YAML 
sandbox:
  path: /usr/local/sandboxes/bank-of-z

This is the root directory on z/OS USS where all components are installed.

  • Must be an absolute path
  • The user must have write permissions
  • The parent directory must exist
  • A dedicated sandbox directory is recommended
YAML 
# Development environment
sandbox:
  path: /usr/local/sandboxes/dev/bank-of-z

# Test environment
sandbox:
  path: /usr/local/sandboxes/test/bank-of-z

# Personal sandbox
sandbox:
  path: /u/userid/sandboxes/bank-of-z

6.1.2 Application Identity

YAML 
app:
  base_name: BANKZ
  short_name: BOZ
  zos_version: V0R1M0
Key Rules Usage
base_name Dataset high-level qualifier. Maximum 8 characters. Alphanumeric only. BANKZ.V0R1M0.LOAD, BANKZ.V0R1M0.COBCOPY
short_name Short application identifier. Maximum 4 characters (legacy limit). CICS region names and transaction IDs, for example CICSBOZ, BOZ1
zos_version Format V#R#M# (Version, Release, Modification). Dataset names, for example BANKZ.V0R1M0.LOAD
YAML 
# Development version
app:
  base_name: BANKZD
  short_name: BOZD
  zos_version: V0R1M0

# Production version
app:
  base_name: BANKZP
  short_name: BOZP
  zos_version: V1R0M0

6.1.3 Repositories

YAML 
repositories:
  - name: dbb
    url: https://github.com/IBM/dbb.git
    target_dir: dbb

These are the Git repositories to clone during setup.

  • name: Repository identifier
  • url: Git clone URL (HTTPS or SSH)
  • target_dir: Directory name in the workspace
YAML 
# Multiple repositories
repositories:
  - name: dbb
    url: https://github.com/IBM/dbb.git
    target_dir: dbb
  - name: custom-tools
    url: https://github.com/company/tools.git
    target_dir: tools

6.1.4 DBB

YAML 
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/java21/current_64
  • dbb_home: DBB installation directory on z/OS. It must contain the DBB libraries and tools. Verify with ls $DBB_HOME/lib.
  • java_home: Java runtime for DBB. The minimum version is Java 8 and Java 11 or higher is recommended. Verify with $JAVA_HOME/bin/java -version.
YAML 
# Java 8
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/J8.0_64

# Java 11
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/J11.0_64

# Java 21
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/java21/current_64

6.1.5 zBuilder

YAML 
zbuilder:
  source_dir: build
  target_dir: ${sandbox.path}/zBuilder
  java_home: /usr/lpp/java/java21/current_64
  • source_dir: Local directory containing the zBuilder framework, relative to .setup/. It contains datasets.yaml, language configurations, and so on.
  • target_dir: USS directory where zBuilder is deployed. It supports variable expansion and is created if it doesn’t exist.
  • java_home: Java runtime for zBuilder. The minimum version is Java 17. It can reference the same Java as DBB.

7. Validation Rules

The setup process validates configuration values before it runs. Correcting configuration issues first helps prevent build and deployment failures.

7.1 Validation Checks

  • Required configuration settings are present
  • Referenced variables can be resolved
  • Paths use valid absolute path formats
  • Application naming limits are respected
  • Required tool locations are defined

The legacy guide describes these checks in more detail:

  1. Required fields present: sandbox.path, app.base_name, app.short_name, dbb.dbb_home, dbb.java_home
  2. Path formats: absolute paths start with /, with no trailing slashes
  3. Variable resolution: all ${section.key} references resolve, with no circular references
  4. Character limits: app.base_name ≤ 8 characters, and app.short_name ≤ 4 characters (legacy; 3 in the current model)

7.2 Validation Flow

graph TD A[Load config.yaml] --> B{Required keys present?} B -- No --> X[Fail: missing setting] B -- Yes --> C{All references resolve?} C -- No --> Y[Fail: unresolved variable] C -- Yes --> D{Paths absolute?} D -- No --> Z[Fail: invalid path format] D -- Yes --> E{Naming limits OK?} E -- No --> W[Fail: name too long] E -- Yes --> F[Proceed with setup stages]

7.3 Prerequisite Validation Command

You can validate the installed tooling before you run the setup stages:

BASH 
.setup/setup-common.sh validate-prereqs

This check confirms the DBB, ZOAU, zconfig, and Wazi Deploy installations. The minimum versions reported by the validation are:

Tool Minimum required version
DBB 3.0.4.1
ZOAU 1.4.1.0
Wazi Deploy 3.0.7.1

8. Using the Configuration in Setup

8.1 Editing the Configuration

Edit the file for your environment before you run setup:

BASH 
vi .setup/config/config.yaml

A typical legacy-style excerpt looks like this:

YAML 
# Workspace location on z/OS USS
sandbox:
  path: /usr/local/sandboxes/bank-of-z

# Application identity
app:
  base_name: BANKZ    # Dataset prefix (max 8 chars)
  short_name: BOZ     # Short identifier
  zos_version: V0R1M0 # Version for dataset naming

# DBB configuration
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/java21/current_64

8.2 Setup Stages That Consume the Configuration

sequenceDiagram participant U as User participant S as setup-common.sh participant C as config.yaml participant M as Middleware U->>S: validate-prereqs S->>C: Read tool locations S-->>U: Version checks (DBB, ZOAU, zconfig, Wazi Deploy) U->>S: environment S->>C: Read repositories, sandbox, app, db2, cics S->>S: Clone DBB, copy zBuilder S->>M: Create Db2 tables, CICS region, z/OS Connect server U->>S: install-bank-of-z S->>C: Read build and deploy settings S->>S: DBB build, then Wazi Deploy S->>M: Populate Db2 database

The commands, in order:

BASH 
.setup/setup-common.sh validate-prereqs
.setup/setup-common.sh environment
.setup/setup-common.sh install-bank-of-z

The configured sandbox path determines where components are created:

├── zBuilder/                     # Build framework
│   ├── languages/

│   └── ...
└── Bank-of-Z/                    # Application source
    ├── src/
    ├── .setup/                   # Setup scripts
    └── dbb-app.yaml              # DBB configuration

9. Troubleshooting Configuration Problems

9.1 Configuration File Not Found

Cause: config.yaml is missing or in the wrong location.

BASH 
# Verify file exists
ls -la .setup/config/config.yaml

# Check you're in the right directory
pwd

9.2 Variable Reference Cannot Be Resolved

Cause: The referenced section or key doesn’t exist.

YAML 
# Bad: References non-existent section
dbb:
  build_dir: ${workspace.path}/build  # 'workspace' doesn't exist

# Good: Use correct section name
dbb:
  build_dir: ${sandbox.path}/build

9.3 Invalid Path Format

Cause: The path is not absolute.

YAML 
# Bad: Relative path
sandbox:
  path: sandboxes/bank-of-z

# Good: Absolute path
sandbox:
  path: /usr/local/sandboxes/bank-of-z

6. Variable Expansion

Configuration values can reference other configuration entries.

YAML 
sandbox:
  path: /usr/local/sandboxes/bank-of-z

dbb:
  dbb_build: ${sandbox.path}/Bank-of-Z/.setup/build

Variables are resolved during setup processing. The legacy implementation resolves references recursively, so a variable can reference another variable.

Environment variables can also be referenced:

YAML 
cics:
  user: ${CICS_USER}
  password: ${CICS_PASSWORD}

Note: Using environment variables is recommended for sensitive information such as credentials. The environment variable must be set before you run setup.

7. Validation Rules

The setup process validates configuration values before it runs. Validation includes:

  • Required configuration settings are present
  • Referenced variables can be resolved
  • Paths use valid absolute path formats
  • Application naming limits are respected
  • Required tool locations are defined
flowchart TD A[Load config.yaml] --> B{Required settings present?} B -- No --> X[Fail setup] B -- Yes --> C{Variables resolvable?} C -- No --> X C -- Yes --> D{Absolute path formats?} D -- No --> X D -- Yes --> E{Naming limits respected?} E -- No --> X E -- Yes --> F{Tool locations defined?} F -- No --> X F -- Yes --> G[Proceed with setup]

Note: Correcting configuration issues before you run setup helps prevent build and deployment failures.

Field Rules Usage
base_name Dataset high-level qualifier; maximum 8 characters; alphanumeric only Dataset names such as BANKZ.V0R1M0.LOAD and BANKZ.V0R1M0.COBCOPY
short_name Short application identifier; maximum 4 characters CICS region names and transaction IDs, such as CICSBOZ or BOZ1
zos_version Format V#R#M# (Version, Release, Modification) Dataset names such as BANKZ.V0R1M0.LOAD

8.1.4 DBB Configuration

YAML 
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/java21/current_64
  • dbb_home: DBB installation directory on z/OS. It must contain the DBB libraries and tools. Verify with ls $DBB_HOME/lib.
  • java_home: Java runtime for DBB. The minimum version is Java 8 and Java 11 or higher is recommended. Verify with $JAVA_HOME/bin/java -version.
YAML 
# Java 8
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/J8.0_64

# Java 11
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/J11.0_64

# Java 21
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/java21/current_64

zbuilder:
