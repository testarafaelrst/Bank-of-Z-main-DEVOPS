Configuration Reference

Bank of Z centralizes all environment-specific settings in a single YAML configuration file located at .setup/config/config.yaml. This file governs every aspect of the application lifecycle — from sandbox path definitions and application identity to middleware connections and deployment tooling. Understanding and correctly configuring this file is a prerequisite for a successful Bank of Z setup, build, and deployment.

1. Overview

The Bank of Z configuration system is built around a single, human-readable YAML file. It supports hierarchical organization, allowing settings to be logically grouped by concern (sandbox, application, tools, middleware, etc.). The system also supports dynamic value resolution through variable expansion, enabling values defined in one section to be referenced in another — reducing duplication and configuration drift across environments.

Key capabilities of the configuration system:

  • Hierarchical configuration using YAML sections for logical grouping
  • Variable expansion using {{ section.key }} syntax to reference other config values
  • Environment variable references using ${ENV_VAR} syntax for runtime-resolved values (recommended for secrets)
  • Comment support using the # character for inline documentation
  • Validation of required fields, path formats, naming limits, and variable resolution before setup runs

The configuration file is the single source of truth for all Bank of Z environment settings. Changes to this file take effect on the next setup or deployment run.

2. System Architecture

The diagram below illustrates how the config.yaml file relates to the major components of the Bank of Z system, and how configuration flows from a single source into each subsystem.

graph TD CFG[".setup/config/config.yaml"] CFG --> SBX["Sandbox\n/usr/local/sandboxes/..."] CFG --> APP["Application Identity\nBANKZ / BOZ"] CFG --> TOOLS["Build & Dev Tools\nDBB · Gradle · Java · Python"] CFG --> ZOS["z/OS System\nRACF · PROCLIB · TCP/IP"] CFG --> MW["Middleware"] CFG --> DEPLOY["Deployment Tools\nWazi Deploy · ZCodeScan"] MW --> CICS["CICS\nCICSTSxx"] MW --> IMS["IMS\nIMSV15"] MW --> DB2["DB2\nDB2V13"] MW --> ZCONN["z/OS Connect\nPort 9080/9444"] MW --> FE["Frontend Liberty\nPort 9081/9445"] TOOLS --> DBB["IBM DBB"] TOOLS --> GRADLE["Gradle 9.5.1"] TOOLS --> JAVA["Java 21 (64-bit)"] TOOLS --> PY["Python 3.14"] TOOLS --> ZOAU["ZOAU"]

The configuration file sits at the center of the system. Every major component — middleware, build tooling, deployment automation, and the z/OS runtime — reads its settings from this single file during setup and build processing.

3. Configuration File Structure

The configuration file is organized into named sections. Each section groups related settings, and values within one section may reference values from another using variable expansion syntax.

graph LR ROOT["config.yaml"] ROOT --> G["global"] ROOT --> SBX["sandbox"] ROOT --> APP["app"] ROOT --> DBB["dbb"] ROOT --> REPO["repositories"] ROOT --> ZB["zbuilder"] ROOT --> ZC["zconfig"] ROOT --> ZCS["zcodescan"] ROOT --> WD["wazideploy"] ROOT --> TAZ["taz"] ROOT --> CICS["cics"]

The global section is the primary section; most other sections either inherit from it or cross-reference its values using the {{ global.key }} expansion syntax.

4. Required Settings

4.1 Sandbox

The sandbox section defines the root directory on z/OS UNIX System Services (USS) where all Bank of Z components are installed. This path must be an absolute USS path, and the user running setup must have write permissions to it.

Variable Default Value Description
sandbox_root /usr/local/sandboxes Root directory of the sandbox

Examples:

YAML 
# Development environment
sandbox:
  path: /usr/local/sandboxes/dev/bank-of-z

# Test environment
sandbox:
  path: /usr/local/sandboxes/test/bank-of-z

# Personal sandbox
sandbox:
  path: /u/userid/sandboxes/bank-of-z

4.2 Application Identity

The app section defines the naming conventions used for datasets, CICS resources, and deployment artifacts across the entire application lifecycle.

Variable Default Value Description
app_base_name BANKZ Application base name (dataset HLQ, max 8 chars)
app_hlq {{ global.app_base_name }} Application high-level qualifier
app_short_name BOZ Application short name (max 3 characters)
app_version 0 Application version
app_release 1 Application release
app_modification 0 Application modification level
  • app_base_name — Used as the dataset HLQ, e.g., BANKZ.V0R1M0.LOAD. Maximum 8 alphanumeric characters.
  • app_short_name — Used in CICS region names and transaction IDs, e.g., CICSBOZ, BOZ1. Maximum 3–4 characters.
  • app_version/release/modification — Combined to form the version string V#R#M# used in dataset naming.

Examples:

YAML 
# Development version
app:
  base_name: BANKZD
  short_name: BOZD
  zos_version: V0R1M0

# Production version
app:
  base_name: BANKZP
  short_name: BOZP
  zos_version: V1R0M0

python_home /usr/lpp/IBM/cyp/v3r14/pyz Python installation path
zoau_home /usr/lpp/IBM/zoau ZOAU installation path
zconfig_home {{ global.sandbox_root }}/tools/zconfig zconfig installation path
zcb_home {{ global.sandbox_root }}/tools/zrb/cics-resource-builder-1.0.6 CICS Resource Builder path
dbb_home {{ global.sandbox_root }}/tools/dbb DBB installation path
gradle_home {{ global.sandbox_root }}/tools/gradle-9.5.1 Gradle installation path
zcodescan_home /global/opt/pyenv/akf Code scan tool installation path
wazideploy_home /global/opt/pyenv/gdp Wazi Deploy installation path
zosconnect_home /usr/lpp/IBM/zosconnect z/OS Connect installation path
liberty_home /usr/lpp/liberty_zos/25.0.0.9 Liberty installation path

DBB Configuration Example:

YAML 
# Java 8
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/J8.0_64

# Java 21 (recommended)
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/java21/current_64

6. Optional Section Settings

The following sections are optional but enable additional capabilities. They should be included when the corresponding tooling is in use.

6.1 Repository Configuration

Defines Git repositories that are cloned during setup.

YAML 
repositories:
  - name: dbb
    url: https://github.com/IBM/dbb.git
    target_dir: dbb
  - name: custom-tools
    url: https://github.com/company/tools.git
    target_dir: tools

Fields:

  • name — Repository identifier
  • url — Git clone URL (HTTPS or SSH)
  • target_dir — Directory name in the workspace

6.2 zBuilder Configuration

Defines where zBuilder source and deployment artifacts are located.

YAML 
zbuilder:
  source_dir: build
  target_dir: ${sandbox.path}/zBuilder
  java_home: /usr/lpp/java/java21/current_64
  • source_dir — Local directory (relative to .setup/) containing zBuilder framework files such as datasets.yaml and language configurations.
  • target_dir — USS deployment target; supports variable expansion.
  • java_home — Java runtime for zBuilder (minimum Java 17).

6.3 zconfig Configuration

Defines settings for z/OS configuration tooling.

YAML 
zconfig:
  zconfig_home: /usr/local/sandboxes/tools/zconfig
  zcb_home: /usr/local/sandboxes/tools/zrb/cics-resource-builder-1.0.6
  java_home: /usr/lpp/java/java21/current_64

Required when using CICS Resource Builder or z/OS Config tools.

6.4 ZCodeScan Configuration

Defines settings for static code analysis.

YAML 
zcodescan:
  zcodescan_home: /global/opt/pyenv/akf
  java_home: /usr/lpp/java/java21/current_64
  src_folder: ${sandbox.path}/Bank-of-Z/src/base
  output_folder: ${sandbox.path}/Bank-of-Z/zcodescan
  src_encoding: IBM-1047
  rseapi_user: ${RESAPI_USER}
  rseapi_password: ${RESAPI_PASSWORD}

Required when performing code quality scans. Credentials should always reference environment variables.

6.5 Wazi Deploy Configuration

Defines deployment automation settings.

YAML 
wazideploy:
  wazideploy_home: /global/opt/pyenv/gdp
  deployment_method: ${sandbox.path}/dbb/WaziDeploy/zDeploy/deployment-configuration/deployment-method.yml
  deployment_envfile: ${sandbox.path}/Bank-of-Z/.setup/deploy/Development.yml

Required when using Wazi Deploy for automated deployments.

6.6 TAZ Unit Test Configuration

Defines the automated unit testing framework configuration.

YAML 
taz:
  taz_home: /usr/local/sandboxes/tools/taz-280/test-cli
  test_folder: ${sandbox.path}/Bank-of-Z/tests
  proclib: SYS1.PROCLIB
  library: ${app.base_name}.${app.zos_version}.LOAD

Required when running automated unit tests.

7. Variable Expansion

Variable expansion is the mechanism that allows configuration values to be derived from other values, reducing duplication and making environment-specific changes easier to manage.

7.1 Section References

Use {{ section.key }} (or ${section.key}) to reference another key within the same configuration file:

YAML 
sandbox:
  path: /usr/local/sandboxes/bank-of-z

dbb:
  dbb_build: ${sandbox.path}/Bank-of-Z/.setup/build
  dbb_cwd: ${sandbox.path}/Bank-of-Z/
  • Syntax: ${section.key} or {{ section.key }}
  • Resolution: Recursive — variables may reference other variables
  • Circular references are invalid and will cause a validation error

7.2 Environment Variable References

Use ${ENV_VAR} to reference a system environment variable at runtime:

YAML 
cics:
  user: ${CICS_USER}
  password: ${CICS_PASSWORD}
  cmci_port: 27100
  ipic_port: 27114

Security Note: Using environment variables is strongly recommended for all sensitive values such as passwords, tokens, and user credentials. The environment variable must be set in the shell environment before running setup.

The following diagram shows how variable expansion flows during setup processing:

sequenceDiagram participant CF as config.yaml participant VP as Variable Processor participant ENV as Environment Variables participant SS as Setup Scripts CF->>VP: Load raw YAML VP->>VP: Parse section references ({{ section.key }}) VP->>ENV: Resolve ${ENV_VAR} references ENV-->>VP: Return runtime values VP->>VP: Validate all references resolved VP-->>SS: Deliver fully resolved config SS->>SS: Execute setup / build / deploy

8. Environment-Specific Configurations

Bank of Z supports multiple deployment environments, each with its own configuration values. The recommended approach is to maintain separate config.yaml files per environment, or use environment variable overrides.

8.1 Development Environment

9. Validation Rules

Before any setup step executes, the configuration system validates the entire file. This prevents build and deployment failures caused by misconfiguration.

9.1 Required Fields

The following fields must be present and non-empty:

  • sandbox.path
  • app.base_name
  • app.short_name
  • dbb.dbb_home
  • dbb.java_home

9.2 Path Format Rules

  • All paths must be absolute (begin with /)
  • No trailing slashes
  • Parent directories must exist before setup runs

9.3 Variable Resolution

  • All ${section.key} and {{ section.key }} references must resolve to a defined value
  • No circular references are permitted

9.4 Character Limits

Field Maximum Length
app.base_name 8 characters
app.short_name 3–4 characters

10. Troubleshooting

10.1 “Configuration file not found”

Cause: config.yaml is missing or located in the wrong directory.

Solution:

BASH 
# Verify file exists
ls -la .setup/config/config.yaml

# Confirm you are in the correct working directory
pwd

10.2 “Variable reference cannot be resolved”

Cause: A ${section.key} reference points to a section or key that does not exist.

Solution:

YAML 
# Bad: References a non-existent section
dbb:
  build_dir: ${workspace.path}/build  # 'workspace' section does not exist

# Good: Use the correct section name
dbb:
  build_dir: ${sandbox.path}/build

10.3 “Invalid path format”

Cause: A path value is relative rather than absolute.

Solution:

YAML 
# Bad: Relative path
sandbox:
  path: sandboxes/bank-of-z

# Good: Absolute path
sandbox:
  path: /usr/local/sandboxes/bank-of-z
