Program Internals: CRDTAGY2 Credit Agency Simulator

CRDTAGY2 is a simulated credit agency program that runs asynchronously within a CICS environment. Its role in the Bank of Z application is to assign a randomly generated credit score to a customer record delivered via a CICS channel and container. The program deliberately introduces a random delay of 1 to 3 seconds to emulate the response latency of a real external credit agency, then computes a random credit score between 1 and 999 using the COBOL FUNCTION RANDOM, seeded with the current CICS task number. The scored customer record is written back into the container for the parent program to collect. The intentional timing overlap with the parent’s 3-second timeout window creates a realistic, non-trivial probability that the score will not be returned in time — faithfully simulating the imperfect reliability of third-party credit bureaus.

1. System Architecture

CRDTAGY2 operates as a child task within the CICS Async API model. The parent program launches it asynchronously, places customer data into a named CICS channel/container pair, and then waits (up to 3 seconds) to fetch the result. CRDTAGY2 runs independently, introduces a simulated delay, computes a credit score, and writes the updated record back to the same container.

CRDTAGY2 is intentionally designed so that its delay range (1–3 s) overlaps with the parent program’s fetch timeout (3 s). This creates a roughly 1-in-3 chance that the parent will time out before the score is returned, faithfully simulating the real-world scenario where an external credit bureau does not always respond within the required SLA.

3.2 Step-by-Step Execution Description

3.2.1 Step 1 — Initialisation (Paragraph A010)

The program sets the container name CIPB and channel name CIPCREDCHANN into working-storage fields, then seeds the COBOL pseudo-random number generator by moving EIBTASKN (the CICS task number from the Execute Interface Block) into WS-SEED. Using the task number as a seed ensures that each CICS task invocation produces a different random sequence.

COBOL 
MOVE EIBTASKN TO WS-SEED
COMPUTE WS-DELAY-AMT = ((3 - 1) * FUNCTION RANDOM(WS-SEED)) + 1

3.2.2 Step 2 — Apply Random Delay

The formula maps the [0, 1) output of FUNCTION RANDOM to the range 1–3 seconds and stores the result in WS-DELAY-AMT. The CICS DELAY command then suspends the task for that duration, simulating external agency latency.

COBOL 
EXEC CICS DELAY
    FOR SECONDS(WS-DELAY-AMT)
    RESP(WS-CICS-RESP)
    RESP2(WS-CICS-RESP2)
END-EXEC

3.2.3 Step 3 — DELAY Error Handling

If WS-CICS-RESP is not DFHRESP(NORMAL), the full abend path is triggered: ABNDINFO-REC is populated with diagnostic context (RESP codes, application ID, task number, transaction ID, timestamp), the ABNDPROC handler is called via EXEC CICS LINK, and the task is terminated with EXEC CICS ABEND ABCODE('PLOP').

COBOL 
IF WS-CICS-RESP NOT = DFHRESP(NORMAL)
    INITIALIZE ABNDINFO-REC
    MOVE EIBRESP    TO ABND-RESPCODE
    MOVE EIBRESP2   TO ABND-RESP2CODE
    EXEC CICS ASSIGN APPLID(ABND-APPLID) END-EXEC
    MOVE EIBTASKN   TO ABND-TASKNO-KEY
    MOVE EIBTRNID   TO ABND-TRANID
    PERFORM POPULATE-TIME-DATE
    MOVE 'PLOP'     TO ABND-CODE
    EXEC CICS ASSIGN PROGRAM(ABND-PROGRAM) END-EXEC
    EXEC CICS LINK PROGRAM(WS-ABEND-PGM)
                   COMMAREA(ABNDINFO-REC)
    END-EXEC
    EXEC CICS ABEND ABCODE('PLOP') END-EXEC
END-IF

3.2.4 Step 4 — Retrieve Customer Record from Container

WS-CONTAINER-LEN is set via the LENGTH OF special register, then the customer record is read from container CIPB on channel CIPCREDCHANN into the working-storage structure WS-CONT-IN.

COBOL 
MOVE LENGTH OF WS-CONT-IN TO WS-CONTAINER-LEN

EXEC CICS GET CONTAINER(WS-CONTAINER-NAME)
             CHANNEL(WS-CHANNEL-NAME)
             INTO(WS-CONT-IN)
             FLENGTH(WS-CONTAINER-LEN)
             RESP(WS-CICS-RESP)
             RESP2(WS-CICS-RESP2)
END-EXEC

3.2.5 Step 5 — Generate Random Credit Score

A second call to FUNCTION RANDOM — this time without a seed argument — continues the same pseudo-random sequence already initialised in Step 1. The result is mapped to the range 1–999.

COBOL 
COMPUTE WS-NEW-CREDSCORE =
    ((999 - 1) * FUNCTION RANDOM) + 1

MOVE WS-NEW-CREDSCORE TO CUSTOMER-CREDIT-SCORE OF WS-CONT-IN

3.2.6 Step 6 — Write Updated Record Back to Container

The updated customer record (now carrying the new credit score) is written back to the same container. If this operation existed previously, its contents are overwritten.

COBOL 
MOVE LENGTH OF WS-CONT-IN TO WS-CONTAINER-LEN

EXEC CICS PUT CONTAINER(WS-CONTAINER-NAME)
             FROM(WS-CONT-IN)
             FLENGTH(WS-CONTAINER-LEN)
             CHANNEL(WS-CHANNEL-NAME)
             RESP(WS-CICS-RESP)
             RESP2(WS-CICS-RESP2)
END-EXEC

3.2.7 Step 7 — Normal Termination

GET-ME-OUT-OF-HERE is performed unconditionally, issuing EXEC CICS RETURN to hand control back to CICS. The parent can subsequently FETCH the child task’s channel to obtain the updated container.

COBOL 
GET-ME-OUT-OF-HERE SECTION.
GMOFH010.
    EXEC CICS RETURN END-EXEC.
GMOFH999.
    EXIT.

The primary output is the full customer record with CUSTOMER-CREDIT-SCORE set to a newly generated random value (1–999), written back to container CIPB on channel CIPCREDCHANN via EXEC CICS PUT CONTAINER. This is the only data output consumed by the parent program.

7.1 POPULATE-TIME-DATE Detail

This paragraph is invoked only from the DELAY error path inside A010. It uses two CICS time services to capture a precise diagnostic timestamp:

COBOL 
POPULATE-TIME-DATE SECTION.
PTD010.
    EXEC CICS ASKTIME
        ABSTIME(WS-U-TIME)
    END-EXEC.

    EXEC CICS FORMATTIME
        ABSTIME(WS-U-TIME)
        DDMMYYYY(WS-ORIG-DATE)
        TIME(WS-TIME-NOW)
        DATESEP
    END-EXEC.
PTD999.
    EXIT.

WS-U-TIME (declared PIC S9(15) COMP-3) receives the absolute time in milliseconds since 00:00 on 1 January 1900. EXEC CICS FORMATTIME converts this to a DD/MM/YYYY date in WS-ORIG-DATE and a six-digit HHMMSS time in WS-TIME-NOW, which the caller then uses to populate ABND-DATE and ABND-TIME.

9. Constraints

9.1 Data Validation Constraints

  • CUSTOMER-EYECATCHER — PIC X(4) with level-88 condition CUSTOMER-EYECATCHER-VALUE requiring 'CUST'. Not explicitly checked at runtime but defines the expected sentinel value for any valid customer record.
  • CUSTOMER-STATUS — PIC X(10) with three mutually exclusive level-88 conditions: CUSTOMER-STATUS-ACTIVE ('ACTIVE'), CUSTOMER-STATUS-INACTIVE ('INACTIVE'), and CUSTOMER-STATUS-SUSPENDED ('SUSPENDED').
  • CUSTOMER-CREDIT-SCORE — PIC 999 constrains storage to 0–999. The generation formula ((999 - 1) * FUNCTION RANDOM) + 1 further restricts the output to the range 1–999 inclusive.
  • Fixed-length character fields — Name and address fields (PIC X(50)) impose hard upper limits; content exceeding these lengths is silently truncated by COBOL.
  • ABND-FREEFORM — PIC X(600) limits the free-form diagnostic message to 600 characters; overflow is silently discarded.

9.2 Channel and Container Constraints

  • Fixed channel name — WS-CHANNEL-NAME is hardcoded as 'CIPCREDCHANN ' (16 characters, space-padded). Both GET CONTAINER and PUT CONTAINER must reference exactly this name.
  • Fixed container name — WS-CONTAINER-NAME is hardcoded as 'CIPB ' (16 characters, space-padded). The same container name is used for both the GET and PUT operations.
  • FLENGTH integrity — WS-CONTAINER-LEN (PIC S9(8) COMP) is always computed via LENGTH OF WS-CONT-IN, guaranteeing it matches the exact structural length of the data area and preventing under/overflow.
  • Strict read-before-write ordering — The program unconditionally exits (via GET-ME-OUT-OF-HERE) if GET CONTAINER fails, so PUT CONTAINER is only ever reached after a successful read.

9.3 Sequencing and Timing Constraints

  • Delay must complete before container I/O — EXEC CICS DELAY is issued before any container access. A delay failure triggers EXEC CICS ABEND, preventing any container operations from occurring.
  • PRNG must be seeded before unseed calls — FUNCTION RANDOM(WS-SEED) must be called first to initialise the sequence; the subsequent unseeded call for the credit score continues that sequence.
  • Abend handler link must precede EXEC CICS ABEND — ABNDINFO-REC is fully populated and ABNDPROC is linked before EXEC CICS ABEND is issued, ensuring the diagnostic record is persisted before task termination.

9.4 Resource and Value Range Constraints

  • Delay range: 1–3 s — WS-DELAY-AMT (PIC S9(8) COMP) is computed as ((3 - 1) * FUNCTION RANDOM(WS-SEED)) + 1, yielding values in [1, 3).
  • Credit score range: 1–999 — WS-NEW-CREDSCORE (PIC 999) holds values from ((999 - 1) * FUNCTION RANDOM) + 1, yielding values in [1, 999).
  • Abend code must not start with 'A' — CICS reserves abend codes beginning with 'A' for its own use. The code 'PLOP' complies with this restriction.
  • ABNDPROC must be installed — WS-ABEND-PGM is the literal constant 'ABNDPROC' (PIC X(8)). If this program is not installed in the CICS region, the EXEC CICS LINK itself will fail.

10. Error Handling

10.1 CICS Response Code Checking (RESP/RESP2 Pattern)

Every CICS command in CRDTAGY2 specifies RESP(WS-CICS-RESP) and RESP2(WS-CICS-RESP2). After each command, the primary response is compared to DFHRESP(NORMAL):

COBOL 
IF WS-CICS-RESP NOT = DFHRESP(NORMAL)
    ... error handling ...
END-IF

This pattern is applied consistently to EXEC CICS DELAY, EXEC CICS GET CONTAINER, and EXEC CICS PUT CONTAINER.

10.2 Full Abend Path (DELAY Failure)

The most comprehensive error path is triggered by a DELAY failure. The sequence is:

10.3 Simplified Error Path (GET / PUT CONTAINER Failures)

Container failures use a lighter-weight path — no abend handler is invoked and no EXEC CICS ABEND is issued. Instead:

  • Two DISPLAY statements log the RESP/RESP2 codes and container/channel/length details to the CICS console.
  • PERFORM GET-ME-OUT-OF-HERE issues EXEC CICS RETURN for a clean, controlled task exit.
COBOL 
*  GET CONTAINER failure example
IF WS-CICS-RESP NOT = DFHRESP(NORMAL)
    DISPLAY 'CRDTAGY2 - UNABLE TO GET CONTAINER. RESP='
            WS-CICS-RESP ' RESP2=' WS-CICS-RESP2
    DISPLAY 'CONTAINER=' WS-CONTAINER-NAME
            ' CHANNEL='  WS-CHANNEL-NAME
            ' LENGTH='   WS-CONTAINER-LEN
    PERFORM GET-ME-OUT-OF-HERE
END-IF

10.4 Controlled Task Exit (Normal and Error)

GET-ME-OUT-OF-HERE is the single exit point for all execution paths other than EXEC CICS ABEND:

COBOL 
GET-ME-OUT-OF-HERE SECTION.
GMOFH010.
    EXEC CICS RETURN END-EXEC.
GMOFH999.
    EXIT.

It is called unconditionally at the end of successful processing and also from both container error paths, ensuring a consistent and predictable task termination regardless of which path was taken.

11. Examples

11.1 Example 1 — Successful Credit Score Generation (Normal Flow)

Scenario: The parent orchestrator places a customer record into channel CIPCREDCHANN, container CIPB, then starts CRDTAGY2 asynchronously. The CICS task number happens to produce a short delay.

Input (customer record placed in container):

Field Value
CUSTOMER-EYECATCHER CUST
CUSTOMER-SORTCODE 987654
CUSTOMER-NUMBER 0000000042
CUSTOMER-NAME Mr John Smith
CUSTOMER-STATUS ACTIVE
CUSTOMER-CREDIT-SCORE 000 (placeholder — to be overwritten)
EIBTASKN 1234 (used as RANDOM seed)

Execution steps:

  1. WS-SEED ← 1234. FUNCTION RANDOM(1234) → e.g. 0.47. WS-DELAY-AMT = ((3 − 1) × 0.47) + 1 = ~1 second → EXEC CICS DELAY FOR SECONDS(1).
  2. Customer record read from container CIPB into WS-CONT-IN.
  3. Second FUNCTION RANDOM call (no seed) → e.g. 0.71. WS-NEW-CREDSCORE = ((999 − 1) × 0.71) + 1 = ~709.
  4. CUSTOMER-CREDIT-SCORE in WS-CONT-IN set to 709.
  5. Updated record written back to container CIPB / channel CIPCREDCHANN.
  6. EXEC CICS RETURN — task ends normally.

Output (updated container CIPB):

Field Value
CUSTOMER-CREDIT-SCORE 709 (newly assigned score)
All other customer fields unchanged

The parent’s FETCH collects this result within its 3-second window — a successful end-to-end flow.

11.2 Example 2 — Delay Causes Parent Timeout (Score Arrives Too Late)

Scenario: Same setup as Example 1, but the CICS task number seeds a high random value, pushing the delay close to 3 seconds.

Input:

Field Value
EIBTASKN 9999 (seed generating a high fraction, e.g. 0.97)
Customer record same as Example 1

Execution steps:

  1. WS-DELAY-AMT = ((3 − 1) × 0.97) + 1 = ~2.94 seconds → EXEC CICS DELAY FOR SECONDS(2) (truncated to integer by the COMP field).
  2. Delay completes normally (RESP = NORMAL) — no abend is triggered.
  3. Container is read, a new credit score (e.g. 850) is computed and written back — identical to Example 1.

Result from the parent’s perspective: The parent waits up to 3 seconds for all child agency tasks. Because CRDTAGY2 consumed ~2–3 seconds, the parent may reach its fetch timeout before collecting this result, meaning the updated credit score is never consumed in this transaction run. CRDTAGY2 itself completes successfully and returns normally — it is the parent’s 3-second FETCH window that determines whether the score is consumed.

Key behavioural note: There is approximately a 1-in-3 chance that the delay will exceed the parent’s 3-second window, intentionally simulating a slow or non-responsive external credit bureau.
