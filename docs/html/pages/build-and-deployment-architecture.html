Build & Deployment Architecture

1. Overview

This page describes how Bank of Z source code is built into deployable artifacts and how those artifacts are provisioned across the CICS and IMS runtime environments on z/OS. The build and deployment process is automated by four tools:

  • IBM Dependency Based Build (DBB)
  • Wazi Deploy
  • zconfig
  • z/OS Connect CLI

These tools run when you run the deployment stages.

The page covers four areas:

  • The build pipeline and the artifacts it produces.
  • The difference between full and incremental builds.
  • The CICS and IMS deployment targets.
  • The role of each tool in the toolchain.

2. System Architecture

2.1 Component Overview

The architecture has three layers:

  • Source assets: the application code held in the repository.
  • Automation tooling: the tools that build, package, provision, and deploy.
  • z/OS runtime environments: CICS and IMS, with Db2 and z/OS Connect.
graph TD A[Source Repository] --> B[IBM DBB Build] B --> C[Wazi Deploy Deployment Archive] C --> D[Wazi Deploy] E[zconfig] --> F[CICS Runtime] E --> G[IMS Runtime] D --> F D --> G H[z/OS Connect CLI] --> I[z/OS Connect APIs] I --> F I --> G F --> J[Db2] G --> J

The diagram shows these relationships:

  • DBB builds the source and packages the output into a Wazi Deploy deployment archive.
  • zconfig provisions the CICS and IMS runtime environments.
  • Wazi Deploy installs the archive contents into the provisioned runtimes.
  • The z/OS Connect CLI configures and starts the z/OS Connect APIs. These APIs route requests to CICS or IMS.

2.2 Tooling Summary

Tool Role
IBM DBB Compiles and packages all application source
Wazi Deploy Deploys the build archive to CICS and IMS
zconfig Provisions the CICS and IMS runtime environment
z/OS Connect CLI Configures and starts z/OS Connect APIs

3. Build Pipeline

The build process uses IBM Dependency Based Build (DBB) to compile and package all application source into deployable artifacts.

Figure 1. Relationship between source assets and generated application components.

3.1 Source Assets

The repository contains these source assets:

  • COBOL, PL/I, and Assembler application programs
  • BMS map definitions
  • Db2 source definitions
  • Java application source
  • z/OS Connect API definitions

3.2 Build Outputs

The build produces these artifacts:

  • Load modules (COBOL, PL/I, Assembler, and BMS)
  • Db2 tables and plans
  • Java archive (JAR) files
  • z/OS Connect API artifacts
  • A Wazi Deploy deployment archive that packages all generated artifacts

3.3 Source-to-Artifact Mapping

graph LR S1[COBOL / PL/I / Assembler] --> DBB[IBM DBB] S2[BMS Maps] --> DBB S3[Db2 Source Definitions] --> DBB S4[Java Source] --> DBB S5[z/OS Connect API Definitions] --> DBB DBB --> O1[Load Modules] DBB --> O2[Db2 Tables and Plans] DBB --> O3[JAR Files] DBB --> O4[z/OS Connect API Artifacts] O1 --> PKG[Wazi Deploy Deployment Archive] O2 --> PKG O3 --> PKG O4 --> PKG

Each source asset type is processed by DBB into a matching artifact type. DBB then collects all the artifacts into a single Wazi Deploy deployment archive. This archive is the unit of delivery for the deployment stages.

4. Full and Incremental Builds

Bank of Z supports full and incremental build workflows for different stages of development.

4.1 Full Build

A full build:

  • Compiles all application components.
  • Packages the complete application.
  • Prepares it for deployment.

Use a full build in these cases:

  • During initial installation.
  • When changes to the runtime infrastructure or environment configuration require a complete redeployment.

4.2 Incremental Build

An incremental build rebuilds and deploys only the components affected by source code changes. It is intended for day-to-day development, such as implementing enhancements or fixing defects. It avoids rebuilding the entire application and avoids reprovisioning the existing runtime environment.

After the initial deployment, you can run an incremental build and deploy with the pipeline-remote.sh script. The build process does the following:

  1. Identifies the modified source files.
  2. Rebuilds the impacted components.
  3. Packages the updated artifacts.
  4. Deploys them to the existing runtime environment.

Note: An incremental build requires an existing Bank of Z environment that has already been deployed successfully. Use a full build and deployment when you set up a new environment or when infrastructure changes require a complete redeployment.

4.3 Decision Flow

graph TD A[Start] --> B{Environment already deployed successfully?} B -- No --> C[Full build and deployment] B -- Yes --> D{Infrastructure or environment configuration changed?} D -- Yes --> C D -- No --> E[Incremental build and deploy] E --> F[pipeline-remote.sh]

4.4 Incremental Build Sequence

sequenceDiagram participant Dev as Developer participant Script as pipeline-remote.sh participant DBB as IBM DBB participant WD as Wazi Deploy participant RT as Existing Runtime Dev->>Script: Run incremental build and deploy Script->>DBB: Identify modified source files DBB->>DBB: Rebuild impacted components DBB->>WD: Package updated artifacts WD->>RT: Deploy to existing environment RT-->>Dev: Updated application available

4.5 Example Usage

The documentation names the script but does not give its arguments. A typical invocation is:

BASH 
./pipeline-remote.sh

Check the script for the options that your environment needs.

5. CICS Deployment

After the build completes, Wazi Deploy installs the generated artifacts into the CICS runtime provisioned by zconfig. The z/OS Connect APIs are configured to route requests to the CICS transaction-processing environment.

Figure 2. CICS, Db2, and z/OS Connect deployment workflow.

sequenceDiagram participant ZC as zconfig participant WD as Wazi Deploy participant CICS as CICS Runtime participant ZOSC as z/OS Connect CLI participant API as z/OS Connect APIs ZC->>CICS: Provision CICS runtime WD->>CICS: Install generated artifacts ZOSC->>API: Configure and start APIs API->>CICS: Route requests to CICS transactions

zconfig provisions the CICS runtime first. Wazi Deploy then installs the build output into it. The z/OS Connect CLI configures and starts the APIs, which route requests to the CICS transaction-processing environment.

6. IMS Deployment

IMS application artifacts are deployed to the IMS region provisioned by zconfig. The z/OS Connect APIs are configured to route requests to the IMS Transaction Manager ™ environment.

Figure 3. IMS TM/DB, Db2, and z/OS Connect deployment workflow.

sequenceDiagram participant ZC as zconfig participant WD as Wazi Deploy participant IMS as IMS Region participant ZOSC as z/OS Connect CLI participant API as z/OS Connect APIs ZC->>IMS: Provision IMS region WD->>IMS: Deploy IMS application artifacts ZOSC->>API: Configure and start APIs API->>IMS: Route requests to IMS TM

The IMS flow follows the same pattern as CICS. The difference is that the z/OS Connect APIs route requests to the IMS Transaction Manager.

6.1 CICS and IMS Comparison

Aspect CICS Deployment IMS Deployment
Runtime provisioning zconfig zconfig
Artifact deployment Wazi Deploy Wazi Deploy
Target environment CICS runtime IMS region
z/OS Connect routing CICS transaction-processing environment IMS Transaction Manager ™
Data store Db2 IMS DB and Db2

7. End-to-End Process

graph TD A[Source Repository] --> B[IBM DBB: Compile and Package] B --> C[Wazi Deploy Deployment Archive] D[zconfig: Provision Runtime] --> E[CICS Runtime] D --> F[IMS Region] C --> G[Wazi Deploy: Deploy Artifacts] G --> E G --> F H[z/OS Connect CLI: Configure and Start APIs] --> I[z/OS Connect APIs] I --> E I --> F

The end-to-end flow has these steps:

  1. DBB compiles and packages the source into a deployment archive.
  2. zconfig provisions the CICS and IMS runtime environments.
  3. Wazi Deploy installs the archive contents into the provisioned runtimes.
  4. The z/OS Connect CLI configures and starts the APIs, which route requests to CICS or IMS.

For a description of what each deployment stage does at runtime, see Deploying Bank of Z.
