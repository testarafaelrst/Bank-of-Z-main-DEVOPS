Application Components

Bank of Z is a hybrid IBM Z banking application that combines modern web-based interfaces with enterprise-grade transaction processing. It is composed of several tightly integrated application and infrastructure components spanning front-end UI, API integration, transaction processing engines, data stores, and asynchronous messaging. Together, these components deliver a unified banking experience that leverages the full power of the IBM Z platform.

1. Overview

Bank of Z demonstrates how a modern banking application can be built on IBM Z technology, exposing traditional CICS and IMS transaction-processing capabilities through REST APIs and a browser-based user interface. The system supports customer management, account management, transaction processing, and credit scoring — all running on IBM Z middleware.

Key capabilities include:

  • Browser-based banking UI with no direct knowledge of backend systems
  • API-driven integration via z/OS Connect, bridging modern REST clients to CICS and IMS
  • Dual transaction-processing paths — one through CICS/Db2 and one through IMS TM/IMS DB
  • Asynchronous credit scoring using the CICS Async API and simulated credit agency programs (e.g., CRDTAGY2)
  • Inter-application messaging via IBM MQ with an external system (Bank of Q)
  • Centralized error handling and abend management across all COBOL programs

2. System Architecture

The following diagram illustrates the high-level architecture of Bank of Z, showing how each component relates to the others:

graph TD UI[Bank of Z UI\nBrowser-Based Frontend] ZC[z/OS Connect\nREST API Layer] CICS[CICS\nTransaction Processing] IMS[IMS TM\nTransaction Processing] DB2M[Money & Account Mgmt\nDb2 Database] DB2H[Account History\nDb2 Database] IMSDB[Money & Account Mgmt\nIMS Database] MQ[IBM MQ\nAsynchronous Messaging] BOQ[Bank of Q\nExternal Banking System] UI -->|REST API Calls| ZC ZC -->|CICS Processing Path| CICS ZC -->|IMS Processing Path| IMS CICS -->|Read/Write| DB2M CICS -->|Read/Write| DB2H IMS -->|Read/Write| IMSDB IMS -->|Read/Write| DB2M CICS -->|Publish/Subscribe| MQ MQ -->|Message Exchange| BOQ

The Bank of Z UI communicates exclusively with z/OS Connect through REST APIs. z/OS Connect routes requests to either the CICS or IMS processing path depending on the operation. Business logic executes within those transaction managers, and data is persisted in Db2 for z/OS and IMS databases. IBM MQ provides reliable asynchronous messaging for integration with external systems like Bank of Q.

3. Application Components

3.1 Bank of Z UI

The Bank of Z user interface provides a browser-based experience for performing banking operations. It allows operators and customers to manage customer records, accounts, and transactions through a single unified interface — without needing to know which backend system is processing the request.

Responsibilities:

  • Present banking operations through a web browser
  • Issue REST API calls to z/OS Connect
  • Display responses from CICS and IMS backend systems
  • Abstract backend complexity from the end user

3.2 z/OS Connect

z/OS Connect provides the API layer between the user interface and the backend transaction-processing systems. It exposes services that enable the Bank of Z UI to communicate with CICS and IMS applications through REST APIs, acting as the primary integration gateway into IBM Z.

Responsibilities:

  • Expose REST APIs to the Bank of Z UI
  • Route requests to the appropriate backend (CICS or IMS)
  • Translate between JSON/HTTP and native CICS/IMS communication protocols
  • Enable modern API consumers to interact with IBM Z applications

3.3 CICS Transaction Processing

CICS provides the primary transaction-processing runtime for Bank of Z. It processes banking requests — including customer management, account management, and transaction processing — along the CICS processing path. CICS programs are written in COBOL and interact with Db2 for z/OS for data persistence.

Responsibilities:

  • Execute COBOL business logic for banking operations
  • Manage transactional integrity for customer and account operations
  • Invoke asynchronous child tasks (e.g., credit agency programs via the CICS Async API)
  • Interface with Db2 databases for reads and writes
  • Handle errors centrally via the ABNDPROC abend handler program

3.3.1 CRDTAGY2 — Simulated Credit Agency Program

CRDTAGY2 is a CICS COBOL program that simulates an asynchronous external credit agency. It is invoked as a CICS child task by a parent orchestrator using the CICS Async API. Its role is to compute a random credit score for a customer and return it via a CICS channel and container.

Processing flow:

graph TD classDef startEnd fill:#d5e8d4,stroke:#82b366,color:#000 classDef process fill:#dae8fc,stroke:#6c8ebf,color:#000 classDef decision fill:#fff2cc,stroke:#d6b656,color:#000 classDef error fill:#f8cecc,stroke:#b85450,color:#000 classDef io fill:#e1d5e7,stroke:#9673a6,color:#000 A([CRDTAGY2 Invoked as Child Task]):::startEnd B[Initialize container/channel names\nSeed RANDOM with EIBTASKN]:::process C[Calculate random delay: 1–3 seconds\nusing FUNCTION RANDOM]:::process D[EXEC CICS DELAY FOR SECONDS]:::io E{DELAY RESP = NORMAL?}:::decision F[Build ABNDINFO-REC\nCapture EIBRESP, EIBRESP2,\nAPPLID, TRANID, TASKNO,\nDate/Time via ASKTIME/FORMATTIME]:::error G[EXEC CICS LINK to ABNDPROC\nEXEC CICS ABEND ABCODE PLOP]:::error H[EXEC CICS GET CONTAINER CIPB\nfrom channel CIPCREDCHANN]:::io I{GET CONTAINER\nRESP = NORMAL?}:::decision J[DISPLAY error\nEXEC CICS RETURN]:::error K[Calculate random credit score: 1–999\nusing FUNCTION RANDOM]:::process L[Move new score to\nCUSTOMER-CREDIT-SCORE]:::process M[EXEC CICS PUT CONTAINER CIPB\nback to channel CIPCREDCHANN]:::io N{PUT CONTAINER\nRESP = NORMAL?}:::decision O[DISPLAY error\nEXEC CICS RETURN]:::error P[EXEC CICS RETURN\nTask completes normally]:::startEnd A --> B --> C --> D --> E E -- Yes --> H E -- No --> F --> G H --> I I -- Yes --> K I -- No --> J K --> L --> M --> N N -- Yes --> P N -- No --> O

CRDTAGY2 deliberately introduces a 1-in-3 chance that the credit score is not returned within the parent’s 3-second timeout window, intentionally simulating the unpredictable response times of real-world third-party credit agencies.

Key implementation details:

Aspect Detail
Invocation Asynchronous CICS child task via CICS Async API
Input channel CIPCREDCHANN
Input/output container CIPB
Credit score range 1–999 (computed via FUNCTION RANDOM)
Random seed EIBTASKN (CICS task number)
Delay range 1–3 seconds (EXEC CICS DELAY FOR SECONDS)
Abend code PLOP
Abend handler ABNDPROC (via EXEC CICS LINK)

Code example — random delay and credit score generation:

COBOL 
* Seed the random number generator with the CICS task number
MOVE EIBTASKN TO WS-SEED

* Calculate a random delay between 1 and 3 seconds
COMPUTE WS-DELAY-AMT = ((3 - 1) * FUNCTION RANDOM(WS-SEED)) + 1

* Suspend the task for the calculated duration
EXEC CICS DELAY
    FOR SECONDS(WS-DELAY-AMT)
    RESP(WS-CICS-RESP)
    RESP2(WS-CICS-RESP2)
END-EXEC

* Calculate a random credit score between 1 and 999
COMPUTE WS-NEW-CREDSCORE = ((999 - 1) * FUNCTION RANDOM) + 1

* Update the customer record with the new credit score
MOVE WS-NEW-CREDSCORE TO CUSTOMER-CREDIT-SCORE OF WS-CONT-IN

Code example — reading and writing the CICS container:

COBOL 
* Read customer record from the CICS channel/container
COMPUTE WS-CONTAINER-LEN = LENGTH OF WS-CONT-IN

EXEC CICS GET CONTAINER(WS-CONTAINER-NAME)
    CHANNEL(WS-CHANNEL-NAME)
    INTO(WS-CONT-IN)
    FLENGTH(WS-CONTAINER-LEN)
    RESP(WS-CICS-RESP)
    RESP2(WS-CICS-RESP2)
END-EXEC

* Write updated customer record back to the container
EXEC CICS PUT CONTAINER(WS-CONTAINER-NAME)
    FROM(WS-CONT-IN)
    FLENGTH(WS-CONTAINER-LEN)
    CHANNEL(WS-CHANNEL-NAME)
    RESP(WS-CICS-RESP)
    RESP2(WS-CICS-RESP2)
END-EXEC

Code example — abend handling on DELAY failure:

COBOL 
IF WS-CICS-RESP NOT = DFHRESP(NORMAL)
    INITIALIZE ABNDINFO-REC
    MOVE EIBRESP    TO ABND-RESPCODE
    MOVE EIBRESP2   TO ABND-RESP2CODE
    EXEC CICS ASSIGN APPLID(ABND-APPLID) END-EXEC
    MOVE EIBTASKN   TO ABND-TASKNO-KEY
    MOVE EIBTRNID   TO ABND-TRANID
    PERFORM POPULATE-TIME-DATE
    MOVE 'PLOP'     TO ABND-CODE
    EXEC CICS ASSIGN PROGRAM(ABND-PROGRAM) END-EXEC
    MOVE ZEROS      TO ABND-SQLCODE
    STRING 'CRDTAGY2 - DELAY FAILED. RESP='
           WS-CICS-RESP ' RESP2=' WS-CICS-RESP2
           DELIMITED SIZE INTO ABND-FREEFORM
    EXEC CICS LINK PROGRAM(WS-ABEND-PGM)
        COMMAREA(ABNDINFO-REC)
    END-EXEC
    DISPLAY '*** The delay messed up ! ***'
    EXEC CICS ABEND ABCODE('PLOP') END-EXEC
END-IF

3.4 IMS Transaction Manager (IMS TM)

IMS TM provides an alternative transaction-processing path for the Bank of Z application. It processes banking requests — including customer management, account management, and transaction processing — using the IMS processing path, accessing both the IMS database and the shared Money & Account Management Db2 database.

Responsibilities:

  • Execute business logic along the IMS processing path
  • Manage transactional integrity for IMS-based banking operations
  • Access the IMS hierarchical database and Db2 relational database

4. Data Layer

4.1 Money and Account Management Db2 Database

The Money and Account Management Db2 database is the primary relational data store for Bank of Z. It stores customer and account information used across both the CICS and IMS processing paths.

Responsibilities:

  • Persist customer records, account details, and transaction data
  • Serve both the CICS and IMS transaction-processing paths
  • Provide relational data access via embedded SQL (EXEC SQL) from COBOL programs

4.2 Account History Db2 Database

The Account History Db2 database stores historical account and transaction information. It is used for inquiry and reporting functions, providing a time-ordered view of account activity.

Responsibilities:

  • Store historical transaction and account records
  • Support inquiry and reporting operations
  • Separate historical data from live operational data for performance and archival purposes

4.3 Money and Account Management IMS Database

The Money and Account Management IMS database is the hierarchical data store for the IMS processing path. It enables IMS applications to manage and retrieve customer and account information using DL/I calls.

Responsibilities:

  • Persist customer and account data for the IMS processing path
  • Provide hierarchical data access via DL/I from IMS application programs
  • Support IMS TM transaction processing

5. Messaging and External Integration

5.1 IBM MQ

IBM MQ provides asynchronous messaging capabilities for Bank of Z. It enables reliable, decoupled communication between Bank of Z and external banking systems, supporting integration scenarios where immediate synchronous responses are not required or practical.

Responsibilities:

  • Provide reliable message delivery between Bank of Z and external systems
  • Decouple Bank of Z processing from external system availability
  • Support publish/subscribe and point-to-point messaging patterns

5.2 Bank of Q

Bank of Q represents an external banking system that exchanges information with Bank of Z through IBM MQ. It is used to demonstrate inter-application communication and money transfer scenarios between independent banking systems.

Responsibilities:

  • Act as an external system consumer/producer of IBM MQ messages
  • Demonstrate cross-application money transfer scenarios
  • Validate asynchronous integration patterns between banking systems

The CUSTOMER-RECORD structure is defined in the CUSTOMER.cpy copybook and is included in the working storage of programs such as CRDTAGY2. The CUSTOMER-CREDIT-SCORE field (three-digit unsigned numeric, range 1–999) is the primary output field updated by the credit agency simulation.

8. Copybooks and Shared Definitions

Bank of Z COBOL programs share common data definitions through COBOL copybooks. These copybooks are included in program working-storage sections and define shared record layouts and constants.

9. Error Handling Architecture

All CICS COBOL programs in Bank of Z follow a consistent error handling pattern. Every CICS command captures response codes via RESP and RESP2 options, and any non-normal response triggers structured error processing.

graph TD A[EXEC CICS Command] --> B{RESP = DFHRESP NORMAL?} B -- Yes --> C[Continue Normal Processing] B -- No --> D[Populate ABNDINFO-REC\nRESP, RESP2, APPLID, TRANID,\nTASKNO, Date/Time, Program Name] D --> E[EXEC CICS LINK\nPROGRAM ABNDPROC\nCOMMARED ABNDINFO-REC] E --> F[EXEC CICS ABEND\nABCODE PLOP] F --> G([Task Terminates Abnormally\nCICS Produces Transaction Dump])

The ABNDPROC program acts as a centralized abend handler for the entire Bank of Z application. When any CICS COBOL program encounters an unrecoverable error, it:

  1. Initializes and populates the ABNDINFO-REC structure with full diagnostic context
  2. Links to ABNDPROC via EXEC CICS LINK, passing ABNDINFO-REC as the COMMAREA
  3. Issues EXEC CICS ABEND ABCODE('PLOP') to terminate the task and produce a transaction dump

This pattern ensures that all abend information is captured and routed consistently, regardless of which program encountered the error.
