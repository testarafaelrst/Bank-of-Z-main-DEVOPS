Environment Configuration

Bank of Z requires a set of environment-specific settings to be defined before deployment. This page describes the configuration steps, system variables, dataset naming conventions, CICS region settings, middleware credentials, and tooling required to prepare your z/OS environment for Bank of Z. Complete all steps in this guide before proceeding to any of the getting-started deployment tutorials.

Before you begin, ensure your z/OS environment satisfies all prerequisites, including an active Db2 subsystem (DBD1) and the required RACF definitions.

1. System Architecture

Bank of Z is a multi-tier banking application that runs on z/OS and integrates several IBM middleware components. The diagram below illustrates the high-level architecture and how each component relates to the central configuration file.

graph TD CONFIG[".setup/config/config.yaml"] subgraph Frontend["Frontend Layer"] FE["Frontend\nHTTP :9081 / HTTPS :9445"] ZC["z/OS Connect\nHTTP :9080 / HTTPS :9444"] end subgraph Middleware["Middleware Layer"] CICS["CICS TS 6.3\nHLQ: CICSTS63"] IMS["IMS V15\nDatastore: IMS2"] DB2["Db2 V13\nSSID: DBD1"] end subgraph ZOS["z/OS System"] RACF["RACF\nKeyring: BOZRING"] PROCLIB["SYS1.PROCLIB"] DATASETS["Datasets\nHLQ: BANKZ"] end subgraph Tools["Build & Deploy Tools"] DBB["IBM DBB"] GRADLE["Gradle 9.5.1"] WAZIDEPLOY["Wazi Deploy"] ZCODESCAN["ZCodeScan"] end CONFIG --> Frontend CONFIG --> Middleware CONFIG --> ZOS CONFIG --> Tools FE --> ZC ZC --> CICS ZC --> IMS CICS --> DB2 IMS --> DB2 CICS --> RACF DB2 --> DATASETS PROCLIB --> CICS

The configuration file acts as the single source of truth, driving setup, build, and deployment across all layers. Variable expansion allows values defined in one section to be reused throughout the file, reducing duplication and potential misconfiguration.

2. Overview

The configuration file .setup/config/config.yaml is the central file that controls all environment-specific settings for Bank of Z. It is organized into a global section plus optional middleware-specific sections. The file supports:

  • Hierarchical configuration using YAML sections
  • Variable expansion using {{section.key}} syntax for cross-section references
  • Environment variable injection using ${ENV_VAR} syntax, recommended for credentials
  • Comments using the # prefix

The following diagram shows the configuration flow from file editing through to a running Bank of Z environment:

sequenceDiagram participant Dev as Developer participant CFG as config.yaml participant VAL as Setup Validator participant ZOS as z/OS Environment participant MW as Middleware (CICS/IMS/Db2) Dev->>CFG: Edit global section values Dev->>CFG: Set environment variables (IMS_USER, CICS_USER, etc.) Dev->>VAL: Run setup scripts VAL->>CFG: Validate required fields, paths, and variable references VAL-->>Dev: Report any validation errors VAL->>ZOS: Provision datasets, USS directories, RACF definitions ZOS->>MW: Configure CICS region, IMS datastore, Db2 subsystem MW-->>Dev: Environment ready for deployment

3. Configuring the Application

Edit .setup/config/config.yaml in your local clone of the repository. Update the values in the global section to match your environment. All other values use template references and do not require modification unless your environment uses non-default settings.

YAML 
# Global properties
# - Shared by middleware/tools
# - Subject to change with middleware/tools updates
global:

  # Sandbox
  sandbox_root: "/usr/local/sandboxes"

  # Application
  app_base_name: "BANKZ"
  app_hlq: "{{ global.app_base_name }}"
  app_short_name: "BOZ"       # Maximum 3 characters
  app_version: "0"
  app_release: "1"
  app_modification: "0"

4. System Variables Reference

The global section is organized into the following subsections. Only the global section values require direct editing; the remaining sections use variable expansion references.

4.1 Sandbox

Variable Default Value Description
sandbox_root /usr/local/sandboxes Root directory of the USS sandbox

The sandbox root must be an absolute USS path where the user has write permissions. The parent directory must exist before setup runs.

Examples by environment:

YAML 
# Development
sandbox_root: "/usr/local/sandboxes/dev"

# Test
sandbox_root: "/usr/local/sandboxes/test"

# Personal sandbox
sandbox_root: "/u/userid/sandboxes"

4.2 Application Identity

Variable Default Value Description
app_base_name BANKZ Application base name — also used as the dataset HLQ (max 8 characters)
app_hlq {{ global.app_base_name }} Dataset high-level qualifier
app_short_name BOZ Short application identifier used in CICS region names and transaction IDs (max 3 characters)
app_version 0 Application version
app_release 1 Application release
app_modification 0 Application modification level

The combination of app_base_name, app_version, app_release, and app_modification determines dataset names such as BANKZ.V0R1M0.LOAD and BANKZ.V0R1M0.COBCOPY.

Examples by environment:

YAML 
# Development
app_base_name: "BANKZD"
app_short_name: "BOZ"

# Production
app_base_name: "BANKZP"
app_short_name: "BOZ"

5. CICS Region Settings

Variable Default Value Description
cics_hlq CICSTS63 CICS TS high-level qualifier
cics_uss_dir /usr/lpp/cicsts/cicsts63 CICS USS installation directory
cics_sec YES Enables CICS security

CICS security is enabled by default (cics_sec: YES). The CICS Resource Builder (zcb_home) is used to provision CICS resources automatically during the setup phase. The app_short_name value (BOZ) is used to derive CICS region names and transaction identifiers.

YAML 
# CICS
cics_hlq: "CICSTS63"
cics_uss_dir: "/usr/lpp/cicsts/cicsts63"
cics_sec: "YES"

6. IMS Configuration

Variable Default Value Description
ims_disabled false Set to true to disable IMS integration
ims_sys_hlq IMSV15 IMS system HLQ
ims_java_dir /usr/lpp/ims/imsjava IMS Java installation path
ims_datastore IMS2 IMS datastore name
ims_dfsplex PLEX2 IMS DFSPLEX name
YAML 
# IMS
ims_disabled: "false"
ims_sys_hlq: "IMSV15"
ims_java_dir: "/usr/lpp/ims/imsjava"
ims_datastore: "IMS2"
ims_dfsplex: "PLEX2"

7. Db2 Configuration

Variable Default Value Description
db2_hlq DB2V13 Db2 HLQ
db2_dsntep DSNTEP13 Db2 DSNTEP program name
db2_ssid DBD1 Db2 subsystem ID
db2_runlib {{ global.db2_ssid }}.RUNLIB.LOAD Db2 RUNLIB dataset
db2_sqlid {{ global.zos_current_user }} Db2 SQL ID
db2_java_dir /usr/lpp/db2d10 Db2 Java installation path
db2_grants CICSUSER List of Db2 grantees

The Db2 subsystem (DBD1) must be active before running the environment setup. Grant permissions are applied to all user IDs listed under db2_grants.

YAML 
# DB2
db2_hlq: "DB2V13"
db2_dsntep: "DSNTEP13"
db2_ssid: "DBD1"
db2_runlib: "{{ global.db2_ssid }}.RUNLIB.LOAD"
db2_sqlid: "{{ global.zos_current_user }}"
db2_java_dir: "/usr/lpp/db2d10"
db2_grants:
- "CICSUSER"

8. Granting Permissions

If you are not using the IBMUSER account, you must grant your user ID permission to create Db2 database objects before running the environment setup script.

Run the following command as an administrator, replacing MYUSER with your actual user ID:

BASH 
.setup/setup/grant-perm-user.sh MYUSER

9. Setting Middleware Credentials

Before running the setup scripts, export the following environment variables. Using environment variables for credentials avoids storing sensitive values directly in the configuration file.

Variable Description
IMS_USER IMS user ID
IMS_PASSWORD IMS password
CICS_USER CICS user ID
CICS_PASSWORD CICS password
BASH 
export IMS_USER=<your_ims_user>
export IMS_PASSWORD=<your_ims_password>

export CICS_USER=<your_cics_user>
export CICS_PASSWORD=<your_cics_password>

These variables are consumed by the CICS and IMS configuration sections of config.yaml via ${CICS_USER} and ${IMS_PASSWORD} references:

YAML 
cics:
  user: ${CICS_USER}
  password: ${CICS_PASSWORD}
  cmci_port: 27100
  ipic_port: 27114

10. Variable Expansion

Configuration values can reference other entries using {{section.key}} syntax. Environment variables use ${ENV_VAR} syntax. References are resolved recursively during setup processing.

graph LR A["sandbox_root: /usr/local/sandboxes"] B["zconfig_home: {{global.sandbox_root}}/tools/zconfig"] C["zcb_home: {{global.sandbox_root}}/tools/zrb/..."] D["dbb_home: {{global.sandbox_root}}/tools/dbb"] E["ENV: ${ZOS_CURRENT_USER}"] F["zos_current_user: ${ZOS_CURRENT_USER}"] G["db2_sqlid: {{global.zos_current_user}}"] A --> B A --> C A --> D E --> F F --> G

The diagram above illustrates how a single root value like sandbox_root fans out to multiple tool path definitions, and how a runtime environment variable flows through to a Db2 SQL ID. This chained resolution means updating sandbox_root automatically propagates to all dependent tool paths.

Example of cross-section variable expansion:

YAML 
sandbox:
  path: /usr/local/sandboxes/bank-of-z

dbb:
  dbb_build: ${sandbox.path}/Bank-of-Z/.setup/build
  dbb_cwd: ${sandbox.path}/Bank-of-Z/

11. ZCodeScan Configuration

The static scan stage requires a separate ZCodeScan configuration file. This file must be created manually and encoded in ISO8859-1, as ZCodeScan cannot read files saved in IBM-1047 or UTF-8.

Create ~/zcs_config_file.yml (or the path specified by zcodescan.config_file in config.yaml):

YAML 
license_server:
  url: https://127.0.0.1:8195
  user: MYUSER
  password: MY_PASSWORD
  verify: false

Note: The password is automatically encrypted after the first scan. Plain-text credentials are only required on the first use.

The ZCodeScan tool path is set in the global section:

YAML 
zcodescan_home: "/global/opt/pyenv/akf"

13. Configuration Validation

The setup scripts automatically validate the configuration before execution. The following checks are performed:

  • Required fields are present: sandbox_root, app_base_name, app_short_name, and all middleware HLQ values must be defined.
  • Variable references resolve: All {{section.key}} and ${ENV_VAR} references must point to existing entries or active environment variables — circular references are not permitted.
  • Absolute path formats: All path values must begin with / and must not end with a trailing slash.
  • Naming length limits: app_base_name ≤ 8 characters; app_short_name ≤ 3 characters.
  • Tool locations defined: All tool home directories must be specified.

Correcting configuration issues before running setup prevents downstream build and deployment failures.

13.1 Common Configuration Issues

Error Cause Resolution
Configuration file not found config.yaml is missing or in the wrong directory Run ls -la .setup/config/config.yaml to verify the file exists
Variable reference cannot be resolved A {{section.key}} reference points to a non-existent field Check that the referenced section and key are spelled correctly and exist in the file
Invalid path format A path value is relative rather than absolute Ensure all path values start with /
