Zowe CLI Workflow

1. Overview

The Zowe CLI workflow provides a structured, Git-based development process for Bank of Z, enabling developers to edit, build, upload, and test COBOL and CICS changes directly from a local workstation without requiring SSH access to z/OS UNIX System Services (USS). By leveraging two key orchestration scripts — setup-local.sh and pipeline-local.sh — the workflow bridges local development environments with the z/OS backend, automating environment provisioning, source cloning, compilation, and deployment.

This workflow supports both full builds (for initial setup or infrastructure changes) and incremental builds (for day-to-day development), making it flexible enough to handle the full spectrum of development scenarios. Integration with VS Code further streamlines the experience by surfacing these scripts as runnable tasks within the editor.

2. System Architecture

The Zowe CLI workflow operates across two distinct environments: the developer’s local workstation and z/OS USS. The local scripts act as orchestrators, using Zowe CLI commands to interact with z/OS without requiring a direct SSH session. The remote scripts then execute natively on USS to perform build, deploy, and validation steps.

The diagram above illustrates how changes originate on the developer’s workstation, are pushed to GitHub, and then pulled down to z/OS USS by the local orchestration scripts via Zowe CLI. Remote scripts handle all USS-side operations, from environment validation through to final deployment into CICS and supporting middleware.

3. Build and Deploy Modes

Bank of Z supports two distinct build and deploy strategies. Choosing the right mode depends on the scope of changes being made and the current state of the target environment.

3.1 Full Build and Deploy

A full build provisions or re-provisions the entire environment, including middleware configuration. Use this mode when:

  • Setting up a brand-new environment for the first time.
  • Recovering from infrastructure-level changes.
  • Onboarding a new developer with a fresh USS workspace.
BASH 
bash .setup/setup-local.sh

3.2 Incremental Build and Deploy

After the initial setup, most day-to-day development uses an incremental build. This mode rebuilds and redeploys only the components affected by your changes, skipping middleware re-provisioning.

BASH 
bash .setup/pipeline-local.sh

The incremental pipeline uploads pipeline assets via Zowe CLI and invokes pipeline-remote.sh on USS, which runs the DBB build and Wazi Deploy steps.

3.3 Build Mode Comparison

Operation Zowe CLI Full Setup Zowe CLI Incremental GRUB
Initial setup ~5–8 minutes N/A ~3–6 minutes
Incremental update N/A ~5–8 minutes ~5–10 seconds
Requires push to remote Yes Yes No

Tip: For ultra-fast iteration during active development, consider the GRUB workflow, which does not require pushing changes to a remote repository between iterations.

4. Daily Development Cycle

The following diagram shows the end-to-end sequence of steps a developer follows in a typical Zowe CLI development cycle:

sequenceDiagram participant Dev as Developer (Local) participant Git as GitHub Repository participant CLI as Zowe CLI Layer participant USS as z/OS USS participant CICS as CICS Region Dev->>Dev: Edit COBOL / BMS / Config files Dev->>Git: git add . && git commit && git push Dev->>CLI: Run setup-local.sh or pipeline-local.sh CLI->>USS: Create USS workspace directory CLI->>Git: git clone branch onto USS USS->>USS: Run validate-prereqs USS->>USS: Run environment setup USS->>USS: Run DBB Build & Wazi Deploy USS->>CICS: Deploy compiled artifacts CICS-->>Dev: Changes live at :9080/bank-frontend-vanilla

4.1 Step 1 — Make Changes

Modify application source code in your local workspace. Common change categories include:

  • COBOL programs and copybooks — core business logic and shared data structures.
  • BMS maps — CICS Basic Mapping Support screen definitions.
  • z/OS Connect API assets — RESTful API definitions bridging the web tier to CICS.
  • Web application components — the Bank of Z frontend UI.
  • Configuration files — environment-specific settings in config.yaml.

4.2 Step 2 — Commit and Push

Because setup-local.sh and pipeline-local.sh clone your branch from GitHub onto USS, any unpushed commits will not be included in the build. Always push before triggering a pipeline run.

BASH 
git add .
git commit -m "Your change description"
git push origin your-branch

4.3 Step 3 — Run the Setup or Pipeline Task

Trigger the appropriate script depending on the scope of your changes.

From the terminal:

BASH 
# Full environment setup (first time or after infrastructure changes)
bash .setup/setup-local.sh

# Incremental build and deploy only
bash .setup/pipeline-local.sh

From VS Code:

Open the Command Palette (Ctrl+Shift+P / Cmd+Shift+P) → Tasks: Run Task → select the appropriate task.

The VS Code task is defined in .vscode/tasks.json:

JSON 
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "Setup Bank of Z Environment",
      "type": "shell",
      "command": "bash .setup/setup-local.sh",
      "problemMatcher": [],
      "presentation": {
        "reveal": "always",
        "panel": "new"
      }
    }
  ]
}

4.4 Step 4 — What Runs Automatically

Once triggered, the scripts orchestrate a sequence of operations across local and remote environments without requiring manual intervention:

CODE 
Local Machine                         z/OS USS
─────────────                         ────────
setup-local.sh executes
│
├─ Creates USS workspace  ──────────→ Directory created
├─ Clones your branch     ──────────→ git clone from GitHub
└─ Invokes setup-remote.sh ─────────→ Runs on USS natively
                                        ├─ validate-prereqs
                                        ├─ environment
                                        └─ install-bank-of-z

For incremental builds, pipeline-local.sh uploads pipeline assets and invokes pipeline-remote.sh on USS, which runs the DBB build and Wazi Deploy without re-provisioning middleware.

4.5 Step 5 — Validate Changes

Once deployment completes, open the Bank of Z frontend in a browser to verify your changes are live:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

5. Working with Branches

The orchestration scripts automatically detect your current local Git branch and use it when cloning source onto USS. This means each developer or feature stream can maintain an isolated USS workspace.

BASH 
# Switch to your feature branch before running
git checkout feature/my-change
git push origin feature/my-change
bash .setup/setup-local.sh

Each developer can configure a separate USS workspace path in config.yaml to avoid collisions when multiple team members are working concurrently on the same z/OS system.

6. Script Reference

Script Location Purpose
setup-local.sh .setup/setup-local.sh Full environment provisioning — runs once or after infrastructure changes
pipeline-local.sh .setup/pipeline-local.sh Incremental build and deploy — used for day-to-day development
setup-remote.sh Executed on USS Runs validate-prereqs, environment, and install-bank-of-z
pipeline-remote.sh Executed on USS Runs DBB build and Wazi Deploy without reprovisioning middleware
