Glossary

This glossary defines key terms, acronyms, and IBM Z concepts used throughout the Bank of Z documentation. It serves as a reference for developers, architects, and operators working with the Bank of Z hybrid banking application and its supporting technologies.

1. Overview

Bank of Z is a sample hybrid banking application built on IBM Z, demonstrating modern application development, integration, build, deployment, and operational workflows. It spans multiple transaction-processing environments, databases, messaging systems, and development toolchains — each with its own terminology and conventions.

This glossary is organized into thematic sections to help you quickly locate related concepts:

  • Core Application & Architecture — fundamental concepts about Bank of Z itself
  • Transaction Processing — CICS and IMS environments
  • Data & Messaging — Db2, IMS DB, and IBM MQ
  • Development Tools & Workflows — IDEs, build frameworks, and CLI tools
  • Infrastructure & Platform — z/OS services and APIs

The diagram below illustrates how these technology domains relate to one another within Bank of Z:

graph TD A[👤 End User / Web App] --> B[z/OS Connect REST API] B --> C{Customer Routing} C -->|ID starts with C| D[CICS Transaction] C -->|ID starts with I| E[IMS TM Transaction] D --> F[COBOL Business Logic] E --> F F --> G[Db2 for z/OS] F --> H[IMS DB] F --> I[IBM MQ] I --> J[Bank of Q - External System] G --> K[Account History Db2 Database]

This diagram shows the end-to-end request flow in Bank of Z, from the web application through z/OS Connect, into the routing layer, down through CICS or IMS TM transaction processing, and finally into the data and messaging backends.

2. System Architecture

Bank of Z follows a hybrid architecture model, where a single web-facing interface connects to multiple back-end transaction environments. Requests are routed dynamically based on the customer identifier, processed through environment-specific COBOL business logic, and served by shared data and messaging resources.

graph LR subgraph Development ["🛠️ Development Toolchain"] VS[VS Code / Bob IDE] GIT[Git Repository] DBB[DBB / zBuilder] ZCS[ZCodeScan] GRUB[GRUB Workflow] VS --> GIT GIT --> DBB DBB --> ZCS GIT --> GRUB end subgraph Deploy ["🚀 Build & Deploy"] PIPE[Pipeline] WAZI[Wazi Deploy] ODE[ODE Environment] PIPE --> WAZI WAZI --> ODE end subgraph zOS ["🖥️ z/OS Platform"] USS[USS - UNIX System Services] ZCONN[z/OS Connect] CICS[CICS TM] IMS[IMS TM] DB2[Db2 for z/OS] IMSDB[IMS DB] MQ[IBM MQ] ZCFG[zconfig] USS --> ZCONN ZCONN --> CICS ZCONN --> IMS CICS --> DB2 IMS --> IMSDB CICS --> MQ IMS --> MQ ZCFG --> CICS ZCFG --> DB2 ZCFG --> IMS ZCFG --> ZCONN end subgraph External ["🌐 External Systems"] BANKQ[Bank of Q] MQ --> BANKQ end DBB --> USS WAZI --> USS

The architecture above highlights three distinct layers:

  1. Development Toolchain — Source code is written in VS Code or Bob IDE, versioned in Git, compiled via DBB/zBuilder, and scanned by ZCodeScan. The GRUB workflow allows iterative development without committing every change.
  2. Build & Deploy — Automated pipelines package and deploy artifacts to z/OS environments using Wazi Deploy, targeting On-Demand Environments (ODE).
  3. z/OS Platform — The runtime layer hosts all transaction, data, and messaging components. zconfig provisions middleware configuration as code across CICS, Db2, IMS, and z/OS Connect.

3. Core Application & Architecture

3.1 Bank of Z

Bank of Z is a sample hybrid banking application that demonstrates modern z/OS application development, integration, build, deployment, and operational workflows.

It serves as a reference implementation for teams learning IBM Z development practices, combining CICS, IMS, Db2, IMS DB, IBM MQ, and z/OS Connect into a single, cohesive application.

3.2 Hybrid Architecture

Hybrid Architecture is an application architecture that integrates multiple transaction-processing environments and technologies into a unified user experience.

In Bank of Z, customer requests are processed through either CICS or IMS TM while sharing common COBOL business logic, data resources, and messaging services.

3.3 Customer Routing

Customer Routing is the Bank of Z mechanism that routes requests to either CICS or IMS TM based on the customer identifier pattern.

Customer ID Prefix Routed To
C CICS Transaction
I IMS TM Transaction
sequenceDiagram participant User as 👤 User participant API as z/OS Connect participant Router as Customer Router participant CICS as CICS TM participant IMS as IMS TM participant DB as Db2 / IMS DB User->>API: REST Request (Customer ID) API->>Router: Forward Request alt Customer ID starts with "C" Router->>CICS: Route to CICS Transaction CICS->>DB: Query / Update Db2 DB-->>CICS: Data Response CICS-->>Router: Transaction Result else Customer ID starts with "I" Router->>IMS: Route to IMS TM Transaction IMS->>DB: Query / Update IMS DB DB-->>IMS: Data Response IMS-->>Router: Transaction Result end Router-->>API: Result API-->>User: REST Response

3.4 Bank of Q

Bank of Q is a sample external banking system used to demonstrate inter-application communication and money transfer scenarios through IBM MQ.

Bank of Q acts as a simulated external banking partner, receiving and sending messages asynchronously via IBM MQ to Bank of Z.

3.5 API

API (Application Programming Interface) is a defined interface that enables applications and services to communicate with each other.

In the Bank of Z context, REST APIs exposed through z/OS Connect serve as the primary integration point between the web front end and z/OS back-end transactions.

4. Transaction Processing

4.1 CICS

CICS (Customer Information Control System) is an IBM transaction-processing system used to execute online business transactions.

In Bank of Z, customers with identifiers beginning with C are routed to CICS transactions. CICS manages the lifecycle of each transaction, including screen interactions (via BMS) and calls to COBOL programs.

4.2 IMS TM

IMS TM (IBM Information Management System Transaction Manager) is a transaction-processing environment used by Bank of Z.

Customers with identifiers beginning with I are routed to IMS TM transactions. IMS TM coordinates the execution of COBOL programs that interact with IMS DB.

4.3 BMS

BMS (Basic Mapping Support) is a CICS facility used to define terminal screen layouts and user interactions.

BMS maps define the structure of 3270-style terminal screens used by CICS applications.

4.4 JVM

JVM (Java Virtual Machine) is the runtime environment used to execute Java applications and services.

In Bank of Z, the JVM underpins Java-based services and tooling that operate alongside traditional COBOL and assembler programs on z/OS.

5. Data & Messaging

5.1 Db2

Db2 (IBM Db2 for z/OS) is a relational database used to store customer, account, and transaction information.

Db2 is accessed by CICS-routed transactions within Bank of Z. SQL embedded in COBOL programs provides structured access to relational data.

Example — Embedded SQL in COBOL accessing Db2:

COBOL 
EXEC SQL
    SELECT ACCT_BALANCE
    INTO   :WS-BALANCE
    FROM   ACCOUNT
    WHERE  ACCT_ID = :WS-ACCT-ID
END-EXEC.

5.2 Account History Db2 Database

Account History Db2 Database is a Db2 database used by Bank of Z to store historical account and transaction information for inquiry and reporting functions.

This database is a dedicated Db2 instance (or table space) within the broader Db2 environment, used specifically for historical lookups and audit trails.

5.3 IMS DB

IMS DB (IBM Information Management System Database) is a hierarchical database used by the IMS processing path within Bank of Z.

Unlike the relational model of Db2, IMS DB organizes data in a parent-child hierarchy. COBOL programs access IMS DB using DL/I calls.

Example — DL/I call in COBOL accessing IMS DB:

COBOL 
CALL 'CBLTDLI' USING DLI-GU
                     PCB-MASK
                     IO-AREA
                     SSA-CUSTOMER.

5.4 IBM MQ

IBM MQ is IBM messaging middleware used for asynchronous communication between applications and external systems.

In Bank of Z, IBM MQ facilitates money transfer messages between Bank of Z and Bank of Q. Its asynchronous model decouples the two banking systems, enabling reliable message delivery.

sequenceDiagram participant BankZ as Bank of Z (CICS/IMS) participant MQ as IBM MQ participant BankQ as Bank of Q BankZ->>MQ: PUT Message (Transfer Request) MQ-->>BankQ: Deliver Message BankQ->>MQ: PUT Reply (Confirmation) MQ-->>BankZ: Deliver Reply

5.5 Copybook

Copybook is a reusable source file containing data structure definitions shared across COBOL programs.

Copybooks promote consistency by centralizing record layouts, ensuring all programs reference the same field names, types, and lengths.

Example — COBOL copybook inclusion:

COBOL 
01 CUSTOMER-RECORD.
   COPY CUSTCPY.

6. Development Tools & Workflows

6.1 COBOL

COBOL (Common Business-Oriented Language) is the primary programming language used for the Bank of Z business logic.

COBOL programs implement customer inquiry, account management, and fund transfer operations within both the CICS and IMS processing paths.

6.2 VS Code

VS Code (Visual Studio Code) is a development environment commonly used to develop, build, and manage Bank of Z assets.

VS Code is typically paired with IBM Z extensions and Zowe CLI to provide a modern IDE experience for z/OS development.

6.3 Bob IDE

Bob IDE (IBM Premium Bob for Z) is an integrated development environment that supports IBM Z application development workflows.

Bob IDE offers Z-specific tooling for editing, building, and debugging COBOL and other z/OS languages.

6.4 Git

Git is a distributed version control system used to manage source code and support collaborative development.

All Bank of Z source files are stored in a Git repository, enabling branching, merging, code review, and CI/CD integration.

6.5 DBB

DBB (IBM Dependency Based Build) is a build framework used to compile, link, and manage z/OS application builds.

DBB analyzes source dependencies and builds only the programs affected by a given change, reducing build times.

6.6 zBuilder

zBuilder is a build framework used with DBB to automate compilation, linking, and build orchestration for z/OS applications.

6.7 ZCodeScan

ZCodeScan is a static analysis tool used to analyze source code quality and identify potential issues.

ZCodeScan integrates into the pipeline to enforce code quality gates before deployment.

6.8 GRUB

GRUB (Git Remote User Build) is a workflow that synchronizes local changes to z/OS USS and runs setup and build processes without requiring commits for every change.

GRUB accelerates the inner development loop, allowing developers to test changes on z/OS rapidly.

6.9 Workflow

Workflow is a defined development process used to build, deploy, test, and validate application changes.

Bank of Z supports two primary workflows:

Workflow Description
VS Code Workflow IDE-driven development using VS Code extensions and Zowe CLI
GRUB Workflow Git-based remote build without requiring a commit per iteration

6.10 Pipeline

Pipeline is an automated sequence of build, packaging, deployment, and validation activities executed through Bank of Z development workflows.

graph LR A[📝 Code Change in Git] --> B[DBB / zBuilder Compile] B --> C[ZCodeScan Analysis] C --> D{Quality Gate} D -->|Pass| E[Wazi Deploy Package] D -->|Fail| F[🔴 Build Failed - Notify Developer] E --> G[Deploy to ODE] G --> H[Validation / Testing] H --> I[✅ Deployment Complete]

6.11 Zowe CLI

Zowe CLI is a command-line interface used to interact with z/OS systems, services, datasets, USS files, and development workflows.

Zowe CLI is commonly used alongside VS Code to submit jobs, browse datasets, and interact with z/OS from a local terminal.

Example — Zowe CLI listing USS files:

BASH 
zowe zos-files list uss "/u/ibmuser/bank-of-z/src"

7. Infrastructure & Platform

7.1 z/OS Connect

z/OS Connect is an API framework that enables REST-based access to z/OS applications and services.

In Bank of Z, z/OS Connect provides the interface between the web application and the CICS and IMS transaction environments, translating RESTful HTTP calls into CICS and IMS transaction invocations.

7.2 USS

USS (UNIX System Services) is the POSIX-compliant environment within z/OS used to host source code, scripts, build artifacts, and application assets.

USS provides a familiar file system structure on z/OS, enabling standard shell scripting, Git operations, and build tooling.

7.3 ODE

ODE (On-Demand Environment) is a preconfigured development and testing environment used to provision and run Bank of Z components.

ODEs enable isolated testing of application changes without impacting shared or production systems.

7.4 RSE API

RSE API (Remote System Explorer API) is a service used by Zowe CLI and development tools to interact with z/OS resources.

RSE API acts as the back-end service layer that handles requests from IDEs and CLI tools, providing access to z/OS datasets, jobs, and USS files.

7.5 ZOAU

ZOAU (IBM Z Open Automation Utilities) is a collection of utilities and APIs used to automate z/OS administration and development tasks.

ZOAU provides shell commands and Python APIs that simplify interaction with z/OS datasets, jobs, and system resources.

Example — ZOAU shell command to copy a dataset:

BASH 
dcp "HLQ.SOURCE.COBOL(PROGRAM1)" /u/ibmuser/backup/PROGRAM1.cbl

7.6 Wazi Deploy

Wazi Deploy is IBM deployment automation tooling used to deploy application artifacts and configuration changes.

Wazi Deploy integrates with the Bank of Z pipeline to package build outputs and apply them to a target z/OS environment.

7.7 zconfig

zconfig (z/OS Middleware Configuration Tool) is a command-line tool used to configure and create artifacts for CICS Transaction Server for z/OS, Db2 for z/OS, IMS, and z/OS Connect — introducing configuration as code to z/OS middleware.

zconfig enables teams to version-control their middleware configuration alongside application source code, making environment provisioning repeatable and auditable.

Example — zconfig provisioning middleware:

BASH 
zconfig apply --config bank-of-z-cics.yaml --env ODE
