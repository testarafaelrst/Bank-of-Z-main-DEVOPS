Deployment Options

Bank of Z supports a fully automated deployment process that provisions a complete application environment on z/OS — including CICS, IMS, z/OS Connect, a Liberty frontend server, and all application data. Regardless of which deployment path you choose, all workflows run the same underlying deployment stages and produce an identical deployed environment. This guide covers all three available deployment approaches: Direct USS, Zowe CLI, and GRUB.

1. Overview

Deploying Bank of Z means standing up a complete, integrated banking application stack on z/OS from source code. The process is driven by a common shell script (setup-common.sh) that orchestrates three sequential stages: prerequisite validation, middleware provisioning, and application build and deployment.

All three deployment workflows are equivalent in outcome. The difference lies in how your source code reaches z/OS USS and how the scripts are triggered:

Workflow Code Transfer Method Requires SSH to USS Requires Git Push
Direct USS Manual git clone on USS ✅ Yes Optional
Zowe CLI Cloned from GitHub via RSE API ❌ No ✅ Yes
GRUB Local file sync via GRUB ❌ No ❌ No

2. System Architecture

Bank of Z is a multi-tier application running entirely on z/OS. The deployment process provisions and wires together all of the following components.

graph TD subgraph Local Machine DEV[Developer Workstation] REPO[Local Git Repository] end subgraph z/OS USS USS[USS Workspace] DBB[DBB Build Engine] WAZI[Wazi Deploy] end subgraph z/OS Middleware CICS[CICS Region] IMS[IMS Region] DB2[Db2 Subsystem DBD1] ZC[z/OS Connect Server] LIB[Liberty Frontend Server] end DEV -->|SSH / Zowe CLI / GRUB| USS USS --> DBB DBB -->|Build Artifacts| WAZI WAZI -->|Deploy| CICS WAZI -->|Deploy| IMS USS -->|Provision| ZC USS -->|Provision| LIB USS -->|Create Tables & Test Data| DB2 CICS --> DB2 IMS --> DB2 ZC --> CICS ZC --> IMS LIB --> ZC

The diagram above illustrates the full stack. The Liberty frontend communicates with z/OS Connect, which in turn routes requests to the CICS and IMS backend regions. Both backend regions interact with the Db2 subsystem. All middleware is provisioned automatically during deployment — the only pre-existing dependency is the Db2 subsystem (DBD1).

3. Deployment Workflows

All three workflows invoke the same three stages via subcommands of .setup/setup-common.sh. The key differences are in how files are transferred to USS and how the scripts are initiated.

graph TD A[Developer: Choose Workflow] --> B{Which Workflow?} B -->|Direct USS| C[SSH to z/OS USS\ngit clone repository] B -->|Zowe CLI| D[Local clone\ngit push branch\nrun setup-local.sh] B -->|GRUB| E[Local clone\nedit config\ntrigger GRUB sync] C --> F[Edit config.yaml on USS] D --> G[Edit config.yaml locally] E --> H[Edit config.yaml locally] F --> I[setup-common.sh validate-prereqs] G --> I H --> I I --> J[setup-common.sh environment] J --> K[setup-common.sh install-bank-of-z] K --> L[Deployed Bank of Z Environment]

3.1 Direct USS

Connect directly to z/OS via SSH, clone the repository on USS, and run each deployment stage manually. This is the most transparent option — every command is visible and can be observed as it runs.

Prerequisites:

  • SSH access to your z/OS system
  • Git installed on z/OS USS
  • A z/OS environment that meets the Prerequisites requirements

3.1.1 Step-by-Step Procedure

Step 1 — SSH to z/OS

BASH 
ssh user@your-zos-host

Step 2 — Clone the repository

Choose a working directory on USS. You will reference this path in the configuration file.

BASH 
export BANK_OF_Z_WORK_DIR=/usr/local/sandboxes/bank-of-z
mkdir -p $BANK_OF_Z_WORK_DIR
cd $BANK_OF_Z_WORK_DIR
git clone https://github.com/IBM/Bank-of-Z.git
cd Bank-of-Z

Step 3 — Edit the configuration file

BASH 
vi .setup/config/config.yaml

For details on each configuration field, see Environment Configuration.

Step 4 — Validate prerequisites

BASH 
.setup/setup-common.sh validate-prereqs

Step 5 — Provision middleware

BASH 
.setup/setup-common.sh environment

Step 6 — Build and deploy

BASH 
.setup/setup-common.sh install-bank-of-z

Note: Warnings related to the YAML scanner and chown failures are expected and do not indicate a problem.

Step 7 — Verify the deployment

Open the Bank of Z frontend in a browser:

  • HTTP: http://<your-zos-host>:9081/admin.html
  • HTTPS: https://<your-zos-host>:9445/admin.html

Step 8 — Run post-install verification tests

BASH 
.setup/setup-common.sh verify-installation

Runs the integration test suite in tests/ against the deployed application. The tests exercise the CICS and IMS API paths and report a pass/fail result for each. All tests must pass before the installation is considered complete.

3.2 Zowe CLI

Clone the repository to your local machine, then use the provided Zowe CLI scripts to clone your current GitHub branch to z/OS USS and run the deployment scripts automatically. No SSH access to USS is required.

Note: The script clones your branch from GitHub on USS. Your branch must be pushed to the remote before running the script. Local commits that have not been pushed are not included.

Prerequisites:

  • z/OS environment meets the Prerequisites requirements
  • Zowe CLI installed with the RSE API plug-in
  • Zowe profile configured — see Zowe CLI Setup

3.2.1 Step-by-Step Procedure

Step 1 — Clone the repository locally

BASH 
git clone https://github.com/IBM/Bank-of-Z.git
cd Bank-of-Z

Step 2 — Edit the configuration file

Open .setup/config/config.yaml in your local editor and update it for your environment.

Step 3 — Push your branch

The script detects your current local branch and clones it from GitHub to z/OS USS. Your branch must be pushed before running the script.

BASH 
git add .setup/config/config.yaml
git commit -m "Configure for my environment"
git push

Step 4 — Run the setup script

BASH 
bash .setup/setup-local.sh

Alternatively, in Visual Studio Code, select Command Palette → Tasks: Run Task → Setup Bank of Z Environment.

3.2.2 What Runs Automatically

sequenceDiagram participant Dev as Developer (Local) participant GitHub as GitHub Remote participant Zowe as Zowe CLI (RSE API) participant USS as z/OS USS Dev->>GitHub: git push branch Dev->>Zowe: bash .setup/setup-local.sh Zowe->>USS: Create USS workspace directory Zowe->>GitHub: Clone branch to USS GitHub-->>USS: Repository files Zowe->>USS: Invoke setup-remote.sh USS->>USS: validate-prereqs USS->>USS: environment (Db2, CICS, IMS, z/OS Connect, Liberty) USS->>USS: install-bank-of-z (DBB build, Wazi Deploy, test data) USS-->>Dev: Logs written to /tmp/remote-setup.log

The automated script performs the following in sequence:

  1. Creates the USS workspace directory using the Zowe RSE API
  2. Clones your current branch from GitHub to z/OS USS
  3. Invokes setup-remote.sh on USS, which runs validate-prereqs, environment, and install-bank-of-z

Logs are written to /tmp/remote-setup.log on your local machine.

Step 5 — Verify the deployment

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

3.3 GRUB

Clone the repository to your local machine, then use GRUB to transfer your local branch directly to z/OS USS and trigger the setup scripts automatically. Unlike the Zowe CLI approach, no commit or push to a remote repository is required before deploying — GRUB syncs your local working directory as-is.

Prerequisites:

  • z/OS environment meets the Prerequisites requirements
  • GRUB installed and configured with the Bank of Z remote path and post-sync hook — see GRUB Setup

3.3.1 Step-by-Step Procedure

Step 1 — Clone the repository locally

BASH 
git clone https://github.com/IBM/Bank-of-Z.git
cd Bank-of-Z

Step 2 — Edit the configuration file

Open .setup/config/config.yaml in your local editor and update it for your environment. You do not need to commit your changes — GRUB syncs the file as-is.

Step 3 — Trigger a GRUB sync

Trigger a GRUB sync from your local machine. Refer to the GRUB documentation for the specific command or UI action for your installation.

GRUB transfers your local changes to z/OS USS. Only files that have changed since the previous sync are transferred, making subsequent syncs faster.

3.3.2 What Runs Automatically

sequenceDiagram participant Dev as Developer (Local) participant GRUB as GRUB Sync Agent participant USS as z/OS USS Dev->>GRUB: Trigger sync GRUB->>USS: Transfer changed files (delta sync) USS-->>GRUB: Sync complete GRUB->>USS: Post-sync hook: invoke setup-remote.sh USS->>USS: validate-prereqs USS->>USS: environment (Db2, CICS, IMS, z/OS Connect, Liberty) USS->>USS: install-bank-of-z (DBB build, Wazi Deploy, test data) USS-->>Dev: Deployment complete

After the sync completes, the configured post-sync hook runs setup-remote.sh on z/OS USS, which automatically executes all three deployment stages.

Step 4 — Verify the deployment

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

4. Deployment Stages

Regardless of which workflow you use, the same three deployment stages always run in sequence. Each stage is a subcommand of .setup/setup-common.sh.

graph LR S1[Stage 1\nvalidate-prereqs] --> S2[Stage 2\nenvironment] S2 --> S3[Stage 3\ninstall-bank-of-z] S3 --> DONE[Bank of Z\nDeployed ✅] style S1 fill:#f0f4ff,stroke:#4a6fa5 style S2 fill:#f0f4ff,stroke:#4a6fa5 style S3 fill:#f0f4ff,stroke:#4a6fa5 style DONE fill:#e6f4ea,stroke:#2e7d32

4.1 Stage 1: Validate Prerequisites

BASH 
.setup/setup-common.sh validate-prereqs

Verifies that all required tools are installed on z/OS USS at the versions specified in config.yaml. This includes:

  • DBB (Dependency Based Build)
  • ZOAU (z/OS Open Automation Utilities)
  • zconfig
  • Wazi Deploy
  • Java
  • Git
  • Network connectivity to GitHub

Resolve any reported failures before proceeding to Stage 2.

4.2 Stage 2: Provision Middleware

BASH 
.setup/setup-common.sh environment

Provisions the complete application runtime from scratch. This stage performs the following operations in sequence:

  1. Stops any existing Bank of Z tasks (CICS, IMS, z/OS Connect, frontend)
  2. Cleans up existing application datasets
  3. Clones the IBM DBB accelerators repository from GitHub
  4. Copies the zBuilder build framework
  5. Creates Db2 database tables
  6. Provisions a CICS region using zconfig
  7. Provisions an IMS region using zconfig
  8. Creates IMS database objects
  9. Starts IMS Bank of Z message processing regions
  10. Creates and starts a z/OS Connect server
  11. Creates and starts a frontend Liberty server

Note: This stage requires a pre-existing Db2 subsystem (DBD1). All other middleware — including CICS, IMS, z/OS Connect, and the frontend server — is provisioned automatically.

4.3 Stage 3: Build and Deploy

BASH 
.setup/setup-common.sh install-bank-of-z

Builds the application from source and deploys the generated artifacts to the provisioned runtime:

  1. Runs a full DBB build for all application sources — COBOL, PL/I, Assembler, BMS, Java, and z/OS Connect APIs
  2. Packages the build outputs into a deployment archive
  3. Runs Wazi Deploy to deploy the archive to the CICS and IMS environments
  4. Populates Db2 with application test data
  5. Populates the IMS database with application test data

The initial build and deployment typically take approximately 15 to 20 minutes.

5. Incremental Builds

After the initial deployment is complete, most day-to-day development can be performed using an incremental build and deploy rather than re-running the full environment provisioning.

The incremental workflow rebuilds and deploys only the application components affected by your source code changes, significantly reducing build time while preserving the existing runtime environment.
