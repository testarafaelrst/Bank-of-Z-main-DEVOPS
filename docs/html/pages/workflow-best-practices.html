Development Best Practices

This page documents the recommended practices for IBM Z development with Bank of Z. It covers branching strategies, incremental change management, build validation, team collaboration, and workflow selection — providing a foundation for consistent, efficient, and maintainable development across the team.

1. Overview

Developing on IBM Z requires disciplined practices to manage source code safely, validate changes quickly, and collaborate effectively across teams. Bank of Z development follows a set of core principles: isolate changes in branches, validate early and often, keep changes small and focused, and select the right workflow tool for each task.

Whether working with COBOL programs, copybooks, BMS maps, z/OS Connect artifacts, or web application components, these practices apply consistently across all source types. Adopting them reduces risk, accelerates feedback, and keeps the codebase stable and well-understood.

2. System Architecture

The Bank of Z development environment integrates a local developer workspace with z/OS hosted resources and a version-controlled source pipeline. The diagram below illustrates the high-level architecture of this development system and how components relate to each other.

graph TD A[Developer Workstation] -->|Edit Source| B[Local Workspace / IDE] B -->|Commit & Push| C[Source Control Repository] C -->|Branch Trigger| D[CI/CD Pipeline] D -->|Build & Compile| E[z/OS Build Environment] E -->|Deploy| F[z/OS Runtime Environment] F -->|CICS / IMS / DB2| G[Application Under Test] G -->|Test Results & Logs| A B -->|Zowe CLI Workflow| E B -->|GRUB Workflow| E subgraph z/OS Platform E F G end subgraph Developer Side A B end subgraph Version Control C D end

This architecture separates concerns clearly: source changes originate on the developer workstation, flow through version control and a pipeline, and land on the z/OS platform for compilation, deployment, and testing. Two supported paths exist for reaching z/OS — the Zowe CLI workflow for branch-based, version-controlled development, and the GRUB workflow for rapid local testing without a prior commit.

3. Branching Strategy

3.1 Work in Isolated Branches

Create a dedicated branch for each feature, enhancement, or defect fix. Isolating changes in branches makes it easier to review, test, and manage updates before they are merged into the main code line.

Recommended branch naming conventions:

Branch Type Naming Pattern Example
Feature feature/<short-desc> feature/add-account-view
Bug Fix fix/<issue-or-desc> fix/balance-calc-error
Enhancement enhance/<short-desc> enhance/cics-map-refresh
Hotfix hotfix/<desc> hotfix/db2-timeout-patch

The following diagram illustrates the recommended branching flow:

graph TD MAIN[main branch] -->|branch off| FEAT[feature/my-change] MAIN -->|branch off| FIX[fix/defect-123] FEAT -->|develop & validate| FEAT_TEST[Build + Test on z/OS] FIX -->|develop & validate| FIX_TEST[Build + Test on z/OS] FEAT_TEST -->|Pull Request / Review| MERGE1[Merge to main] FIX_TEST -->|Pull Request / Review| MERGE2[Merge to main] MERGE1 --> MAIN2[Updated main branch] MERGE2 --> MAIN2

Each branch lifecycle follows: branch → develop → build → test → review → merge. No code bypasses review or validation before reaching the main code line.

3.2 Synchronize Regularly

Keep your local workspace synchronized with the latest project changes to reduce merge conflicts and ensure that development is based on the most current source. Pull from the main branch frequently, especially before starting a new task or when a long-running branch is in progress.

4. Workspace Configuration

4.1 Keep Your Workspace Configuration Up to Date

Review your setup configuration before starting development activities. Ensure that paths, environment settings, and required dependencies match your target environment.

Key configuration items to verify before beginning development:

  • z/OS target environment — hostname, port, and HLQ (High-Level Qualifier) for your datasets
  • Zowe CLI profiles — ensure profiles reference the correct z/OSMF, SSH, and TSO endpoints
  • Dependency paths — copybooks, BMS maps, and include libraries must be correctly referenced
  • Environment variables — confirm any local overrides align with the target environment

If configuration values change, update your local environment before running setup or deployment tasks to avoid deploying with stale or mismatched settings.

5. Incremental Development

5.1 Make Small, Incremental Changes

Implement and validate changes in small increments rather than making large updates at once. Smaller changes are easier to test, troubleshoot, and review.

Why incremental changes matter on z/OS:

  • Compilation errors are isolated to a narrow changeset
  • Rollback is straightforward if a problem is detected
  • Code reviewers can provide more meaningful feedback
  • Integration risk is minimized at merge time

5.2 Validate Changes Frequently

Run the appropriate setup and deployment workflow after making changes to verify that updates build and deploy successfully. Early validation helps identify issues before they affect additional development work.

The sequence below shows the recommended validation loop within a single development iteration:

sequenceDiagram participant Dev as Developer participant WS as Local Workspace participant zOS as z/OS Build & Deploy participant Log as Build Logs Dev->>WS: Edit COBOL / Copybook / BMS Source Dev->>zOS: Trigger Build Workflow (Zowe CLI or GRUB) zOS->>zOS: Compile & Link-Edit zOS->>Log: Emit Build Output & Diagnostics Log-->>Dev: Review Warnings / Errors alt Build Successful zOS-->>Dev: Deploy to Test Region Dev->>zOS: Run Application Tests zOS-->>Dev: Test Results else Build Failed Dev->>WS: Correct Source Dev->>zOS: Re-trigger Build end

This tight loop — edit → build → review output → test — keeps problems small and resolvable before they compound.

6. Source Organization

6.1 Keep Source Changes Organized

Store application updates in the appropriate source directories and follow established project conventions. The Bank of Z project organizes source by artifact type:

Artifact Type Source Directory / Convention
COBOL Programs src/cobol/
Copybooks src/copy/
BMS Maps src/bms/
Web Application Sources src/web/
z/OS Connect Artifacts src/zosconnect/
JCL src/jcl/

Following directory conventions ensures that automated build pipelines can locate and process source files correctly without manual path overrides.

6.2 Document Significant Changes

Update relevant documentation when introducing new functionality, modifying configuration requirements, or changing development processes. Keeping documentation current helps other contributors understand and use your changes.

Examples of changes that require documentation updates:

  • New COBOL program or service endpoint introduced
  • Copybook structure modified (impacts all programs using it)
  • BMS map screen layout changed
  • z/OS Connect API definition updated
  • New environment variable or configuration parameter added

7. Build Output and Logging

7.1 Review Setup Output

Monitor workflow output and setup logs during development activities. Review any warnings or errors before proceeding to the next task.

Enterprise COBOL compiler output, for example, includes severity-coded diagnostics. Always review messages at W (Warning) level or above:

CODE 
IGY-compiled listing excerpt (example):
IGYPS2145-W  "COMPUTE" on line 00320: Possible data truncation detected.
IGYOP1094-E  "PERFORM" on line 00540: THRU phrase references undefined paragraph.

A clean build with zero errors and reviewed warnings is a prerequisite before promoting a branch to code review. Treat warnings as actionable — they frequently indicate logic errors or portability issues that will surface at runtime.

8. Workflow Selection

8.1 Use the Workflow That Matches Your Development Needs

Select the workflow that best supports your current task:

Workflow When to Use Key Characteristic
Zowe CLI Branch-based development with version-controlled changes Changes are committed before deployment
GRUB Rapid testing of local changes without committing them first Faster feedback; no commit required

Note: Selecting the appropriate workflow can improve development efficiency and reduce turnaround time during testing.

The diagram below compares the two workflow paths:

graph TD START[Developer Makes a Change] --> CHOICE{Workflow Selection} CHOICE -->|Version-controlled change| ZOWE[Zowe CLI Workflow] CHOICE -->|Rapid local test| GRUB[GRUB Workflow] ZOWE --> COMMIT[Commit & Push to Branch] COMMIT --> PIPELINE[CI/CD Pipeline Triggered] PIPELINE --> BUILD_Z[Build & Deploy on z/OS] GRUB --> DIRECT[Direct Deploy to z/OS\nNo Commit Required] DIRECT --> BUILD_G[Build & Deploy on z/OS] BUILD_Z --> TEST[Test & Validate] BUILD_G --> TEST TEST -->|Pass| REVIEW[Code Review / Merge] TEST -->|Fail| START

Use Zowe CLI as your primary workflow for work that will be retained in the repository. Reserve GRUB for exploratory or throw-away testing iterations where speed is the priority and a commit would be premature.

9. Team Collaboration

9.1 Code Review Standards

Every change targeting the main branch should pass through a structured code review. Reviews should evaluate:

  • Correctness — Does the logic meet the intended requirement?
  • COBOL standards — Are naming conventions, paragraph structure, and data definitions consistent with project norms?
  • Copybook impacts — Does a change to a shared copybook affect downstream programs?
  • Test coverage — Has the change been validated through appropriate test scenarios?

9.2 Collaboration Workflow Summary

The full team collaboration lifecycle — from task assignment through merge — is illustrated below:

sequenceDiagram participant TL as Team Lead participant Dev as Developer participant SCM as Source Control participant zOS as z/OS Platform participant Rev as Code Reviewer TL->>Dev: Assign Task (Feature / Fix) Dev->>SCM: Create Isolated Branch Dev->>Dev: Develop in Small Increments Dev->>zOS: Build & Validate Frequently zOS-->>Dev: Build Logs & Test Results Dev->>SCM: Commit & Push Changes Dev->>Rev: Open Pull Request Rev->>SCM: Review Code Rev-->>Dev: Feedback / Approval Dev->>SCM: Address Feedback & Update Branch Rev->>SCM: Approve SCM->>SCM: Merge to Main Branch TL->>Dev: Assign Next Task

This lifecycle ensures that all changes are reviewed, tested, and traceable before reaching the main code line — a critical discipline in mainframe environments where a single faulty deployment can affect production systems.
