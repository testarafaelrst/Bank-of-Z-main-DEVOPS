Repository Structure

The Bank of Z repository is a self-contained monorepo that bundles everything needed to build, deploy, and operate a full-stack mainframe banking application on z/OS. It organises application source code, middleware provisioning automation, build and deployment tooling, IDE integration, and product documentation under a single root, making it straightforward to clone once and have every asset available in one place.

1. Overview

Bank of Z is a reference banking application that runs on IBM z/OS, exercising CICS, IMS, Db2, and z/OS Connect as its middleware stack. The repository is structured so that:

  • Application source (src/) holds all COBOL programs, BMS maps, IMS artefacts, the z/OS Connect API project, and a browser-based frontend.
  • Setup automation (.setup/) contains every script, configuration file, and asset needed to provision middleware, compile the application with IBM Dependency Based Build (DBB), and deploy it with Wazi Deploy.
  • Supporting directories (.vscode/, scripts/, docs/, zcodescan/) cover IDE integration, extension management, documentation, and static analysis configuration.
  • Root manifest files (dbb-app.yaml, zapp.yaml) describe the application to the DBB and z/OS toolchains.

2. System Architecture

The Bank of Z system architecture spans a local developer workstation, the z/OS Unix System Services (USS) layer, and the z/OS middleware tier. The repository structure directly mirrors this three-tier model: scripts in .setup/ orchestrate the transition from local to remote, while src/ feeds artefacts into the z/OS runtime.

The setup automation chains three stages in sequence — validate-prereqs → environment → install-bank-of-z — before the application is available for use. Incremental pipeline runs (build + deploy) are handled separately by the pipeline scripts once the baseline is established.

4. Application Source (src/)

The src/ directory separates the application into distinct technology domains. Each sub-directory is built independently by the DBB build engine using the language scripts in .setup/build/.

4.1. CICS Path (src/base/cics/)

Contains all artefacts for the CICS online transaction path:

Sub-directory Contents
cobol/ COBOL programs (e.g., BNKMENU.cbl, CREACC.cbl, INQCUST.cbl, XFRFUN.cbl)
bms/ BMS map source (e.g., BNK1MAI.bms, BNK1CAM.bms)
copybooks/ Shared COBOL copybooks

During a full build, DBB processes the BMS maps first (language BMS), then compiles the COBOL programs (language Cobol), producing .MAPLOAD and .CICSLOAD members that are copied into BANKZ.V0R1M0.LOADLIB at deploy time.

4.2. IMS Path (src/base/ims/)

Contains artefacts for the IMS transaction path:

Sub-directory Contents
cobol/ COBOL programs (e.g., IBTRAN.cbl, LOADACCT.cbl, IBLOGIN1.cbl)
pli/ PL/I program (IBLOGIN.pli)
DBD/ Database Descriptor source in Assembler (e.g., CUSTOMER.asm, ACCOUNT.asm)
PSB/ Program Specification Block source in Assembler (e.g., IBTRAN.asm, IBLOGIN.asm)
copybooks/ Shared COBOL copybooks for IMS programs

4.3. Batch Components (src/base/batch/)

Holds batch application components that operate against the same Db2 tables used by the online paths.

4.4. z/OS Connect API (src/api/)

A Gradle-based project that produces the api.war deployment artefact. The OpenAPI specification (openapi.yaml) defines the REST surface exposed by the bankzServer z/OS Connect instance. DBB handles this via the zOSConnect task in the build lifecycle.

4.5. Browser Frontend (src/frontend/)

Static web assets (HTML, CSS, JavaScript) and a Node.js development server. The build task VanillaFrontend packages these into bank-frontend-vanilla.war, which is deployed alongside api.war to the z/OS Connect server.

5. Setup Automation (.setup/)

The .setup/ directory is the operational core of the repository. It contains every script, configuration, and asset needed to go from a bare z/OS system to a fully running Bank of Z environment.

5.1. Orchestration Scripts

The five orchestration scripts follow a clear local/remote split. Local scripts run on the developer’s workstation and use Zowe CLI to drive their remote counterparts; remote scripts run directly on z/OS USS.

sequenceDiagram participant DEV as Developer (Local) participant LOCAL as setup-local.sh (Local) participant REMOTE as setup-remote.sh (USS) participant COMMON as setup-common.sh (USS) DEV->>LOCAL: Run via VS Code Task LOCAL->>LOCAL: Create USS workspace (Zowe CLI) LOCAL->>LOCAL: Clone repository on USS (Zowe CLI) LOCAL->>REMOTE: Invoke via Zowe CLI SSH REMOTE->>COMMON: validate-prereqs COMMON-->>REMOTE: Prerequisites OK REMOTE->>COMMON: environment COMMON-->>REMOTE: Db2, CICS, IMS, z/OS Connect provisioned REMOTE->>COMMON: install-bank-of-z COMMON-->>REMOTE: Build + Deploy complete REMOTE-->>LOCAL: Setup complete LOCAL-->>DEV: Environment ready
Script Runs On Description
setup-local.sh Local machine Creates the USS workspace, clones the repository, invokes setup-remote.sh via Zowe CLI. Used by the VS Code task workflow.
setup-remote.sh z/OS USS Chains the three setup stages in sequence. Used by both the Zowe CLI and GRUB workflows.
setup-common.sh z/OS USS Implements the three stages: validate-prereqs, environment, and install-bank-of-z.
pipeline-local.sh Local machine Uploads pipeline assets and invokes pipeline-remote.sh via Zowe CLI. Used for incremental builds.
pipeline-remote.sh z/OS USS Runs the DBB build and Wazi Deploy. Used by both workflows for incremental builds.

The three setup stages exposed by setup-common.sh can also be called individually from a direct USS terminal session:

BASH 
# Stage 1 – validate all prerequisites (DBB, ZOAU, zconfig, Wazi Deploy)
.setup/setup-common.sh validate-prereqs

# Stage 2 – provision middleware (Db2 tables, CICS region, z/OS Connect server)
.setup/setup-common.sh environment

# Stage 3 – build and deploy the Bank of Z baseline
.setup/setup-common.sh install-bank-of-z

The central config.yaml controls the most commonly changed parameters. A minimal excerpt looks like this:

YAML 
# Workspace location on z/OS USS
sandbox:
  path: /usr/local/sandboxes/bank-of-z

# Application identity
app:
  base_name: BANKZ    # Dataset prefix (max 8 chars)
  short_name: BOZ     # Short identifier (max 4 chars)
  zos_version: V0R1M0 # Version for dataset naming

# DBB configuration
dbb:
  dbb_home: /usr/lpp/IBM/dbb
  java_home: /usr/lpp/java/java21/current_64

6. IDE Extension Scripts (scripts/)

The scripts/ directory provides three Node.js utilities for managing the IDE extensions required to work with Bank of Z source code.

Script Description
download-vsix.js Downloads all required IDE extension VSIX packages from IBM artifact repositories
install-bobide-vsix.js Installs the downloaded VSIX packages into IBM Bob Premium Package for Z
install-vscode-vsix.js Installs the downloaded VSIX packages into VS Code

Usage instructions are maintained in scripts/README.md. These scripts are independent of the setup automation and can be run at any time to refresh extension versions.

7. Documentation (docs/)

Product documentation is maintained in the docs/ directory alongside the application source, ensuring documentation stays in sync with code changes. Key sections include:

  • Architecture — Bank of Z solution design and component relationships
  • Installation and Setup — Step-by-step deployment guides
  • Reference — This repository structure document and related reference material

8. Static Analysis Configuration (zcodescan/)

The zcodescan/ directory holds ZCodeScan configuration and rules (zcodescan-rules.yaml) used during the static analysis stage of the pipeline simulation. The ZCodeScan licence server connection is configured separately in a zcs_config_file.yml placed in the user’s home directory, using ISO8859-1 encoding:

YAML 
license_server:
  url: https://127.0.0.1:8195
  user: IBMUSER
  password: MY_PASSWORD
  verify: false

The password is encrypted automatically after the first successful scan.

9. Application Manifests

Two YAML files at the repository root bind the application to the IBM z/OS toolchain:

File Purpose
dbb-app.yaml IBM Dependency Based Build application descriptor. Tells DBB which source directories to scan, how to resolve dependencies, and which language scripts to invoke.
zapp.yaml z/OS application manifest. Provides application identity and metadata consumed by IBM Z Open Editor and related tooling.

10. USS Workspace Layout (Post-Setup)

After a successful install-bank-of-z run, the configured sandbox directory on USS contains the following runtime layout. This is distinct from the repository layout but is produced entirely by the assets within it.

CODE 
/usr/local/sandboxes/bank-of-z/      ← sandbox.path in config.yaml
├── Bank-of-Z/                        ← cloned repository
│   ├── src/
│   ├── .setup/
│   ├── dbb-app.yaml
│   └── zapp.yaml
├── dbb/                              ← DBB accelerators (cloned from GitHub)
│   ├── Pipeline/
│   └── Build/
├── zBuilder/                         ← build framework (copied from .setup/build/)
│   ├── languages/
│   └── datasets.yaml
├── zosconnect-server/                ← z/OS Connect server instance
│   └── servers/bankzServer/
│       └── apps/
│           ├── api.war
│           └── bank-frontend-vanilla.war
└── logs/                             ← build and deploy output
    ├── dbb/
    │   ├── BuildReport.json
    │   └── BANKZ-<timestamp>.tar
    └── deploy/
        ├── deploymentPlan-bankz.yaml
        └── evidences/

The build produces a timestamped TAR package (e.g., BANKZ-20260603.114759.608.tar) that Wazi Deploy consumes to drive all subsequent copy, bind, NEWCOPY, and WAR-deployment operations.
