Key Capabilities

Bank of Z demonstrates a powerful combination of banking functionality and modern IBM Z development practices. This page provides an overview of the core capabilities delivered by the platform, covering supported development tools, build automation, deployment pipelines, application modernization features, and enterprise integration across key IBM Z technologies.

1. Overview

Bank of Z is a reference banking application built on IBM Z that showcases how modern development workflows can be applied to traditional mainframe environments. It supports a full suite of common banking operations while simultaneously serving as a demonstration platform for IBM Z best practices — from source management with Git to automated build and deployment pipelines.

The application is designed to be both functionally representative of a real-world banking system and technically instructive for development teams looking to modernize their IBM Z practices. It integrates multiple IBM Z middleware technologies under a single, cohesive architecture, enabling hybrid transaction processing, enterprise-grade data management, and seamless connectivity.

2. System Architecture

Bank of Z is built on a hybrid architecture that combines CICS, IMS Transaction Manager (IMS TM), Db2 for z/OS, IMS DB, IBM MQ, and z/OS Connect into a unified platform. The user interface layer routes requests to either the CICS or IMS-based backend implementation while maintaining a consistent experience for end users.

The diagram below illustrates the high-level system architecture and how the major components relate to one another:

graph TD UI[User Interface / Client] --> ZC[z/OS Connect] ZC --> CICS[CICS Transaction Manager] ZC --> IMS_TM[IMS Transaction Manager] CICS --> DB2[Db2 for z/OS] CICS --> MQ[IBM MQ] IMS_TM --> IMS_DB[IMS DB] IMS_TM --> MQ DB2 --> DATA[(Banking Data)] IMS_DB --> DATA subgraph IBM Z Platform ZC CICS IMS_TM DB2 IMS_DB MQ end

This architecture ensures that both CICS and IMS transaction paths share a common data layer and messaging backbone, enabling consistent banking operations regardless of which runtime processes a given request.

3. Banking Operations

Bank of Z supports the core set of operations found in a typical retail banking system. These operations exercise the full stack of the application — from the user interface through the middleware layers down to the persistent data stores.

Supported banking operations include:

Operation Description
Account Management Create, retrieve, and update customer account records
Customer Management Manage customer profiles and associated account relationships
Deposits & Withdrawals Process credit and debit transactions against accounts
Funds Transfers Move funds between accounts within the system
Transaction History Query and process historical transaction records

The following sequence diagram illustrates a typical funds transfer flow through the system:

sequenceDiagram participant Client as Client / UI participant ZC as z/OS Connect participant CICS as CICS Program participant DB2 as Db2 for z/OS participant MQ as IBM MQ Client->>ZC: POST /transfer { from, to, amount } ZC->>CICS: Invoke Transfer Transaction CICS->>DB2: Debit source account DB2-->>CICS: Confirmation CICS->>DB2: Credit target account DB2-->>CICS: Confirmation CICS->>MQ: Publish transaction event MQ-->>CICS: Acknowledgement CICS-->>ZC: Transfer result ZC-->>Client: HTTP 200 OK { transactionId }

This flow demonstrates how a single banking operation traverses multiple IBM Z middleware components in a coordinated, transactional manner.

4. Hybrid Transaction Processing

4.1 Dual-Runtime Architecture

One of the defining characteristics of Bank of Z is its hybrid transaction processing model. The application integrates both CICS and IMS Transaction Manager (IMS TM) as backend runtimes, allowing teams to compare and contrast the two dominant IBM Z transaction processing environments side by side.

The user interface layer determines whether an incoming request is routed to the CICS or IMS-based implementation. Despite this routing, the end user receives a consistent experience — the same banking operations are available regardless of which runtime handles the request.

graph LR UI[User Interface] --> Router{Transaction Router} Router -->|CICS Path| CICS_PGM[CICS Program] Router -->|IMS Path| IMS_PGM[IMS TM Program] CICS_PGM --> DB2[(Db2 for z/OS)] IMS_PGM --> IMS_DB[(IMS DB)] CICS_PGM --> MQ[IBM MQ] IMS_PGM --> MQ

4.2 Benefits of the Hybrid Model

  • Flexibility: Teams can choose the runtime that best suits their operational requirements.
  • Comparison: Developers can observe equivalent functionality implemented in both CICS and IMS environments.
  • Resilience: The dual-runtime design provides architectural diversity within a single application.

5. Modern Development Workflows

5.1 Source Management

Bank of Z uses Git-based source management, bringing mainframe development in line with modern DevOps practices. Developers work with familiar branching and merging workflows, enabling collaborative development and full version history for all z/OS artifacts.

5.2 Integrated Development Environments

The project supports multiple IDE experiences:

  • VS Code — Developers can write, edit, and navigate COBOL, PL/I, and other z/OS source files directly within VS Code using IBM Z extensions.
  • GRUB — An alternative development workflow for teams that prefer a browser-based or alternative toolchain experience.

5.3 Dependency Based Build (DBB)

Bank of Z uses IBM Dependency Based Build (DBB) to manage the compilation and linking of z/OS programs. DBB understands the relationships between source files and only rebuilds artifacts that have changed or are impacted by a change — reducing build times and improving reliability.

A sample DBB build script invocation might look like:

GROOVY 
// DBB Build Script Example
@groovy.transform.BaseScript com.ibm.dbb.groovy.ScriptLoader baseScript

def file = "BankingTransfer.cbl"
def buildFile = new File(file)

TaskFactory.create("COBOL", buildFile)
    .addProperty("deployType", "LOAD")
    .addProperty("copybooks", "BANK.COPYLIB")
    .run()

5.4 Bob and zBuilder Integration

In addition to DBB, Bank of Z integrates with Bob (Build on Demand) and zBuilder, providing flexible options for build orchestration. These tools complement DBB by enabling higher-level build pipeline definitions and integration with CI/CD toolchains.

5.5 Automated Build and Deployment Pipelines

The project demonstrates end-to-end pipeline automation, covering:

  1. Source checkout from Git
  2. Dependency analysis via DBB
  3. Compilation and linking of z/OS programs
  4. Package creation for deployment artifacts
  5. Deployment to target z/OS environments
  6. Automated testing and validation
graph LR A[Git Push / PR] --> B[Pipeline Trigger] B --> C[DBB Dependency Analysis] C --> D[Compile & Link] D --> E[Package Artifacts] E --> F[Deploy to z/OS] F --> G[Automated Tests] G --> H{Pass?} H -->|Yes| I[Promote to Production] H -->|No| J[Notify Developer]

This pipeline ensures that every code change is validated automatically before reaching a production environment, reducing risk and accelerating delivery.

6. Enterprise Integration

Bank of Z demonstrates deep integration across the IBM Z middleware stack. The table below summarizes the key technologies and their roles within the application:

Technology Role in Bank of Z
z/OS Connect Exposes banking transactions as RESTful APIs, enabling integration with web and mobile clients
CICS Provides one of the two transaction processing runtimes for banking operations
IMS TM Provides the alternative transaction processing runtime for banking operations
Db2 for z/OS Relational database used by the CICS runtime for account and transaction data
IMS DB Hierarchical database used by the IMS TM runtime for account and transaction data
IBM MQ Messaging backbone for asynchronous event publishing and inter-component communication

6.1 z/OS Connect

z/OS Connect bridges the gap between modern API consumers (web, mobile, cloud) and IBM Z backend transactions. Bank of Z uses z/OS Connect to expose CICS and IMS transactions as standard RESTful endpoints, enabling the user interface to communicate with the backend using HTTP/JSON without requiring knowledge of the underlying transaction protocols.

A typical z/OS Connect API definition excerpt might look like:

JSON 
{
  "swagger": "2.0",
  "info": {
    "title": "Bank of Z - Account API",
    "version": "1.0.0"
  },
  "paths": {
    "/accounts/{accountId}": {
      "get": {
        "summary": "Retrieve account details",
        "parameters": [
          {
            "name": "accountId",
            "in": "path",
            "required": true,
            "type": "string"
          }
        ],
        "responses": {
          "200": {
            "description": "Account details retrieved successfully"
          }
        }
      }
    }
  }
}

6.2 IBM MQ

IBM MQ provides reliable, asynchronous messaging between components. In Bank of Z, MQ is used to publish transaction events — ensuring that operations such as deposits, withdrawals, and transfers are recorded and can be consumed by downstream systems (e.g., audit, notifications) without tight coupling between producers and consumers.

7. Summary

Bank of Z delivers a comprehensive demonstration of IBM Z capabilities across five key dimensions:

  1. Full-featured banking operations that exercise the complete application stack
  2. Hybrid transaction processing across both CICS and IMS TM runtimes
  3. Modern development workflows using Git, VS Code, GRUB, DBB, Bob, and zBuilder
  4. Automated CI/CD pipelines for build, deployment, and testing
  5. Enterprise integration across z/OS Connect, CICS, IMS, Db2, IMS DB, and IBM MQ

Together, these capabilities make Bank of Z a practical, real-world reference for teams looking to adopt modern development practices on IBM Z while maintaining the reliability and performance characteristics that mainframe environments are known for.
