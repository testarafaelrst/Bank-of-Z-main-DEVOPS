Application Components

Bank of Z is a hybrid IBM Z banking application that integrates modern web technologies with enterprise transaction-processing systems. This page provides a detailed breakdown of every component in the Bank of Z application — from the browser-based user interface through to the backend databases, messaging infrastructure, and external systems — explaining what each component does, how it fits into the overall architecture, and how components relate to one another.

1. Overview

Bank of Z delivers a unified banking experience by combining a browser-based front end with IBM Z transaction-processing technologies. Users interact with a single web application to manage customers, accounts, and transactions, while all heavy lifting is performed by CICS or IMS TM on the backend. Data is persisted in Db2 for z/OS and IMS databases, asynchronous integration is handled by IBM MQ, and the entire stack is exposed through z/OS Connect REST APIs.

The architecture is intentionally hybrid: it demonstrates how a single modern banking application can simultaneously leverage CICS transaction processing, IMS Transaction Manager, relational and hierarchical databases, and message-based integration — all within an IBM Z environment and all presented to the end user through a single, consistent interface.

Key capabilities delivered by the application:

  • Customer management — create, update, and retrieve customer records
  • Account management — open, manage, and close bank accounts
  • Transaction processing — post debits, credits, and transfers
  • Account history — query historical transaction data
  • Inter-bank messaging — exchange payment messages with external systems via IBM MQ

The front end communicates exclusively with z/OS Connect, which acts as the API gateway. z/OS Connect routes each request to either the CICS or IMS TM processing path. Both paths share access to the Money and Account Management Db2 database, while CICS additionally owns the Account History Db2 database. The IMS path uses an IMS hierarchical database for its primary data store. IBM MQ decouples Bank of Z from the external Bank of Q system.

3. Application Components

3.1 Bank of Z UI

The Bank of Z user interface is a browser-based single-page application (SPA) that provides the primary entry point for all banking operations. It allows bank operators and customers to:

  • Search and manage customer records
  • Open, view, and close accounts
  • Post and review transactions
  • Initiate inter-bank money transfers

The UI communicates exclusively through REST APIs exposed by z/OS Connect, making it completely decoupled from the backend transaction-processing technologies. This means the same UI can target either the CICS or IMS processing path without any change in the user experience.

CODE 
Bank of Z UI  ──REST──▶  z/OS Connect  ──▶  CICS / IMS TM

3.2 z/OS Connect

z/OS Connect is the API integration layer that bridges the browser-based UI with the IBM Z backend systems. It exposes RESTful endpoints that the UI calls, and it translates those API calls into native CICS or IMS TM transactions.

Responsibilities:

  • Hosting and versioning REST API definitions
  • Routing requests to the correct backend transaction-processing system
  • Handling authentication and authorization at the API boundary
  • Transforming JSON payloads to and from CICS/IMS data formats

z/OS Connect is central to the hybrid architecture — it is the single point through which all front-end traffic enters the IBM Z environment, and it provides the clean separation between the modern API layer and the enterprise transaction-processing layer.

3.3 CICS Transaction Processing

CICS (Customer Information Control System) is one of the two primary transaction-processing engines in Bank of Z. It handles the CICS processing path for all core banking functions.

3.3.1 Role in the Architecture

When z/OS Connect routes a request down the CICS path, CICS executes the corresponding COBOL or PL/I program, which reads and writes data in Db2 for z/OS. CICS manages:

  • Transaction lifecycle (begin, commit, rollback)
  • Program-to-program linking
  • Terminal and API communication sessions
  • Resource recovery and error handling

3.3.2 Banking Functions Handled by CICS

Function Description
Customer management Create, read, update, and delete customer records
Account management Open, modify, and close bank accounts
Transaction posting Debit and credit operations against accounts
Balance enquiry Real-time balance lookups
Account history Retrieval of historical transaction data
Inter-bank transfer Initiation of MQ-based transfer messages

3.4 IMS Transaction Manager (IMS TM)

IMS Transaction Manager is the second transaction-processing engine. It provides an alternative processing path for banking operations, demonstrating how IBM Z applications can support multiple transaction-processing technologies within a single solution.

3.4.1 Role in the Architecture

When z/OS Connect routes a request down the IMS path, IMS TM schedules and executes the corresponding application program. IMS TM manages:

  • Message queuing and scheduling for transactions
  • Application program execution
  • Access to IMS hierarchical databases
  • Shared access to the Db2 Money and Account Management database

3.4.2 IMS TM Processing Flow

3.5 Databases

Bank of Z uses three distinct databases, each serving a specific purpose within the application.

3.5.1 Money and Account Management Db2 Database

This is the primary relational database for the CICS processing path and is also shared by IMS-based transactions. It stores:

  • Customer master records
  • Account records (current accounts, savings accounts)
  • Pending and posted transaction records

Both CICS and IMS TM programs access this database, making it the central shared data store across both processing paths. Db2 for z/OS provides full ACID transaction semantics, ensuring data consistency regardless of which path posted the change.

Example embedded SQL used by CICS programs to query account data:

COBOL 
EXEC SQL
    SELECT ACCT_ID, ACCT_BALANCE, ACCT_TYPE
    INTO  :WS-ACCT-ID, :WS-BALANCE, :WS-TYPE
    FROM   ACCOUNT
    WHERE  ACCT_ID = :WS-INPUT-ACCT-ID
END-EXEC.

3.5.2 Account History Db2 Database

This Db2 database stores historical account and transaction records for inquiry and reporting purposes. It is written to by CICS programs every time a transaction is posted, capturing a full audit trail. Functions supported include:

  • Transaction history retrieval by account
  • Date-range filtering of posted transactions
  • Balance history snapshots

3.5.3 Money and Account Management IMS Database

The IMS database is the primary data store for the IMS TM processing path. It is a hierarchical database accessed using DL/I calls. Application programs issue GU (Get Unique) and GN (Get Next) calls to traverse the hierarchy and retrieve or update account and customer data.

Example DL/I call structure used in IMS application programs:

COBOL 
CALL 'CBLTDLI' USING DLI-GU
                     PCB-MASK
                     IO-AREA
                     UNQUAL-SSA.

3.6 IBM MQ

IBM MQ provides reliable, asynchronous messaging capabilities for Bank of Z. It decouples the Bank of Z application from external systems, ensuring that messages are delivered even if the receiving system is temporarily unavailable.

3.6.1 Role in the Architecture

IBM MQ is used primarily for inter-bank communication scenarios, such as money transfers between Bank of Z and the external Bank of Q system. CICS programs put messages onto MQ queues, and those messages are consumed by Bank of Q (and vice versa).

3.6.2 MQ Message Flow

sequenceDiagram participant CICS as CICS Program participant MQ as IBM MQ participant BANKQ as Bank of Q CICS->>MQ: MQPUT (Transfer Request) MQ-->>BANKQ: Message Delivered BANKQ->>MQ: MQPUT (Transfer Confirmation) MQ-->>CICS: Message Available CICS->>MQ: MQGET (Read Confirmation)

Key MQ capabilities used by Bank of Z:

  • Persistent messaging — messages survive MQ restarts
  • Queue-based decoupling — sender and receiver operate independently
  • Transactional PUT/GET — MQ operations participate in CICS unit-of-work

3.7 Bank of Q

Bank of Q is an external banking system that communicates with Bank of Z through IBM MQ. It represents a peer institution and is used to demonstrate inter-application communication scenarios, specifically cross-bank money transfers.

Bank of Q:

  • Receives transfer requests placed by Bank of Z onto an MQ queue
  • Processes the transfer and posts a confirmation message back to a reply queue
  • May also initiate inbound transfer requests that Bank of Z processes

This component illustrates how IBM MQ enables loosely coupled, reliable communication between independent banking applications, a pattern common in real-world financial services integrations.
