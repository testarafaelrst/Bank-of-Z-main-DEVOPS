1. Application Flow

The Bank of Z application employs a modern hybrid architecture that bridges browser-based user interfaces with core IBM Z transaction-processing environments. Banking operations initiated by end users are dynamically routed to either CICS or IMS Transaction Manager (IMS TM) based on the customer identifier format, providing seamless data retrieval and updates across mainframe databases.

1. Overview

Bank of Z delivers unified retail banking functionality by coordinating front-end digital experiences with enterprise transaction engines on z/OS. The platform enables users to query accounts, execute transactions, and process incoming funds transfers across multiple underlying subsystems without exposing backend complexity to the client.

Key architectural characteristics include:

  • Dual Transaction Engines: Supports parallel workloads across CICS and IMS TM.
  • API-Driven Integration: Exposes core z/OS transactional assets as RESTful services through z/OS Connect.
  • Identifier-Based Routing: Dispatches banking operations dynamically using structured customer ID prefixes.
  • Asynchronous Messaging: Leverages IBM MQ for external transaction exchange and third-party fund transfers.

2.1. Component Breakdown

  • Bank of Z UI: Modern single-page web interface where users log in, inspect account balances, and execute banking transfers.
  • z/OS Connect: Enterprise REST API gateway transforming HTTP/JSON payloads into binary payloads consumed by CICS programs and IMS transactions.
  • CICS Transaction Server: Hosts core banking business logic for accounts identified by the Cnnnn pattern, executing relational queries against Db2.
  • IMS Transaction Manager (IMS TM): Processes high-volume transaction workloads for accounts matching the Innn pattern, directly accessing IMS DB hierarchical databases.
  • IBM MQ: Enterprise messaging backbone managing asynchronous transfer requests arriving from external financial institutions.

3.1. Detailed Step-by-Step Execution

  1. User Action: The customer submits a banking request (e.g., account inquiry, balance lookup, fund transfer) via the web interface.
  2. Client-Side Route Evaluation: The UI inspects the customer identifier to evaluate whether the target service resides in CICS or IMS.
  3. API Dispatch: The UI sends an HTTP REST request containing JSON payload to z/OS Connect.
  4. Subsystem Routing: z/OS Connect handles JSON-to-byte transformation and dispatches the payload to the appropriate subsystem (CICS or IMS TM).
  5. Business Logic Execution: CICS programs or IMS TM message-processing programs execute the requested transactional logic.
  6. Data Persistence:
    • CICS transactions query or update relational tables residing in Db2 for z/OS.
    • IMS TM transactions interact with hierarchical records stored in the IMS Database.
  7. Response Transformation: The backend payload is serialized into a standard JSON response by z/OS Connect and returned via HTTP.
  8. UI Presentation: The Bank of Z UI parses the JSON payload and updates the client interface.

4. Routing Logic and Rules

Bank of Z routes incoming requests to the designated transaction engine by applying pattern-matching rules to the customer identifier.

Customer Identifier Pattern Processing Environment Data Backend Example Identifier
Cnnnn CICS IBM Db2 C1234, C5678
Innn / Innnn IMS TM IMS Database (DL/I) I1234, I056

4.1. Routing Decision Logic

The front-end and z/OS Connect routing layer determine the transaction path according to the customer ID structure:

JSON 
{
  "routingRules": [
    {
      "prefix": "C",
      "targetSystem": "CICS",
      "targetDatabase": "Db2",
      "protocol": "IPIC / REST",
      "description": "Routes all C-prefixed accounts to CICS regions"
    },
    {
      "prefix": "I",
      "targetSystem": "IMS_TM",
      "targetDatabase": "IMS_DB",
      "protocol": "OTMA / REST",
      "description": "Routes all I-prefixed accounts to IMS Transaction Manager"
    }
  ]
}

This model allows financial institutions to run heterogeneous core banking workloads concurrently while preserving a uniform digital banking interface.

6. External Integration via IBM MQ

In addition to interactive web transactions, Bank of Z interacts with external banking systems using IBM MQ. This infrastructure supports asynchronous financial exchanges, such as processing inbound money transfers.

6.1. Inbound Transfer Message Payload Example

External systems publish inbound wire and payment messages to the designated input queue:

JSON 
{
  "transactionId": "TXN-98472019-Z",
  "sourceBank": "EXT-FINANCIAL-CORP",
  "sourceAccount": "994827110",
  "targetCustomerId": "C1234",
  "targetAccount": "000102938471",
  "transferAmount": 2500.00,
  "currency": "USD",
  "timestamp": "2025-01-15T14:32:00Z"
}

When an external money transfer is consumed:

  1. IBM MQ delivers the message to the queue listener.
  2. The payload is inspected to determine the destination customer account (C1234 for CICS/Db2 or I1234 for IMS TM/IMS DB).
  3. The transaction is processed atomically against the database.
  4. An acknowledgment message is placed onto the reply queue to confirm settlement.
