Application Flow

Bank of Z is a hybrid banking application that seamlessly unifies a modern browser-based UI with the transaction-processing power of IBM Z. This page documents the end-to-end lifecycle of a banking request — from the moment a user interacts with the web interface, through routing, transaction execution on CICS or IMS Transaction Manager (IMS TM), database access, and response delivery — including asynchronous integration with external systems via IBM MQ.

1. Overview

Bank of Z routes banking operations to one of two IBM Z transaction-processing environments — CICS or IMS TM — depending on the format of the customer identifier supplied with each request. The application layer abstracts this complexity entirely from the end user, who experiences a single, consistent web interface regardless of which back-end system processes their request.

Key design principles of the application flow:

  • Identifier-based routing: Customer IDs beginning with C are directed to CICS; IDs beginning with I are directed to IMS TM.
  • REST gateway: All requests pass through z/OS Connect, which translates REST/JSON calls into native CICS or IMS TM transactions.
  • Structured data handoff: CICS programs exchange data internally using channels and containers, a flexible alternative to the legacy COMMAREA model.
  • Asynchronous external integration: External banking systems can submit inbound requests (e.g., money transfers) through IBM MQ, decoupling external partners from the synchronous transaction path.

2. System Architecture

The Bank of Z architecture spans three tiers: a web front-end, a connectivity/gateway layer, and the IBM Z transaction-processing back-end.

3. Request Processing Flow

3.1 End-to-End Transaction Lifecycle

A standard banking request (e.g., account inquiry or fund transfer) follows this lifecycle:

  1. A user performs a banking operation through the Bank of Z web UI.
  2. The UI inspects the customer identifier to determine the transaction-processing path.
  3. The UI sends the request to z/OS Connect via a REST API call.
  4. z/OS Connect forwards the request to either the CICS or IMS TM environment.
  5. The target system executes the required business logic.
  6. Data is read from or written to Db2 (CICS path) or the IMS database (IMS TM path).
  7. The transaction result is returned through z/OS Connect to the web UI.
  8. The UI renders the result for the user.

3.2 Routing Logic

Bank of Z uses a simple but effective identifier-based routing scheme to direct requests to the correct transaction environment:

Customer Identifier Pattern Processing Environment Database
Cnnnn (e.g., C1234) CICS Db2 for z/OS
Innn (e.g., I1234) IMS Transaction Manager IMS Database

This routing model demonstrates how multiple IBM Z transaction-processing technologies can coexist in a single application while presenting a unified experience to the end user.

4. CICS Processing Path

4.1 Transaction Initiation

When a request is routed to CICS, z/OS Connect initiates the appropriate CICS transaction. CICS, acting as a service provider, receives the inbound request and dispatches the business logic program.

4.2 Channels and Containers: Data Handoff Between Programs

A key feature of the CICS processing path is the use of channels and containers to pass data between CICS programs — replacing the older, size-limited COMMAREA approach.

Containers are named blocks of data that can hold any form of application data in any format and any size (limited only by available storage). They are grouped into channels, which act as a structured parameter list passed between programs.

Key advantages of channels and containers over COMMAREA:

  • Not limited to the 32 KB COMMAREA size ceiling.
  • Programs do not need to know the exact size of returned data in advance.
  • A channel can contain multiple containers, enabling structured, modular data exchange.
  • Channels are automatically destroyed when they go out of scope.

Note: Channels and COMMAREAs are mutually exclusive — an EXEC CICS LINK, EXEC CICS XCTL, or EXEC CICS RETURN can only pass one or the other.

Example: Putting data into a container and linking to a business logic program (COBOL)

COBOL 
EXEC CICS PUT CONTAINER('REQUEST-DATA')
              CHANNEL('BANK-CHANNEL')
              FROM(WS-REQUEST-AREA)
              FLENGTH(LENGTH OF WS-REQUEST-AREA)
END-EXEC.

EXEC CICS LINK PROGRAM('BIZLOGIC')
               CHANNEL('BANK-CHANNEL')
END-EXEC.

Example: Getting data from a container in the called program (COBOL)

COBOL 
EXEC CICS GET CONTAINER('REQUEST-DATA')
              CHANNEL('BANK-CHANNEL')
              INTO(WS-REQUEST-AREA)
              FLENGTH(WS-DATA-LENGTH)
END-EXEC.

4.4 Database Access (Db2)

CICS business logic programs access Db2 for z/OS through embedded SQL statements. The CICS attachment facility manages the connection between the CICS region and the Db2 subsystem.

COBOL 
EXEC SQL
    SELECT ACCOUNT_BALANCE
    INTO   :WS-BALANCE
    FROM   ACCOUNTS
    WHERE  CUSTOMER_ID = :WS-CUSTOMER-ID
END-EXEC.

5. IMS TM Processing Path

5.1 Transaction Initiation

When a request is routed to IMS TM, z/OS Connect dispatches the corresponding IMS transaction. IMS TM receives the input message and schedules the application program for execution in a dependent region.

5.2 DL/I Database Access

IMS TM application programs access the IMS database using DL/I (Data Language/I) calls. The most common calls are:

  • GU (Get Unique) — retrieves a single segment by key.
  • GN (Get Next) — retrieves the next segment in sequence.
  • GNP (Get Next within Parent) — retrieves the next child segment within the current parent.
  • ISRT (Insert) — inserts a new segment.
  • DLET (Delete) — deletes a segment.
  • REPL (Replace) — updates a segment.

6. External Integration via IBM MQ

6.1 Overview

For selected operations — such as processing inbound money transfer requests from external banking systems — Bank of Z integrates with external partners through IBM MQ. This asynchronous model decouples external systems from the synchronous CICS/IMS TM transaction path, enabling reliable, guaranteed message delivery.

6.2 MQ Integration Architecture

graph TD EXT[External Banking System] -->|MQPUT - Places message on queue| MQ[IBM MQ Queue Manager] MQ -->|MQ Trigger - CPIL Transaction| CICS[CICS Transaction Server] MQ -->|OTMA / MQ-IMS Bridge| IMS[IMS Transaction Manager] CICS -->|Processes inbound transfer| DB2[(Db2 for z/OS)] IMS -->|Processes inbound transfer| IMSDB[(IMS Database)] CICS -->|MQPUT - Reply to ReplyToQ| MQ IMS -->|Reply written to ReplyToQ in MQMD| MQ MQ -->|Delivers response| EXT

6.3 MQ-to-IMS Bridge

The IBM MQ – IMS bridge allows external applications to initiate IMS transactions without needing to use the MQI directly inside the IMS application. The bridge uses OTMA (Open Transaction Manager Access), a transaction-based connectionless client/server protocol running over the z/OS Cross Systems Coupling Facility (XCF).

The flow is:

  1. An external system places a message (optionally with an MQIIH IMS Information Header) onto an IBM MQ queue.
  2. IBM MQ queues the message first (enabling syncpoint and data integrity), then routes it via OTMA to the IMS TM.
  3. IMS TM processes the transaction and writes the reply directly to the reply-to queue specified in the MQMD (Message Descriptor) of the original message.
sequenceDiagram participant EXT as External Banking System participant MQ as IBM MQ Queue Manager participant OTMA as OTMA / MQ-IMS Bridge participant IMS as IMS Transaction Manager participant IMSDB as IMS Database EXT->>MQ: MQPUT (message + MQIIH header) MQ->>MQ: Queue message (syncpoint assured) MQ->>OTMA: Route via XCF to IMS partner OTMA->>IMS: Submit IMS Transaction IMS->>IMSDB: DL/I Read / Write IMSDB-->>IMS: Segment Data IMS-->>MQ: Write reply to ReplyToQ (from MQMD) MQ-->>EXT: Deliver response

6.4 MQ-to-CICS (Trigger-Based)

IBM MQ can also trigger CICS transactions using MQ Triggering. When a message arrives on a monitored local queue, the Queue Manager generates a trigger message and sends it to an initiation queue. A CICS trigger monitor picks up this trigger message and starts the designated CICS transaction (e.g., CPIL) to process the waiting message.

sequenceDiagram participant EXT as External System participant LQ as MQ Local Queue participant IQ as MQ Initiation Queue participant TM as CICS Trigger Monitor participant CICS as CICS Transaction (CPIL) EXT->>LQ: MQPUT (inbound message) LQ->>IQ: Generate Trigger Message (first message rule) IQ->>TM: Trigger Monitor retrieves message TM->>CICS: Start CPIL Transaction CICS->>LQ: MQGET (retrieve application message) CICS->>CICS: Process banking operation CICS-->>EXT: Reply (via reply-to queue)

8. Summary

Bank of Z demonstrates how a single web application can provide a consistent banking experience while delegating transaction processing to multiple IBM Z back-end systems. The key integration patterns are:

Pattern Technology Purpose
REST API Gateway z/OS Connect Translates REST calls to CICS/IMS TM transactions
Identifier-based Routing Bank of Z UI Routes requests to CICS (C-prefix) or IMS TM (I-prefix)
Intra-program Data Handoff CICS Channels & Containers Structured, size-unlimited data passing between CICS programs
Relational Data Access Db2 for z/OS (via CICS) SQL-based reads and writes for CICS-path customers
Hierarchical Data Access IMS Database (via DL/I) DL/I calls for IMS-path customers
Asynchronous External Integration IBM MQ Decoupled, guaranteed-delivery integration with external banks
IMS Bridge IBM MQ OTMA / IMS Bridge Enables external MQ producers to invoke IMS transactions without code changes
CICS Trigger IBM MQ Triggering Automatically starts a CICS transaction when a message arrives on a queue
