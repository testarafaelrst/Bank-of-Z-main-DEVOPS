CRDTAGY2 – Credit Agency Simulator

1. Overview

CRDTAGY2 is a simulated credit agency program that operates asynchronously within a CICS environment. Its primary purpose is to assign a randomly generated credit score to a customer record delivered via a CICS channel and container. When invoked as an asynchronous child task by a parent orchestrator program, CRDTAGY2:

  1. Introduces a random delay of 1 to 3 seconds to emulate the response latency of a real external credit bureau.
  2. Generates a random credit score between 1 and 999 using the COBOL FUNCTION RANDOM, seeded with the current CICS task number (EIBTASKN).
  3. Writes the updated customer record — with the newly computed credit score — back to the originating CICS channel/container (CIPCREDCHANN/CIPB), making it available for the parent program to collect via a FETCH.

The deliberate latency simulation is architecturally significant: combined with the parent program’s 3-second timeout window, it creates a realistic 1-in-3 chance that the score will not be returned in time — intentionally modelling the imperfect reliability of real-world third-party credit agencies.

2. System Architecture

CRDTAGY2 operates as a child task within the CICS Asynchronous API model. It has no direct database access; all data exchange is performed exclusively through the CICS channel-and-container mechanism. The program depends on three external copybooks for its data structures and links to a centralised abend handler (ABNDPROC) on any error path.

3.2 Step-by-Step Execution Description

3.2.1 Step 1 — Initialisation (Paragraph A010)

The program’s entry point sets up the channel and container names and primes the COBOL random number generator:

COBOL 
MOVE 'CIPB            ' TO WS-CONTAINER-NAME
MOVE 'CIPCREDCHANN    ' TO WS-CHANNEL-NAME
MOVE EIBTASKN           TO WS-SEED

EIBTASKN — the current CICS task number from the Execute Interface Block — is used as the seed value so that each task invocation produces a unique and unpredictable sequence of random numbers.

3.2.2 Step 2 — Random Delay Calculation and Application

A random delay between 1 and 3 seconds is computed and applied using EXEC CICS DELAY:

COBOL 
COMPUTE WS-DELAY-AMT = ((3 - 1) * FUNCTION RANDOM(WS-SEED)) + 1

EXEC CICS DELAY
    FOR SECONDS(WS-DELAY-AMT)
    RESP(WS-CICS-RESP)
    RESP2(WS-CICS-RESP2)
END-EXEC

Since FUNCTION RANDOM returns a value in the range [0, 1), WS-DELAY-AMT is bounded to the interval [1, 3) seconds. The CICS DELAY command suspends the child task for this duration, freeing the CICS dispatcher to run other tasks in the meantime.

3.2.3 Step 3 — Customer Data Retrieval

After the delay, the customer record is read from the named container into working storage:

COBOL 
MOVE LENGTH OF WS-CONT-IN TO WS-CONTAINER-LEN

EXEC CICS GET CONTAINER(WS-CONTAINER-NAME)
    CHANNEL(WS-CHANNEL-NAME)
    INTO(WS-CONT-IN)
    FLENGTH(WS-CONTAINER-LEN)
    RESP(WS-CICS-RESP)
    RESP2(WS-CICS-RESP2)
END-EXEC

WS-CONT-IN is a copy of the CUSTOMER-RECORD structure defined in CUSTOMER.cpy. FLENGTH specifies the maximum number of bytes to retrieve, computed using the LENGTH OF special register to match the exact structural size of the data area.

3.2.4 Step 4 — Credit Score Generation

With the random generator already seeded in Step 2, a second call to FUNCTION RANDOM — this time without a seed argument — continues the same pseudo-random sequence to produce the credit score:

COBOL 
COMPUTE WS-NEW-CREDSCORE = ((999 - 1) * FUNCTION RANDOM) + 1

MOVE WS-NEW-CREDSCORE TO CUSTOMER-CREDIT-SCORE OF WS-CONT-IN

This maps the [0, 1) output of FUNCTION RANDOM to a credit score in the range 1 to 999, which is then written directly into the CUSTOMER-CREDIT-SCORE field of the in-memory customer record.

3.2.5 Step 5 — Write Updated Record Back to Container

The updated customer record — now containing the newly computed credit score — is written back to the same container, overwriting the previous content:

COBOL 
MOVE LENGTH OF WS-CONT-IN TO WS-CONTAINER-LEN

EXEC CICS PUT CONTAINER(WS-CONTAINER-NAME)
    FROM(WS-CONT-IN)
    FLENGTH(WS-CONTAINER-LEN)
    CHANNEL(WS-CHANNEL-NAME)
    RESP(WS-CICS-RESP)
    RESP2(WS-CICS-RESP2)
END-EXEC

3.2.6 Step 6 — Normal Termination

On the success path, control is passed to the GET-ME-OUT-OF-HERE section, which issues EXEC CICS RETURN to hand control back to CICS and signal task completion to the parent’s FETCH:

COBOL 
GET-ME-OUT-OF-HERE SECTION.
GMOFH010.
    EXEC CICS RETURN
    END-EXEC.
GMOFH999.
    EXIT.

7. Constraints

7.1 Data Validation Constraints

  • CUSTOMER-EYECATCHER (PIC X(4)) — A level-88 condition CUSTOMER-EYECATCHER-VALUE requires the value 'CUST'. The program does not explicitly validate this before processing, but any valid customer record placed in the container must contain this sentinel value.
  • CUSTOMER-STATUS (PIC X(10)) — Three mutually exclusive level-88 conditions restrict valid status values to 'ACTIVE', 'INACTIVE', and 'SUSPENDED'.
  • CUSTOMER-CREDIT-SCORE (PIC 999) — The picture clause restricts storage to values 0–999. The computed formula ((999 - 1) * FUNCTION RANDOM) + 1 further constrains the generated value to the range 1–999.
  • ABND-FREEFORM (PIC X(600)) — The free-form diagnostic message built by the STRING statement is capped at 600 characters; any overflow is silently discarded.
  • ABND-SQLCODE — Hard-coded to ZEROS since CRDTAGY2 performs no DB2 activity.

7.2 Channel and Container Constraints

  • Fixed channel name — WS-CHANNEL-NAME is hard-coded as 'CIPCREDCHANN ' (16 characters, space-padded). Any divergence between the name placed by the parent and this hard-coded value will result in a non-NORMAL CICS response.
  • Fixed container name — WS-CONTAINER-NAME is hard-coded as 'CIPB ' (16 characters, space-padded). The same name is used for both GET and PUT operations.
  • WS-CONTAINER-LEN (PIC S9(8) COMP) — Calculated via LENGTH OF WS-CONT-IN before each container operation. Use of LENGTH OF ensures the value always equals the exact structural byte length of WS-CONT-IN, preventing under- or overflow in FLENGTH.
  • Read-before-write ordering — The program unconditionally aborts (via GET-ME-OUT-OF-HERE) if GET CONTAINER fails. The credit score computation and PUT CONTAINER are therefore only reached if the GET succeeded, enforcing a strict read-before-write ordering on the container.

7.3 Sequencing and Timing Constraints

  • Delay must complete before container I/O — EXEC CICS DELAY is issued before any container access. A DELAY failure triggers the full abend path and EXEC CICS ABEND ABCODE('PLOP'), preventing any subsequent container or score computation activity.
  • RANDOM seed must be set before unseeded calls — FUNCTION RANDOM(WS-SEED) must be called first to initialise the COBOL pseudo-random generator. The subsequent unseeded FUNCTION RANDOM call for the credit score continues that same sequence and must follow the seeded call.
  • Abend handler link must precede EXEC CICS ABEND — On every error path, ABNDINFO-REC is fully populated and EXEC CICS LINK PROGRAM(ABNDPROC) is issued before EXEC CICS ABEND, ensuring the diagnostic record is persisted before task termination.

7.4 Resource and Value Range Constraints

  • Delay range: 1–3 seconds — FUNCTION RANDOM returns a value in [0, 1), so WS-DELAY-AMT is bounded to [1, 3) seconds (at least 1 second, strictly less than 3 seconds).
  • Credit score range: 1–999 — WS-NEW-CREDSCORE (PIC 999) and its generating formula bound the value to [1, 999).
  • Abend code convention — The abend code 'PLOP' complies with the CICS constraint that user-defined abend codes must not begin with 'A' (reserved for CICS system use).
  • ABNDPROC must be installed — WS-ABEND-PGM is the literal 'ABNDPROC'. This name cannot be changed at runtime; if the program is absent from the CICS region, the LINK command itself will fail.

8. Error Handling

The following sequence diagram illustrates the two distinct error paths — the full abend path triggered by a DELAY failure, and the simplified return path triggered by a container I/O failure.

8.1 CICS Response Code Checking (RESP/RESP2 Pattern)

Every CICS command in CRDTAGY2 uses the RESP and RESP2 options to capture primary and secondary response codes into WS-CICS-RESP and WS-CICS-RESP2. After each command, the primary response is tested against the DFHRESP(NORMAL) symbolic constant:

COBOL 
IF WS-CICS-RESP NOT = DFHRESP(NORMAL)
   ... error handling ...
END-IF

This pattern is applied consistently after EXEC CICS DELAY, EXEC CICS GET CONTAINER, and EXEC CICS PUT CONTAINER.

8.2 Full Abend Path — DELAY Failure

When EXEC CICS DELAY returns a non-normal response, the program executes the most comprehensive error path:

COBOL 
INITIALIZE ABNDINFO-REC
MOVE EIBRESP    TO ABND-RESPCODE
MOVE EIBRESP2   TO ABND-RESP2CODE
EXEC CICS ASSIGN APPLID(ABND-APPLID) END-EXEC
MOVE EIBTASKN   TO ABND-TASKNO-KEY
MOVE EIBTRNID   TO ABND-TRANID
PERFORM POPULATE-TIME-DATE
MOVE WS-ORIG-DATE TO ABND-DATE
MOVE WS-U-TIME    TO ABND-UTIME-KEY
MOVE 'PLOP'       TO ABND-CODE
EXEC CICS ASSIGN PROGRAM(ABND-PROGRAM) END-EXEC
MOVE ZEROS        TO ABND-SQLCODE
STRING 'CRDTAGY2 - DELAY FAILED ...' DELIMITED SIZE
       ' RESP=' DELIMITED SIZE
       WS-CICS-RESP DELIMITED SIZE
       INTO ABND-FREEFORM
DISPLAY '*** The delay messed up ! ***'
EXEC CICS LINK PROGRAM(WS-ABEND-PGM)
    COMMAREA(ABNDINFO-REC)
END-EXEC
EXEC CICS ABEND ABCODE('PLOP') END-EXEC

The POPULATE-TIME-DATE paragraph is only invoked on this error path, calling EXEC CICS ASKTIME and EXEC CICS FORMATTIME to provide a precise failure timestamp.

8.3 Simplified Error Path — GET/PUT CONTAINER Failure

Container I/O failures trigger a lighter-weight error path that logs diagnostics and exits cleanly without an abend:

COBOL 
* GET CONTAINER failure:
DISPLAY 'CRDTAGY2 - UNABLE TO GET CONTAINER. RESP=' WS-CICS-RESP
        ' RESP2=' WS-CICS-RESP2
DISPLAY 'CONTAINER=' WS-CONTAINER-NAME
        ' CHANNEL=' WS-CHANNEL-NAME
        ' FLENGTH=' WS-CONTAINER-LEN
PERFORM GET-ME-OUT-OF-HERE

* PUT CONTAINER failure:
DISPLAY 'CRDTAGY2 - UNABLE TO PUT CONTAINER. RESP=' WS-CICS-RESP
        ' RESP2=' WS-CICS-RESP2
DISPLAY 'CONTAINER=' WS-CONTAINER-NAME
        ' CHANNEL=' WS-CHANNEL-NAME
        ' FLENGTH=' WS-CONTAINER-LEN
PERFORM GET-ME-OUT-OF-HERE

Unlike the DELAY failure path, these paths do not invoke ABNDPROC or issue EXEC CICS ABEND — they perform a controlled return via EXEC CICS RETURN.

8.4 Controlled Task Exit

GET-ME-OUT-OF-HERE is the single exit point for all execution paths — both the normal success path and both container error paths:

COBOL 
GET-ME-OUT-OF-HERE SECTION.
GMOFH010.
    EXEC CICS RETURN
    END-EXEC.
GMOFH999.
    EXIT.

9. Examples

9.1 Example 1 — Successful Credit Score Generation (Normal Flow)

Scenario: The parent orchestrator program invokes CRDTAGY2 asynchronously via the CICS Async API, placing the following customer record into channel CIPCREDCHANN, container CIPB:

Input (customer record placed in container):

Field Value
CUSTOMER-EYECATCHER CUST
CUSTOMER-SORTCODE 987654
CUSTOMER-NUMBER 0000000042
CUSTOMER-FIRST-NAME John
CUSTOMER-LAST-NAME Smith
CUSTOMER-STATUS ACTIVE
CUSTOMER-CREDIT-SCORE 000 (placeholder — to be overwritten)
EIBTASKN (CICS task number) 1234 (used as RANDOM seed)

Execution steps:

  1. WS-SEED ← 1234. FUNCTION RANDOM(1234) returns, for example, 0.47. WS-DELAY-AMT = ((3 − 1) × 0.47) + 1 = ~1.94 seconds → EXEC CICS DELAY FOR SECONDS(1) (integer-truncated by PIC S9(8) COMP).
  2. RESP = NORMAL → no abend path taken.
  3. EXEC CICS GET CONTAINER retrieves the customer record into WS-CONT-IN. RESP = NORMAL.
  4. FUNCTION RANDOM (unseeded, continuing sequence) returns 0.71. WS-NEW-CREDSCORE = ((999 − 1) × 0.71) + 1 = ~709.
  5. CUSTOMER-CREDIT-SCORE in WS-CONT-IN is set to 709.
  6. EXEC CICS PUT CONTAINER writes the updated record back to CIPB. RESP = NORMAL.
  7. EXEC CICS RETURN — task completes normally; parent can FETCH the result.

Output (updated container CIPB):

Field Value
CUSTOMER-CREDIT-SCORE 709 (newly assigned score)
All other customer fields Unchanged

9.2 Example 2 — Delay Causes Parent Timeout (Score Arrives Too Late)

Scenario: Same setup as Example 1, but EIBTASKN produces a FUNCTION RANDOM value close to 1.0, pushing the delay toward the 3-second boundary.

Input:

Field Value
EIBTASKN 9999 (seed generating a high random fraction, e.g. 0.97)
Customer record Same as Example 1

Execution steps:

  1. WS-DELAY-AMT = ((3 − 1) × 0.97) + 1 = ~2.94 seconds → EXEC CICS DELAY FOR SECONDS(2) (truncated to integer).
  2. RESP = NORMAL → no abend; delay completes in approximately 2 seconds.
  3. Container read, score generation (e.g. 850), and container write all complete successfully.
  4. EXEC CICS RETURN — CRDTAGY2 completes normally.

Result from the parent program’s perspective:

The parent waits up to 3 seconds for all asynchronous child agency tasks. Because CRDTAGY2 consumed ~2–3 seconds, the parent may have already timed out before issuing a successful FETCH, meaning the updated credit score is never read in this transaction execution. CRDTAGY2 itself completes successfully — it is the parent’s 3-second FETCH window that determines whether the score is consumed.

Key behavioural note: There is approximately a 1-in-3 chance of the delay exceeding the parent’s timeout window. This is a deliberate design choice to simulate the realistic scenario of a slow or unresponsive external credit bureau.
