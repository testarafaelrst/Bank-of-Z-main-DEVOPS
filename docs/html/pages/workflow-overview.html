Development Workflows Overview

Bank of Z supports modern, Git-based development practices that integrate seamlessly with enterprise z/OS technologies, including Db2, CICS, IMS, z/OS Connect, IBM Dependency Based Build (DBB), and Wazi Deploy. This page provides a comparison and selection guide for the supported development workflows: direct mainframe editing, Zowe CLI, and GRUB, helping developers choose the approach that best fits their needs.

1. System Architecture

The Bank of Z development platform connects developer workstations to the z/OS target environment through a set of tools and pipelines. Regardless of which workflow is chosen, all paths converge on the same target runtime environment — consisting of CICS, Db2, IMS, and z/OS Connect — ensuring consistency across development approaches.

The Zowe CLI workflow routes changes through Git before landing on USS, while the GRUB workflow synchronizes files directly to USS via SSH — both ultimately feeding the same build and deployment pipeline.

2. Overview

A typical Bank of Z development cycle follows a structured sequence of activities, from making a code change through to validating the deployed result. The steps below apply broadly to all supported workflows, with differences in how source synchronization and pipeline triggering are handled.

2.1 Make Changes

  • Modify application source code, configuration files, or deployment artifacts.
  • Common changes include updates to COBOL programs, BMS maps, copybooks, z/OS Connect APIs, and web application components.

2.2 Commit Changes

  • Review and commit changes to the source repository.
  • Use meaningful commit messages to document modifications and support traceability.

Note: Committing before testing is required in the Zowe CLI workflow but optional in the GRUB workflow.

2.3 Run the Pipeline

  • Run the build pipeline using the supported development workflow.
  • The pipeline analyzes source changes, builds affected components, packages deployment artifacts, and prepares deployment plans.

2.4 Review Results

  • Review build logs, reports, and generated artifacts.
  • Address any build, dependency, or deployment issues identified during the pipeline run.

2.5 Deploy Changes

  • Deploy validated artifacts to the target environment.
  • Updated components are activated in the appropriate runtime environments, including CICS, Db2, IMS, and z/OS Connect.

2.6 Validate Changes

  • Verify that the deployed changes function as expected.
  • Run application tests and review runtime behavior before promoting changes to additional environments.

3. Supported Workflows

Bank of Z provides three development approaches. Each is optimized for a different combination of tooling, access constraints, and development pace.

3.1 Direct Mainframe Editing

Developers edit source files directly on the mainframe using traditional tools (e.g., ISPF/Edit or z/OS Explorer). Changes take effect immediately within the mainframe environment without requiring a local workstation or Git integration.

Best suited for: Quick, targeted fixes directly on z/OS where local tooling is not available.

3.2 Zowe CLI Workflow

A task-based workflow that uses Zowe CLI to clone a repository branch on z/OS USS and run the setup and pipeline scripts. It can be triggered from the command line or from a VS Code task, making it well-suited for developers who prefer an IDE-driven experience.

Key characteristics:

  • Source synchronization is driven by Git and Zowe CLI.
  • A commit is required before the pipeline can be triggered.
  • Fits naturally into branch-based, team-collaborative development.
  • Works even when direct SSH access to z/OS USS is restricted.

Example: Triggering the pipeline via setup-local.sh

BASH 
# After committing your changes and checking out your feature branch:
./setup-local.sh --branch feature/my-cobol-fix

Example: Triggering via VS Code task

JSON 
{
  "label": "Bank of Z: Run Pipeline (Zowe CLI)",
  "type": "shell",
  "command": "./setup-local.sh",
  "args": ["--branch", "${input:branchName}"],
  "group": "build"
}

3.3 GRUB Workflow

A development workflow optimized for rapid iteration, allowing developers to synchronize local changes directly to the z/OS USS target environment and run build and deployment activities — without requiring committed changes.

Key characteristics:

  • Changes are transferred via SSH and the GRUB synchronization mechanism.
  • Setup is initiated automatically after synchronization.
  • Ideal for fast feedback loops and frequent incremental changes.
  • Primarily suited for individual development and testing rather than team collaboration.

Example: Synchronizing changes with GRUB

BASH 
# Synchronize local working directory changes to z/OS USS
grub sync --target uss://mymainframe/u/developer/boz

4. Workflow Comparison

The table below summarizes the key differences between the Zowe CLI and GRUB workflows to help you select the right tool for your situation.

Feature Zowe CLI Workflow GRUB Workflow
Source synchronization Git + Zowe CLI clone on z/OS USS Direct file sync to z/OS USS
Commit required before testing ✅ Yes ❌ No
GitHub dependency Required Not required for daily development
Remote access method Zowe CLI SSH and GRUB
Development style Branch-based, version-controlled Rapid local iteration
Change transfer Repository clone + setup execution Synchronization of changed files
Collaboration Well suited for shared branch-based development Primarily individual development and testing
Setup execution VS Code task or setup-local.sh Automatic after synchronization
Best suited for Feature development, team collaboration, restricted SSH environments Fast testing, frequent changes, rapid development cycles

5. Choosing a Workflow

5.1 Use the Zowe CLI Workflow When

  • You work in a branch-based development model.
  • Changes should be committed and tracked through Git before testing.
  • You want to use Zowe CLI and VS Code integration.
  • SSH access to z/OS USS is limited or unavailable.
  • You are working on a shared feature branch with other team members.

5.2 Use the GRUB Workflow When

  • You need to test changes quickly without committing them first.
  • You want rapid feedback during active development.
  • You have SSH access to z/OS USS.
  • You frequently make and validate incremental changes.
  • You are working on individual, exploratory development or debugging.

Important: Both workflows ultimately prepare and update the same Bank of Z environment. The choice depends on your development process, tooling preferences, and access requirements.
