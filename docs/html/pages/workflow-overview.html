Development Workflow Overview

Bank of Z supports modern, Git-based development practices for z/OS application assets. This page provides a comparison and selection guide for the two supported development workflows — the Zowe CLI workflow and the GRUB workflow — helping developers choose the right approach based on tooling, environment, and team preferences.

Both workflows enable developers to modify application source code, build and validate changes, and deploy updates to the target z/OS environment, leveraging enterprise technologies such as Db2, CICS, IMS, z/OS Connect, IBM Dependency Based Build (DBB), and Wazi Deploy.

1. System Architecture

The Bank of Z development environment is built around a z/OS target system and a Git-based source repository. Both workflows interact with the same core infrastructure but differ in how changes are synchronized and how pipeline activities are triggered.

graph TD DEV[Developer Workstation] GIT[Git Repository / GitHub] VSCODE[VS Code + Zowe CLI Extension] ZUSS[z/OS USS - Unix System Services] DBB[IBM Dependency Based Build - DBB] WAZI[Wazi Deploy] RUNTIME[z/OS Runtime Environments\nCICS · Db2 · IMS · z/OS Connect] DEV -->|Edit source code| VSCODE VSCODE -->|Commit & push| GIT GIT -->|Clone branch via Zowe CLI| ZUSS VSCODE -->|Sync files via SSH/GRUB| ZUSS ZUSS --> DBB DBB -->|Package artifacts| WAZI WAZI -->|Deploy & activate| RUNTIME

The diagram above illustrates the high-level architecture shared by both workflows. Source changes originate on the developer workstation and are delivered to z/OS USS, where IBM DBB performs the build and Wazi Deploy activates the updated components in the target runtime environments. The key architectural difference is the synchronization path: the Zowe CLI workflow routes changes through the Git repository, while the GRUB workflow pushes files directly to USS via SSH.

2. Overview

2.1 Development Workflow Lifecycle

Every Bank of Z development cycle follows the same six-step lifecycle, regardless of which workflow is selected:

graph LR A[1. Make Changes] --> B[2. Commit Changes] B --> C[3. Run Pipeline] C --> D[4. Review Results] D --> E[5. Deploy Changes] E --> F[6. Validate Changes] F -->|Iterate| A

Each step is described in detail below.

2.1.1 Make Changes

Modify application source code, configuration files, or deployment artifacts. Common changes include:

  • COBOL programs
  • BMS maps
  • Copybooks
  • z/OS Connect APIs
  • Web application components

2.1.2 Commit Changes

Review and commit changes to the source repository. Use meaningful commit messages to document modifications and support traceability.

Note (GRUB workflow): The GRUB workflow does not require a commit before testing. Changes are synchronized directly to z/OS USS, enabling rapid iteration without going through Git.

2.1.3 Run the Pipeline

Run the build pipeline using the supported development workflow. The pipeline:

  • Analyzes source changes
  • Builds affected components
  • Packages deployment artifacts
  • Prepares deployment plans

2.1.4 Review Results

Review build logs, reports, and generated artifacts. Address any build, dependency, or deployment issues identified during the pipeline run.

2.1.5 Deploy Changes

Deploy validated artifacts to the target environment. Updated components are activated in the appropriate runtime environments, including CICS, Db2, IMS, and z/OS Connect.

2.1.6 Validate Changes

Verify that the deployed changes function as expected. Run application tests and review runtime behavior before promoting changes to additional environments.

3. Supported Workflows

Bank of Z supports two distinct development approaches. Each workflow targets a different development style and access model.

3.1 Zowe CLI Workflow

A task-based workflow that uses Zowe CLI to clone your branch on z/OS USS and run the setup and pipeline scripts. It can be triggered from:

  • The command line using setup-local.sh
  • A VS Code task via the Zowe CLI VS Code extension

This workflow is inherently branch-based and version-controlled, making it well suited for team collaboration, feature development, and environments where direct SSH access to z/OS USS is limited or unavailable.

Example: Triggering the setup script from the command line

BASH 
# Clone the feature branch to z/OS USS and run the setup
./setup-local.sh --branch feature/my-cobol-update

Example: VS Code task definition (tasks.json)

JSON 
{
  "label": "Run Bank of Z Pipeline (Zowe CLI)",
  "type": "shell",
  "command": "./setup-local.sh",
  "args": ["--branch", "${input:branchName}"],
  "problemMatcher": []
}

3.2 GRUB Workflow

A development workflow optimized for rapid iteration, allowing developers to synchronize local file changes directly to the z/OS USS target environment and run build and deployment activities without requiring committed changes.

This workflow is ideal for fast feedback cycles, frequent incremental changes, and individual development and testing scenarios where the developer has SSH access to z/OS USS.

Example: Syncing a changed COBOL file via SSH/GRUB

BASH 
# Synchronize a modified COBOL source file directly to z/OS USS
grub sync src/COBPGM1.cbl /u/developer/bankofz/src/COBPGM1.cbl

After synchronization, the setup and build activities are initiated automatically, eliminating the need for a manual commit-push-clone cycle.

4. Workflow Comparison

4.1 Feature Comparison Table

The table below summarizes the key differences between the two workflows:

Feature Zowe CLI Workflow GRUB Workflow
Source synchronization Git clone via Zowe CLI to z/OS USS Direct file sync to z/OS USS
Commit required before testing Yes No
GitHub dependency Required Not required for daily development
Remote access method Zowe CLI SSH and GRUB
Development style Branch-based and version-controlled Rapid local iteration
Change transfer Repository clone and setup execution Synchronization of changed files
Collaboration Well suited for shared branch-based development Primarily individual development and testing
Setup execution VS Code task or setup-local.sh Initiated automatically after synchronization
Best suited for Feature development, team collaboration, restricted SSH environments Fast testing, frequent changes, rapid development cycles

4.2 Workflow Selection Guide

Use the decision flowchart below to determine which workflow best fits your needs:

graph TD START([Start: Choose a Workflow]) --> Q1{Do you have\ndirect SSH access\nto z/OS USS?} Q1 -->|No| ZOWE[Use Zowe CLI Workflow] Q1 -->|Yes| Q2{Do you need to commit\nchanges before testing?} Q2 -->|Yes| ZOWE Q2 -->|No| Q3{Are you working\non a shared team\nbranch?} Q3 -->|Yes| ZOWE Q3 -->|No| Q4{Do you need\nrapid iteration\nand fast feedback?} Q4 -->|Yes| GRUB[Use GRUB Workflow] Q4 -->|No| ZOWE ZOWE --> ENV[Same Bank of Z\nTarget Environment] GRUB --> ENV

4.2.1 Use the Zowe CLI Workflow When:

  • You work in a branch-based development model
  • Changes should be committed and tracked through Git
  • You want to use Zowe CLI and VS Code integration
  • SSH access to z/OS USS is limited or unavailable
  • You are collaborating on a shared team branch

4.2.2 Use the GRUB Workflow When:

  • You need to test changes quickly without committing them
  • You want rapid feedback during development
  • You have SSH access to z/OS USS
  • You frequently make and validate incremental changes

6. Summary

Both the Zowe CLI workflow and the GRUB workflow ultimately prepare and update the same Bank of Z environment. The choice between them depends on your development process, tooling preferences, and access requirements:

  • Choose the Zowe CLI workflow for structured, team-based, version-controlled development — especially where SSH access is restricted.
  • Choose the GRUB workflow for speed and agility during individual development, where rapid iteration and immediate feedback are the priority.
