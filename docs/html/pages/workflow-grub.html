GRUB Workflow

The GRUB (Git Remote Utilities for Build) workflow enables rapid, iterative development on IBM Z by synchronizing local file changes directly to z/OS UNIX System Services (USS) and automatically triggering the build and setup pipeline — all without requiring a Git commit or push. GRUB transfers only the files that have changed, making it the fastest available option for day-to-day development on the platform.

Before using this workflow, complete the GRUB deployment setup to configure your local environment and establish connectivity to your z/OS host.

1. System Architecture

The GRUB workflow connects a developer’s local workstation to a z/OS USS environment through a lightweight, patch-based file transfer mechanism. Once files arrive on USS, the setup pipeline runs natively, eliminating the need for Zowe CLI overhead or GitHub connectivity.

The architecture is intentionally minimal: GRUB bypasses the traditional Git remote push cycle, communicating directly with USS. This means a developer can see their changes reflected in the running application within seconds of triggering a sync, regardless of network access to GitHub.

2. Overview

The GRUB workflow follows a tight, four-step daily development cycle. The diagram below illustrates how each step flows into the next, forming a rapid feedback loop between local code changes and a live z/OS environment.

sequenceDiagram participant Dev as Developer (Local) participant GRUB as GRUB Client participant USS as z/OS USS participant App as Bank of Z App Dev->>GRUB: Modify source files (no commit needed) GRUB->>GRUB: Analyze changed files & create patch bundle GRUB->>USS: Transfer only changed files via patch USS->>USS: Apply patches to Bank-of-Z repo USS->>USS: Run setup-remote.sh natively USS->>USS: validate-prereqs → environment → install-bank-of-z USS->>App: Deploy updated application App-->>Dev: Changes live at http://:9080/bank-frontend-vanilla

This sequence highlights the key advantage of GRUB: the developer never interacts with a remote Git repository. The entire round-trip — from saving a file locally to seeing it deployed — is driven by GRUB’s patch transfer and USS-native execution.

3. Daily Development Cycle

3.1 Make Changes

Modify application source code in your local workspace. No git commit, git add, or git push is required at any point in this workflow. GRUB operates directly on your working-tree files, whether they are staged, unstaged, or entirely untracked.

Common file types you will work with include:

Asset Type Description
COBOL Programs Core application business logic
COBOL Copybooks Shared data structures and common routines
BMS Maps Basic Mapping Support screen definitions
z/OS Connect API Assets API configuration and service definitions
Configuration Files Environment and pipeline configuration

3.2 Trigger a GRUB Sync

Once your local changes are ready, trigger a GRUB sync from your workstation. GRUB performs the following actions automatically:

  1. Analyzes your local workspace to identify files that have changed relative to the last sync state.
  2. Creates a patch bundle containing only the deltas — not full file copies.
  3. Transfers the patch bundle securely to your z/OS USS target.

Refer to your GRUB installation documentation for the specific command or UI action used to trigger the sync in your environment.

3.3 What Runs Automatically on USS

Once the patch bundle arrives on USS, the entire downstream pipeline executes without any further manual intervention. The flow is as follows:

CODE 
Local Machine                    z/OS USS
─────────────                    ────────
GRUB analyzes changes
Creates patch files
Transfers changed files ────────→ Patches applied to USS
                                  setup-remote.sh runs natively
                                  ├─ validate-prereqs
                                  ├─ environment
                                  └─ install-bank-of-z

A critical detail: GRUB detects that it is running from within the Bank-of-Z repository and uses the already-synced files directly. No re-cloning from GitHub occurs. This is what makes every sync after the first one significantly faster — only the delta is ever transferred or processed.

3.3.1 Stage Detection Logic

The setup-remote.sh script uses a Git-based detection mechanism to determine whether it is being invoked from a GRUB sync context or a fresh clone context. If it detects the Bank-of-Z repository at the current path, it uses that location in-place:

BASH 
if git rev-parse --git-dir > /dev/null 2>&1; then
    local repo_name=$(basename "$(git rev-parse --show-toplevel)")
    if [[ "$repo_name" == "Bank-of-Z" ]]; then
        # GRUB workflow — use current repository location
        BANK_DIR="$(git rev-parse --show-toplevel)"
    fi
fi

This logic ensures that your uncommitted local changes — which GRUB has already transferred — are used as-is by the setup pipeline, without being overwritten by a fresh clone.

3.4 Validate Changes

Once the pipeline completes, open the Bank of Z frontend in your browser to verify your changes are live:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

Replace <your-zos-host> with the hostname or IP address of your z/OS system. If the application reflects your latest edits, the full cycle has completed successfully.

4. Why Use GRUB

GRUB is purpose-built for speed and simplicity during active development. The table below summarizes its key advantages over alternative workflows:

Feature Benefit
No commits required Test changes immediately without a Git commit or push — ideal for rapid iteration
Patch-based sync Only changed files are transferred, keeping each sync fast regardless of project size
Automatic setup The build and deployment pipeline runs as soon as the sync completes — zero manual steps
Native USS execution Scripts run directly on USS without Zowe CLI overhead, improving reliability and speed
Works offline No GitHub connectivity is needed after the initial clone — syncs work on isolated networks

Use the GRUB workflow when you need the fastest possible feedback loop and do not require full Git traceability for every change. Use the Zowe CLI workflow when working in a team environment where branch-based history and pull request reviews are required.
