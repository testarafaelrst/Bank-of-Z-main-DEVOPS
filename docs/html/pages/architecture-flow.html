Application Flow

Bank of Z is a modern banking demonstration application that showcases how a contemporary web interface integrates with IBM Z transaction-processing systems. It leverages CICS, IMS Transaction Manager (IMS TM), Db2, IMS databases, and IBM MQ to process banking requests end-to-end, providing a consistent user experience regardless of the underlying transaction-processing path.

1. Overview

Bank of Z employs a hybrid architecture that bridges a browser-based frontend with the power and reliability of IBM Z backend systems. Users interact with the application through a standard web UI, which communicates with z/OS through REST APIs exposed via z/OS Connect. Behind that gateway, banking operations are routed to either CICS or IMS TM based on the customer identifier, each backed by its own database (Db2 or IMS DB, respectively).

The system also supports external integration through IBM MQ, enabling inbound money transfer requests and other inter-bank messaging scenarios from external banking applications.

Key capabilities include:

  • Account management – view and update account information
  • Credit scoring – evaluate customer creditworthiness
  • Fund transfers – both internal and externally initiated via IBM MQ
  • Menu navigation – a unified UI regardless of backend processing path

2. System Architecture

The Bank of Z system is composed of four primary tiers: the browser-based UI, the integration layer (z/OS Connect), the transaction-processing layer (CICS / IMS TM), and the data layer (Db2 / IMS DB). IBM MQ bridges external banking partners into this architecture.

graph TD A[👤 User / Browser UI] -->|REST API Call| B[z/OS Connect] B -->|Customer ID starts with C| C[CICS Transaction Server] B -->|Customer ID starts with I| D[IMS Transaction Manager] C -->|SQL Queries / Updates| E[(Db2 Database)] D -->|DL/I Calls| F[(IMS Database)] C -->|Transaction Result| B D -->|Transaction Result| B B -->|Response| A G[External Banking App] -->|Inbound Messages| H[IBM MQ] H -->|MQ Trigger / Queue| C H -->|MQ Trigger / Queue| D

The diagram above illustrates how the Bank of Z UI acts as the single entry point for all users. z/OS Connect serves as the RESTful gateway into z/OS, routing work to the correct backend based on the customer identifier prefix. IBM MQ introduces an asynchronous pathway for externally initiated operations such as inbound fund transfers.

3. Request Processing Flow

3.1 Step-by-Step Walkthrough

A complete end-to-end transaction follows these steps:

  1. The user performs a banking operation (e.g., account lookup, fund transfer) through the Bank of Z web UI.
  2. The UI evaluates the customer identifier to determine the appropriate processing path:
    • Identifiers beginning with C → CICS path
    • Identifiers beginning with I → IMS TM path
  3. The UI sends an HTTP REST request to z/OS Connect with the relevant operation payload.
  4. z/OS Connect translates the REST request and forwards it to the selected backend (CICS or IMS TM).
  5. The backend transaction program executes the required business logic (account lookup, credit scoring, fund transfer, etc.).
  6. The transaction program reads from or writes to the appropriate database:
    • CICS → Db2
    • IMS TM → IMS Database
  7. The transaction result propagates back through IMS TM or CICS → z/OS Connect → UI.
  8. The Bank of Z UI renders the result to the user.
sequenceDiagram actor User as 👤 User participant UI as Bank of Z UI participant ZC as z/OS Connect participant CICS as CICS / IMS TM participant DB as Db2 / IMS DB User->>UI: Initiate banking operation UI->>UI: Evaluate customer identifier (C/I prefix) UI->>ZC: HTTP REST Request ZC->>CICS: Forward transaction request CICS->>DB: Read / Write data DB-->>CICS: Data response CICS-->>ZC: Transaction result ZC-->>UI: HTTP REST Response UI-->>User: Display result

3.2 Routing Logic

The routing decision is made by the Bank of Z UI before any call is issued to z/OS Connect. The rule is straightforward:

Customer Identifier Pattern Processing Environment Data Store
Cnnnn (e.g., C1234) CICS Db2
Innn (e.g., I123) IMS TM IMS DB

This routing model demonstrates how multiple IBM Z transaction-processing technologies can coexist behind a single application interface without any difference in the user experience.

4. Transaction Flows by Function

4.1 Menu Navigation

When a user first accesses Bank of Z, the UI presents a menu of available operations. The menu itself is stateless — no backend call is made until the user selects an operation and provides a customer identifier. At that point, the routing logic described in Section 3.2 is applied.

graph TD A[User Lands on Bank of Z UI] --> B[Main Menu Displayed] B --> C{User Selects Operation} C --> D[Account Management] C --> E[Credit Scoring] C --> F[Fund Transfer] D --> G{Evaluate Customer ID} E --> G F --> G G -->|C prefix| H[Route to CICS] G -->|I prefix| I[Route to IMS TM]

4.2 Account Management

Account management covers operations such as viewing account balances, account details, and updating account information.

CICS path example (customer C1234):

CODE 
HTTP GET /accounts/C1234
  → z/OS Connect
    → CICS Transaction (e.g., BACM)
      → Db2: SELECT * FROM ACCOUNT WHERE CUST_ID = 'C1234'
    ← Result set returned
  ← JSON response
← Account details displayed in UI

IMS TM path example (customer I123):

CODE 
HTTP GET /accounts/I123
  → z/OS Connect
    → IMS TM Transaction (e.g., BAIM)
      → IMS DB: GU (Get Unique) on ACCOUNT segment
    ← Segment data returned
  ← JSON response
← Account details displayed in UI

4.3 Credit Scoring

The credit scoring function evaluates a customer’s creditworthiness based on account data and transaction history. This is a read-intensive operation that follows the same routing logic.

sequenceDiagram actor User as 👤 User participant UI as Bank of Z UI participant ZC as z/OS Connect participant BE as CICS or IMS TM participant DB as Db2 or IMS DB User->>UI: Request credit score for customer UI->>ZC: POST /creditscore/{customerId} ZC->>BE: Invoke credit scoring transaction BE->>DB: Retrieve account history & balances DB-->>BE: Account data BE->>BE: Apply credit scoring logic BE-->>ZC: Credit score result ZC-->>UI: JSON response with score UI-->>User: Display credit score

The credit scoring transaction program applies internal business rules against the retrieved data, computing a score that is then returned all the way back to the browser.

4.4 Fund Transfers

Fund transfers can be initiated in two ways:

  1. User-initiated transfers — the user submits a transfer request through the UI, which is processed synchronously via z/OS Connect to CICS or IMS TM.
  2. Externally initiated transfers — inbound requests from external banking applications arrive via IBM MQ and are picked up asynchronously by CICS or IMS TM.
graph TD A[User-Initiated Transfer] -->|REST via z/OS Connect| B[CICS / IMS TM] C[External Banking App] -->|MQ Message| D[IBM MQ Queue] D -->|MQ Trigger| B B -->|Debit source account| E[(Db2 / IMS DB)] B -->|Credit destination account| E E -->|Confirmation| B B -->|Transfer result| F[Response back to UI or MQ Reply Queue]

User-initiated flow:

CODE 
HTTP POST /transfers
  Body: { "from": "C1234", "to": "C5678", "amount": 500.00 }
  → z/OS Connect → CICS
    → Db2: UPDATE ACCOUNT SET BALANCE = BALANCE - 500 WHERE CUST_ID = 'C1234'
    → Db2: UPDATE ACCOUNT SET BALANCE = BALANCE + 500 WHERE CUST_ID = 'C5678'
  ← Commit → Success response

MQ-initiated flow:

CODE 
External App → MQPUT to inbound transfer queue
  → IBM MQ trigger fires CICS / IMS TM transaction
    → Transaction reads MQ message (MQGET)
    → Applies debit/credit to Db2 / IMS DB
    → MQPUT confirmation to reply queue (optional)

5. External Integration

For selected operations, Bank of Z exchanges information with external systems through IBM MQ. MQ provides reliable, asynchronous message delivery that decouples the external sender from the Bank of Z backend processing.

sequenceDiagram participant ExtBank as External Banking App participant MQ as IBM MQ (z/OS) participant CICS as CICS / IMS TM participant DB as Db2 / IMS DB ExtBank->>MQ: MQPUT — Inbound transfer request MQ-->>CICS: MQ Trigger initiates transaction CICS->>MQ: MQGET — Read transfer message CICS->>DB: Apply debit / credit DB-->>CICS: Confirmation CICS->>MQ: MQPUT — Reply to reply queue (optional) MQ-->>ExtBank: Transfer acknowledgment

This architecture ensures that:

  • External partners do not need direct access to CICS or IMS TM.
  • Message persistence in IBM MQ guarantees no transfer request is lost, even if the backend is temporarily unavailable.
  • Security is enforced at the MQ layer using IBM RACF, ensuring only authorized external systems can put messages to Bank of Z queues.

6. End-to-End Architecture Summary

The following diagram consolidates all flows — user-initiated, CICS-routed, IMS-routed, and MQ-mediated — into a single view of the Bank of Z application:

graph TD User["👤 User (Browser)"] -->|HTTP REST| UI[Bank of Z Web UI] UI -->|Evaluate Customer ID| Router{Routing Logic} Router -->|C prefix| ZC_CICS[z/OS Connect → CICS Path] Router -->|I prefix| ZC_IMS[z/OS Connect → IMS TM Path] ZC_CICS --> CICS[CICS Transaction Server] ZC_IMS --> IMS[IMS Transaction Manager] CICS -->|SQL| Db2[(Db2 Database)] IMS -->|DL/I| IMSDB[(IMS Database)] CICS --> ZC_CICS IMS --> ZC_IMS ZC_CICS --> UI ZC_IMS --> UI ExtApp[External Banking App] -->|MQPUT| MQ[IBM MQ for z/OS] MQ -->|MQ Trigger| CICS MQ -->|MQ Trigger| IMS

This unified view demonstrates Bank of Z’s core design principle: a single, consistent user experience layered over multiple IBM Z transaction-processing environments, with seamless support for both synchronous REST-driven operations and asynchronous MQ-driven integration.
