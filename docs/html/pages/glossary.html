Glossary

This glossary defines common terms, acronyms, and concepts used throughout the Bank of Z documentation. It covers IBM Z platform components, middleware systems, programming languages, development tools, and DevOps workflows that together form the Bank of Z hybrid banking application ecosystem. Whether you are a developer, architect, or operations engineer, this reference provides the foundational vocabulary needed to understand and work with Bank of Z.

1. Overview

Bank of Z is a sample hybrid banking application designed to demonstrate modern z/OS application development, integration, build, deployment, and operational workflows. It combines multiple IBM Z technologies — including CICS, IMS, Db2, IBM MQ, and z/OS Connect — into a unified, end-to-end banking solution.

The application supports two primary transaction-processing paths determined by customer identifier patterns:

  • CICS path — Customers whose identifiers begin with C are routed to CICS transactions.
  • IMS TM path — Customers whose identifiers begin with I are routed to IMS TM transactions.

Both paths share common data resources (Db2, IMS DB) and are exposed externally through z/OS Connect REST APIs, which bridge the web front end to the mainframe back end.

graph TD A[Web Application / REST Client] --> B[z/OS Connect] B --> C{Customer Routing} C -->|ID starts with C| D[CICS Transaction] C -->|ID starts with I| E[IMS TM Transaction] D --> F[Db2 - Relational Database] D --> G[IBM MQ - Messaging] E --> H[IMS DB - Hierarchical Database] E --> F G --> I[Bank of Q - External System]

The diagram above illustrates how incoming REST requests flow through z/OS Connect into the Bank of Z customer routing mechanism, which dispatches work to either the CICS or IMS TM processing paths. Both paths interact with shared data stores and messaging infrastructure.

2. System Architecture

The Bank of Z system architecture is a hybrid architecture that integrates multiple transaction-processing environments, databases, messaging systems, and DevOps toolchains into a cohesive platform.

graph TD subgraph Client Layer A[VS Code / Bob IDE] B[Zowe CLI] C[Web Application] end subgraph DevOps Layer D[Git Repository] E[Pipeline - DBB / zBuilder] F[Wazi Deploy] G[ZCodeScan] end subgraph z/OS Platform H[USS - UNIX System Services] I[z/OS Connect] J[CICS Transaction Server] K[IMS TM] L[Db2 for z/OS] M[IMS DB] N[IBM MQ] end A --> D B --> D D --> E E --> G E --> F F --> H C --> I I --> J I --> K J --> L J --> N K --> M K --> L N --> O[Bank of Q]

The architecture spans three conceptual layers:

  1. Client Layer — Developer IDEs (VS Code, Bob IDE), Zowe CLI, and the end-user web application.
  2. DevOps Layer — Source control (Git), build automation (DBB/zBuilder), static analysis (ZCodeScan), and deployment tooling (Wazi Deploy).
  3. z/OS Platform — The runtime environment hosting CICS, IMS TM, Db2, IMS DB, IBM MQ, and z/OS Connect, all running within or alongside z/OS USS.

The following sequence diagram shows a typical end-to-end transaction flow from a web client through to the mainframe back end:

3. IBM Z Platform Terms

3.1 z/OS and USS

Term Definition
z/OS The primary operating system for IBM Z mainframe servers, providing high availability, security, and scalability for enterprise workloads.
USS UNIX System Services. The POSIX-compliant environment within z/OS used to host source code, scripts, build artifacts, and application assets.
JVM Java Virtual Machine. The runtime environment used to execute Java applications and services.
ODE On-Demand Environment. A preconfigured development and testing environment used to provision and run Bank of Z components.

USS acts as the integration point between traditional z/OS datasets and modern open-source tooling. Build scripts, pipeline configurations, and application artifacts all reside in USS, making it the backbone of the Bank of Z DevOps workflow.

3.2 Middleware — CICS

CICS (Customer Information Control System) is an IBM transaction-processing system that executes online business transactions. It is one of the two primary runtime environments in Bank of Z.

Term Definition
CICS Customer Information Control System. An IBM transaction-processing system used to execute online business transactions.
BMS Basic Mapping Support. A CICS facility used to define terminal screen layouts and user interactions.

Key Bank of Z behavior: Customers with identifiers beginning with C are routed to CICS transactions. CICS interacts with Db2 for account data and with IBM MQ for inter-bank messaging.

A typical CICS COBOL program in Bank of Z uses EXEC CICS commands to interact with the transaction environment:

COBOL 
EXEC CICS RECEIVE
    MAP('BANKMAP')
    MAPSET('BANKMAPS')
END-EXEC.

EXEC CICS READ
    FILE('ACCTFILE')
    INTO(WS-ACCOUNT-RECORD)
    RIDFLD(WS-ACCOUNT-ID)
END-EXEC.

EXEC CICS RETURN
    TRANSID('BNKZ')
    COMMAREA(WS-COMMAREA)
END-EXEC.

3.3 Middleware — IMS

IMS (Information Management System) provides both a hierarchical database (IMS DB) and a transaction manager (IMS TM) within Bank of Z.

Term Definition
IMS TM IBM Information Management System Transaction Manager. A transaction-processing environment used by Bank of Z. Customers with identifiers beginning with I are routed to IMS TM transactions.
IMS DB IBM Information Management System Database. A hierarchical database used by the IMS processing path within Bank of Z.

Key Bank of Z behavior: Customers with identifiers beginning with I are routed to IMS TM transactions, which store and retrieve data from IMS DB.

3.4 Middleware — Db2

Db2 (IBM Db2 for z/OS) is a relational database used to store customer, account, and transaction information across both the CICS and IMS processing paths.

Term Definition
Db2 IBM Db2 for z/OS. A relational database used to store customer, account, and transaction information.
Account History Db2 Database A Db2 database used by Bank of Z to store historical account and transaction information for inquiry and reporting functions.

A typical embedded SQL statement used within a COBOL program to query Db2:

COBOL 
EXEC SQL
    SELECT ACCT_BALANCE,
           ACCT_OWNER,
           ACCT_TYPE
    INTO  :WS-BALANCE,
          :WS-OWNER,
          :WS-TYPE
    FROM  ACCOUNT
    WHERE ACCT_ID = :WS-ACCT-ID
END-EXEC.

3.5 Middleware — IBM MQ

IBM MQ is messaging middleware used for asynchronous communication between applications and external systems. In Bank of Z, it enables money transfer scenarios between Bank of Z and the external Bank of Q system.

Term Definition
IBM MQ IBM messaging middleware used for asynchronous communication between applications and external systems.
Bank of Q A sample external banking system used to demonstrate inter-application communication and money transfer scenarios through IBM MQ.

3.6 z/OS Connect

z/OS Connect is an API framework that enables REST-based access to z/OS applications and services. It is the primary integration layer between the Bank of Z web application and the mainframe transaction environments.

Term Definition
z/OS Connect An API framework that enables REST-based access to z/OS applications and services. In Bank of Z, it provides the interface between the web application and the CICS and IMS transaction environments.
API Application Programming Interface. A defined interface that enables applications and services to communicate with each other.
RSE API Remote System Explorer API. A service used by Zowe CLI and development tools to interact with z/OS resources.

4. Programming Languages and Source Artifacts

4.1 COBOL

COBOL (Common Business-Oriented Language) is the primary programming language used for Bank of Z business logic. It is used to implement transaction processing, account management, and data access routines.

Term Definition
COBOL Common Business-Oriented Language. The primary programming language used for the Bank of Z business logic.
Copybook A reusable source file containing data structure definitions shared across COBOL programs.

Copybooks promote reuse by centralizing shared data layouts. An example copybook defining an account record:

COBOL 
******************************************
      * COPYBOOK: ACCTCPY
      * Account Record Layout
      ******************************************
       01 ACCOUNT-RECORD.
           05 ACCT-ID          PIC X(10).
           05 ACCT-OWNER       PIC X(30).
           05 ACCT-TYPE        PIC X(02).
           05 ACCT-BALANCE     PIC S9(11)V99 COMP-3.
           05 ACCT-STATUS      PIC X(01).

This copybook can be included in any COBOL program using:

COBOL 
COPY ACCTCPY.

5. DevOps and Build Tooling

5.1 Build Frameworks

Bank of Z uses a modern DevOps pipeline to automate the build, test, and deployment of z/OS application changes.

Term Definition
DBB IBM Dependency Based Build. A build framework used to compile, link, and manage z/OS application builds.
zBuilder A build framework used with DBB to automate compilation, linking, and build orchestration for z/OS applications.
ZCodeScan A static analysis tool used to analyze source code quality and identify potential issues.
Wazi Deploy IBM deployment automation tooling used to deploy application artifacts and configuration changes.
ZOAU IBM Z Open Automation Utilities. A collection of utilities and APIs used to automate z/OS administration and development tasks.
zconfig z/OS Middleware Configuration Tool. A command-line tool to configure and create artifacts for CICS TS, Db2, IMS, and z/OS Connect, introducing configuration as code to z/OS middleware.

5.2 Pipelines and Workflows

Term Definition
Pipeline An automated sequence of build, packaging, deployment, and validation activities executed through Bank of Z development workflows.
Workflow A defined development process used to build, deploy, test, and validate application changes. Bank of Z supports VS Code and GRUB workflows.
GRUB Git Remote User Build. A workflow that synchronizes local changes to z/OS USS and runs setup and build processes without requiring commits for every change.

The following diagram illustrates the Bank of Z DevOps pipeline flow:

graph LR A[Developer - VS Code / Bob IDE] --> B[Git Repository] B --> C[Pipeline Triggered] C --> D[ZCodeScan - Static Analysis] D --> E[DBB / zBuilder - Compile & Link] E --> F[Package Artifacts] F --> G[Wazi Deploy - Deploy to z/OS] G --> H[CICS / IMS TM Runtime] H --> I[Validation & Testing] I -->|Pass| J[Production Ready] I -->|Fail| A

This pipeline ensures that every code change is automatically analyzed, compiled, packaged, deployed, and validated before promotion, reducing risk and accelerating delivery.

5.3 Version Control and Source Management

Term Definition
Git A distributed version control system used to manage source code and support collaborative development.

5.4 Developer Tools

Term Definition
VS Code Visual Studio Code. A development environment commonly used to develop, build, and manage Bank of Z assets.
Bob IDE IBM Premium Bob for Z. An integrated development environment that supports IBM Z application development workflows.
Zowe CLI A command-line interface used to interact with z/OS systems, services, datasets, USS files, and development workflows.

6. Application Concepts

6.1 Bank of Z Application

Term Definition
Bank of Z A sample hybrid banking application that demonstrates modern z/OS application development, integration, build, deployment, and operational workflows.
Hybrid Architecture An application architecture that integrates multiple transaction-processing environments and technologies into a unified user experience. In Bank of Z, requests are processed through either CICS or IMS TM while sharing common services and data resources.
Customer Routing The Bank of Z mechanism that routes requests to either CICS or IMS TM based on the customer identifier pattern.

6.2 Customer Routing Logic

The following diagram shows the customer routing decision logic at the heart of Bank of Z:

graph TD A[Incoming Request via z/OS Connect] --> B{Inspect Customer ID} B -->|Starts with 'C'| C[Route to CICS Transaction] B -->|Starts with 'I'| D[Route to IMS TM Transaction] C --> E[Access Db2 / IBM MQ] D --> F[Access IMS DB / Db2] E --> G[Return Response via z/OS Connect] F --> G

The customer routing logic is a foundational design pattern in Bank of Z. By using the first character of the customer identifier as a routing key, the application cleanly separates CICS and IMS TM workloads while sharing a common API surface through z/OS Connect.
