Tutorial: Incremental Build

1. Overview

The Bank of Z Incremental Build tutorial walks you through making a COBOL source code change and triggering an incremental build using the Bank of Z build workflow. The key insight is that IBM Dependency Based Build (DBB) is smart enough to detect only the files that have changed — so instead of recompiling every program in the application, it targets only the affected components.

This tutorial covers the complete end-to-end workflow: editing a COBOL source file locally, committing and pushing the change via Git, pulling the update onto z/OS USS, and running the incremental build pipeline. You will then verify that DBB correctly identifies the changed file and confirms it was compiled and deployed.

graph TD A[Developer Edits BNKMENU.cbl] --> B[Commit & Push to Git Branch] B --> C[Pull Changes to z/OS USS] C --> D[Run pipeline-remote.sh] D --> E{DBB Change Detection} E --> F[Recompile Changed Programs Only] F --> G[Deploy Updated Load Module] G --> H[Verify in CICS]

The diagram above illustrates the high-level flow from a local COBOL edit all the way through to CICS verification. Only the components DBB identifies as changed are recompiled, making the build faster and more predictable.

2. System Architecture

The Bank of Z incremental build pipeline spans three distinct environments: the developer’s workstation, a Git remote repository, and the z/OS USS environment where DBB executes the build.

graph LR subgraph Developer Workstation A[IDE / Editor] --> B[Local Git Repository] end subgraph Git Remote C[Remote Branch] end subgraph z/OS USS D[USS Clone of Repository] E[pipeline-remote.sh] F[DBB - Dependency Based Build] G[COBOL Compiler] H[Load Library] end subgraph CICS Region I[Updated Transaction] end B -->|git push| C C -->|git pull| D D --> E E --> F F --> G G --> H H --> I

The three-tier architecture works as follows:

Layer Components Role
Developer Workstation IDE, Local Git Author and stage COBOL source changes
Git Remote Remote Branch Central version-control hub for collaboration
z/OS USS pipeline-remote.sh, DBB, COBOL Compiler, Load Library Change detection, compilation, and packaging
CICS Region CICS Transaction Runtime execution of the updated program

DBB sits at the heart of the z/OS layer — it analyses source dependencies, computes the build list from changed files, and drives the compiler for only those members that require a rebuild.

3. Prerequisites

Before starting this tutorial, confirm that all of the following conditions are met:

  • ✅ The Deploy Bank of Z tutorial has been completed successfully
  • ✅ Bank of Z has been built and deployed at least once
  • ✅ A working Bank of Z development environment is available
  • ✅ You have access to the Bank of Z Git repository
  • ✅ You have access to the z/OS USS environment where the pipeline runs

4. What You Will Learn

By the end of this tutorial you will be able to:

  • Make a targeted change to a COBOL program (BNKMENU.cbl)
  • Commit and push that change to a Git feature branch
  • Pull the latest source changes onto z/OS USS
  • Trigger an incremental build using pipeline-remote.sh
  • Interpret DBB output to verify that only the changed file was detected
  • Confirm that the affected program was included in the compiled output
  • Optionally validate the updated runtime behaviour inside a CICS transaction

5. Part 1 — Make and Push the COBOL Change

5.1 Locate and Edit BNKMENU.cbl

Open BNKMENU.cbl in your editor. The change demonstrated in this tutorial targets the invalid-key message string — a user-facing message displayed when an invalid menu key is pressed.

Typical location in the repository:

CODE 
Bank-of-Z/
└── src/
    └── cobol/
        └── BNKMENU.cbl

Locate the relevant COBOL paragraph and update the message literal. For example:

COBOL 
INVALID-KEY-HANDLING.
    MOVE 'INVALID KEY - PLEASE TRY AGAIN'
        TO WS-MESSAGE-TEXT.

Change the message to your updated text:

COBOL 
INVALID-KEY-HANDLING.
    MOVE 'INVALID SELECTION - ENTER A VALID MENU OPTION'
        TO WS-MESSAGE-TEXT.

5.2 Confirm the Correct Git Branch

Before committing, verify you are working on the intended feature branch:

BASH 
git branch
# Expected output highlights your active branch, e.g.:
# * feature/incremental-build-demo
#   main

If you are not on the correct branch, switch to it:

BASH 
git checkout feature/incremental-build-demo

5.3 Commit the Source Change

Stage and commit the modified file:

BASH 
git add src/cobol/BNKMENU.cbl
git commit -m "Update invalid-key message in BNKMENU"

5.4 Push the Change to the Remote Repository

BASH 
git push origin feature/incremental-build-demo

After the push, the change is available in the remote Git repository and ready to be pulled down to z/OS USS.

6. Part 2 — Run and Verify the Incremental Build

6.1 Connect to the z/OS USS Environment

Open an SSH session to your z/OS system:

BASH 
ssh user@your-zos-host

Navigate to the Bank of Z repository clone on USS:

BASH 
cd /u/youruser/Bank-of-Z

6.2 Confirm the Correct Git Branch on USS

BASH 
git branch
# * feature/incremental-build-demo
#   main

If the branch does not exist locally on USS yet, check it out from the remote:

BASH 
git checkout -b feature/incremental-build-demo \
    origin/feature/incremental-build-demo

6.3 Pull the Latest Source Changes

BASH 
git pull origin feature/incremental-build-demo

Expected output confirms that BNKMENU.cbl was updated:

CODE 
Updating a1b2c3d..e4f5g6h
Fast-forward
 src/cobol/BNKMENU.cbl | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

6.4 Run the Incremental Build Pipeline

Execute the pipeline script to trigger the DBB incremental build:

BASH 
./pipeline-remote.sh

The script coordinates with DBB to scan the repository for changed source members since the last successful build.

6.5 Verify That DBB Detects the Changed File

Examine the build log output. DBB prints a list of files it has identified as requiring a rebuild. You should see an entry similar to:

CODE 
[DBB] Detected changes:
[DBB]   src/cobol/BNKMENU.cbl  --> INCLUDED IN BUILD

This confirms DBB correctly identified BNKMENU.cbl as the only changed source file.

6.6 Confirm BNKMENU Is Included in the Compiled Programs

Further down in the build log, verify the compilation step:

CODE 
[DBB] Compiling: BNKMENU
[DBB] COBOL compile step RC=0
[DBB] Link-edit step RC=0
[DBB] Build complete. Programs compiled: 1

A return code of 0 on both the compile and link-edit steps confirms a successful incremental build.

6.7 Sequence of Build Operations

The following sequence diagram shows the interaction between all actors during the incremental build execution:

sequenceDiagram participant Dev as Developer (USS) participant Git as Git Remote participant Pipeline as pipeline-remote.sh participant DBB as DBB Engine participant Compiler as COBOL Compiler participant CICS as CICS Region Dev->>Git: git pull origin feature/incremental-build-demo Git-->>Dev: Updated BNKMENU.cbl Dev->>Pipeline: ./pipeline-remote.sh Pipeline->>DBB: Initiate incremental build DBB->>DBB: Scan changed files since last build DBB-->>Pipeline: Changed files: [BNKMENU.cbl] Pipeline->>Compiler: Compile BNKMENU.cbl Compiler-->>Pipeline: RC=0, Load module produced Pipeline->>CICS: Deploy updated load module CICS-->>Pipeline: Deployment confirmed Pipeline-->>Dev: Build complete — 1 program compiled

6.8 Optionally Validate the Updated Message in CICS

If you have access to a CICS terminal, log in and navigate to the Bank of Z main menu transaction. Trigger an invalid key press. The updated message text you entered in Step 5.1 should now appear on the screen, confirming the end-to-end deployment was successful.

7. Outcome

After completing this tutorial you have:

  1. Edited BNKMENU.cbl to change the invalid-key message
  2. Committed and pushed the change to a Git remote branch
  3. Pulled the update to z/OS USS
  4. Triggered an incremental build via pipeline-remote.sh
  5. Verified that DBB detected only the changed source file
  6. Confirmed that only BNKMENU was recompiled — no other programs were touched
  7. Validated (optionally) the updated behaviour at runtime in CICS

This workflow demonstrates the efficiency of DBB-driven incremental builds: by tracking source dependencies and change history, DBB eliminates unnecessary recompilation, reduces build times, and gives developers a fast, reliable feedback loop when iterating on z/OS COBOL applications.
