Tutorial: Deploy Bank of Z

Bank of Z includes a guided first-time deployment experience that demonstrates how the application moves from source code to a running hybrid IBM Z banking solution. This tutorial walks through the end-to-end deployment flow described in the project documentation: preparing a z/OS environment with prerequisites in place, cloning the Bank of Z repository to USS, running the three setup stages, and bringing up the full application stack so you can execute an initial banking transaction.

1. Overview

This tutorial is part of the broader Bank of Z tutorial set, which is designed to help users understand common development, deployment, and modernization workflows. The tutorials build on one another and show how application changes move from source code to deployment in a hybrid IBM Z environment.

By completing this deployment tutorial, you learn how to:

  • Build and deploy Bank of Z application components
  • Provision the required runtime stack
  • Deploy application code from source
  • Work with a hybrid IBM Z environment
  • Validate that the application is running successfully
  • Prepare for incremental day-to-day development workflows

The deployment shown here uses the Direct USS method, which starts from a prepared z/OS environment and performs a complete first-time setup.

1.1. Tutorial scope

This page covers the application-level deployment flow for Bank of Z:

  1. Start from a z/OS system where prerequisites are already installed
  2. Clone the Bank of Z repository into USS
  3. Run the three setup stages
  4. Automatically provision the runtime stack
  5. Build and deploy the application from source
  6. Access the frontend and perform initial validation
  7. Transition to incremental development using the remote pipeline script

1.2. What is deployed

A full first-time deployment provisions and deploys the main Bank of Z application components, including:

  • CICS
  • IMS
  • z/OS Connect
  • Liberty frontend server

These components work together to expose and process banking application functionality.

2. System Architecture

At a high level, Bank of Z is deployed as a multi-component application stack on IBM Z. The deployment process provisions middleware services and deploys application artifacts so that frontend requests can be routed to backend banking services.

graph TD A[Developer or Operator] --> B[USS Working Copy of Bank of Z] B --> C[Setup Stage 1] C --> D[Setup Stage 2] D --> E[Setup Stage 3] E --> F[Liberty Frontend Server] E --> G[z/OS Connect] E --> H[CICS] E --> I[IMS] F --> G G --> H G --> I

The diagram shows the first-time deployment path from source in USS through the staged setup flow into the runtime components that make up the Bank of Z application stack.

2.1. Core runtime components

2.1.1. USS source workspace

The Bank of Z repository is cloned into USS and serves as the deployment working directory. This is where the deployment starts and where the setup stages are run.

2.1.2. Three setup stages

The documentation describes three setup stages that are executed during first-time deployment. Together, these stages automate environment setup, stack provisioning, and build/deploy operations.

2.1.3. Liberty frontend server

The Liberty frontend server provides the web-facing layer for the application and is part of the stack provisioned during setup.

2.1.4. z/OS Connect

z/OS Connect acts as an integration layer between frontend-facing interfaces and backend IBM Z services.

2.1.5. CICS and IMS

CICS and IMS provide core transactional backend environments for Bank of Z application processing.

2.2. Component relationships

The following diagram highlights the relationships between the main entities involved in deployment and runtime execution.

graph TD A[Bank of Z Source Repository] --> B[USS] B --> C[Deployment Scripts] C --> D[Provisioned Application Stack] D --> E[Liberty Frontend] D --> F[z/OS Connect] D --> G[CICS Services] D --> H[IMS Services] E --> F F --> G F --> H

This relationship view emphasizes that the repository and scripts are not separate from the deployment story—they are the mechanism used to create and connect the full Bank of Z runtime stack.

3. Deployment Prerequisites

Before starting the tutorial, ensure the deployment environment is ready.

3.1. Required starting point

The documented deployment assumes:

  • A z/OS environment is already available
  • All prerequisites are in place
  • You are performing a first-time deployment
  • You are using the Direct USS method

Because this tutorial page focuses on the application-level process, prerequisite installation details are referenced rather than repeated here.

3.2. Reference for setup details

For the actual deployment procedure and prerequisite preparation, use the project’s deployment documentation:

  • Deploying Bank of Z: ../installation-and-setup/deploying.html

4. End-to-End Deployment Flow

The first-time deployment follows a simple but important sequence: move the source to USS, execute the setup stages, provision the stack, and deploy the application.

sequenceDiagram participant U as User participant Z as z/OS Environment participant S as USS Source Copy participant P as Setup Stages participant R as Runtime Stack U->>Z: Start with prerequisites installed U->>S: Clone Bank of Z repository to USS U->>P: Run setup stage 1 U->>P: Run setup stage 2 U->>P: Run setup stage 3 P->>R: Provision CICS, IMS, z/OS Connect, Liberty P->>R: Build and deploy application from source R-->>U: Bank of Z environment ready

This sequence captures the main operational path shown in the tutorial: setup stages are both provisioning and deployment mechanisms, not just initialization steps.

4.1. Step 1: Prepare the environment

Begin with a z/OS environment where all required prerequisites have already been installed and verified.

Expected outcome:

  • The system is ready for Direct USS deployment
  • Middleware dependencies required by Bank of Z are available
  • You can proceed directly to source onboarding and setup execution

4.2. Step 2: Clone the repository to USS

Clone the Bank of Z repository into USS. This creates the local working copy from which deployment scripts and setup stages are run.

Example command pattern:

BASH 
git clone <bank-of-z-repository-url>
cd Bank-of-Z

This code example reflects the repository cloning step described in the tutorial narrative.

4.3. Step 3: Run the three setup stages

After cloning the repository into USS, run the three setup stages in order. The documentation states that these stages automatically provision the complete application stack and build/deploy the application from source.

General staged flow:

BASH 
./stage1.sh
./stage2.sh
./stage3.sh

If your environment uses different script names, follow the deployment instructions in the referenced setup documentation. The important concept from the tutorial is that all three stages are required for a complete first-time deployment.

4.4. Step 4: Provision the full application stack

During the staged setup, Bank of Z provisions:

  • CICS
  • IMS
  • z/OS Connect
  • Liberty frontend server

This means the deployment is not limited to copying code. It creates the application runtime context needed for the banking solution to function end to end.

4.5. Step 5: Build and deploy from source

The setup stages also perform the build and deployment of Bank of Z application components from the cloned source repository.

Expected result:

  • Application components are built from source
  • Artifacts are deployed into the target runtime stack
  • Frontend and backend services are connected and ready for validation

5. Data Flow Through the Deployed Application

Once deployed, Bank of Z supports business transactions through a layered flow from frontend to backend services.

graph TD A[User Request] --> B[Liberty Frontend Server] B --> C[z/OS Connect] C --> D[CICS Transaction Processing] C --> E[IMS Transaction Processing] D --> F[Banking Response] E --> F

This data flow illustrates how a user-initiated banking action can traverse the deployed architecture. The frontend receives the request, z/OS Connect mediates access to backend services, and the transactional environments process the operation and return the result.

5.1. Why this flow matters

This flow is central to understanding Bank of Z as a hybrid IBM Z application:

  • The frontend is separated from backend transaction engines
  • Integration is handled through z/OS Connect
  • Business processing can span multiple IBM Z middleware environments
  • Validation after deployment should confirm not just startup, but successful end-to-end transaction behavior

6. Running the First Banking Transaction

After deployment completes successfully, the next milestone is to validate the system by running an initial banking transaction through the deployed application.

6.1. Validation objective

The goal of the first transaction is to confirm that:

  • The frontend is reachable
  • z/OS Connect is functioning
  • Backend transaction services are available
  • The deployed application behaves correctly after provisioning and build/deploy

6.2. Example validation flow

sequenceDiagram participant User participant Frontend as Liberty Frontend participant API as z/OS Connect participant Tx as CICS/IMS participant App as Bank of Z Application User->>Frontend: Submit banking action Frontend->>API: Send service request API->>Tx: Invoke backend transaction Tx->>App: Execute business logic App-->>Tx: Return result Tx-->>API: Transaction response API-->>Frontend: Service response Frontend-->>User: Confirmation or result

This sequence is useful when troubleshooting deployment validation because it shows each stage that must be working correctly for the first transaction to succeed.

6.3. Success criteria

A successful first transaction indicates that the deployment has achieved its intended outcome:

  • Source has been correctly deployed
  • Runtime services are active
  • End-to-end connectivity is working
  • The application is ready for further development and testing

7. Transition to Day-to-Day Development

After a successful first-time deployment, the recommended workflow changes.

7.1. Use incremental build and deploy

The documentation explicitly recommends using the incremental remote pipeline workflow for normal development instead of repeating full deployment after every code change.

Use:

BASH 
pipeline-remote.sh

This is the preferred day-to-day workflow once the full environment has already been established.

7.2. Why incremental deployment is recommended

A full first-time deployment is designed to establish the entire Bank of Z runtime stack. After that baseline exists, incremental deployment is more efficient because it allows developers to:

  • Apply changes faster
  • Avoid recreating the whole stack unnecessarily
  • Validate updates in a more typical development cycle
  • Focus on application changes rather than environment recreation
